## 一、问题（修之前）

- `UploadQueue.offer()` 判"文件变没变"**只比字节数**：`size <= old.size` 即跳过（`engine/upload_queue.py` 旧实现）。
- `report.md`/`report.html` 每次判读或人工复核都被删掉重生成（`app/server.py::_stale_reports`），`findings.json` 判读重跑整个换掉（`inspect/judge.py:352`）——都是**原地改写、字节数常常相同或更小**。
- 后果（此前已复现）：本地 `NEW REPORT`，服务器仍是 `OLD REPORT`；变大的文件靠服务器哈希核对能救（`rewound`），同大或变小的永远传不上去。

## 四、已知边界（诚实列出）

- 判据是 **mtime + size**，不是内容哈希。以下情况仍会漏：同一纳秒内的改写；`cp -p`/`rsync -t` 保留 mtime 的覆盖；时钟回拨到恰好相同。这些场景对 `findings.json`/`review.json`（`_atomic_write`：写临时文件再 rename，新 inode 新 mtime）和 `report.md`/`report.html`（`_stale_reports` 先 unlink、`write_reports()` 再 `write_text` 新建——不是原地覆盖）都不会发生；若发生且文件变大，服务器哈希核对仍能救，同大则漏。选 mtime 是因为每轮 `scan()` 全目录哈希在 Orin 上代价不可接受。
- ~~老条目"只记 mtime 不重开"意味着升级前最后一次改写不会被发现~~ **外部审核判为阻断项，已修（`2d18615`）**：老队列里的 `done` 对改写型文件不可信（升级前最后一次判读可能已换掉内容，而没进 pending 的条目服务器哈希也救不了），所以改写型文件第一次见到 mtime 即从 0 重传一次；照片、追加流从不原地改写，只记 mtime。代价：升级后每趟的报告/findings/review 各重传一次，都是小文件。
- 照片：`engine/archive.py::save_photo` 用秒级时间戳命名、`write_bytes` 不查重，同一航点同一相机同一秒内两张会静默覆盖。升级**之后**发生的覆盖，mtime 分支照样抓到（对所有已知 mtime 的条目生效，不限改写型）；升级**之前**发生、且老队列已 `done` 的那张会漏——窄、既有、与本单无关，记在这里。
- 新增一条维护规矩：以后加一种会被原地改写的文件，必须同时进 `_EXACT` 和 `REWRITTEN_IN_PLACE`（W03 会加 findings/review/report.html 进 `_EXACT`，`REWRITTEN_IN_PLACE` 已预先含它们）。
