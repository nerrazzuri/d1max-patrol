## 三、最终形态

```
/var/lib/d1max/            ← D1MAX_DATA_ROOT（服务单元设；开发机不设 → 仓库相对路径）
  runs/                    ← --runs-root（slam/、bags/、logs/ 在它底下）
  missions/                ← --missions-dir
  queue.jsonl              ← runs_root.parent / QUEUE_FILE_NAME（代码未改，自动落对）
  baselines/  exports/     ← 同上
```

`SLOT_DATA_ITEMS = ("runs", "missions", "queue.jsonl", "baselines", "exports")` 同时是：`prune()` 保险检查的清单、`migrate_slot_data` 搬运的清单。

装机 7/7（`deploy/install.sh:497-507`）：

```bash
systemctl stop d1max-patrol.service || true          # 第一次装机服务不存在，stop 报错要吞
if systemctl is-active --quiet d1max-patrol.service; then   # 停不掉就别搬：搬的前提是没人在往槽里写
  echo "  !! 服务停不掉,跳过数据迁移 ..." >&2
else
  sudo -u "$RUN_USER" env D1MAX_RELEASE_ROOT="$ROOT" D1MAX_DATA_ROOT=/var/lib/d1max \
    "$ROOT/bin/python" -m d1max_patrol.cli release migrate-data \
    || echo "  !! 槽内数据迁移没成功。没搬动的原名文件受 prune 保护;已改名 *.migrated 的不受 ..." >&2
fi
systemctl start d1max-patrol.service
```

## 五、执行中发现并改掉的计划错误（4 处）与评审追加（4 处）

| # | 计划原文 | 错在哪 | 改成 |
|---|---|---|---|
| ① | 保险命中后 `continue` | 会跳过被保护的槽去删**下一个**槽凑 `keep` 配额——[A(有数据), B, C(当前)] 会删掉无辜的 B | `break`；测试 `dropped == ()` 钉住 |

## 八、没做 / 真机项 / 后续账

- **没有真机**。以下必须上机验：老机器升级后 `/var/lib/d1max/runs` 历史齐不齐；`journalctl -u d1max-patrol` 没有"还有巡检数据"警告；`ls /opt/d1max/releases/*/` 只见 `*.migrated`；第一次装机 `stop` 报错被吞、`start` 成功。
- **文件属主**：`copy2` 不保留属主。装机脚本以服务用户跑迁移，属主正确；人手工用 `sudo` 跑会归 root——CLI 已打告警，未强制。
- **OTA 升级路径不更新单元文件**（评审 I1）：只加了启动警告。根治要让升级包携带 `deploy/d1max-patrol.service` 并在 `activate` 时装入（需要 root，服务以 `robot` 跑）——这是新工单，记入工单表。
- **prune 因数据拒删时只有日志**：槽会一直累积到有人跑 `migrate-data`。该上报到值守屏/自检，记在工单表 W01 行"后续账"。
- **`*.migrated` 副本不自动删**：数据翻倍直到人核对后手删；文档已写。可考虑后续给 `migrate-data --purge-verified`。
- **数据根是符号链接时**：`chown`/`rm_sys` 只动链接本身（评审 M4），与 `/opt/d1max` 同类，未处理。
- 计划里"2–3 周"之类工期从未出现在本工单；本工单从计划到完工在一个会话内。
