## SDK 侧待验证(2026-09-01 追加)

原先判"本次现场不碰 SDK",前提是出门的笔记本跑 Windows。前提已变 —— 实际带出去的是
**Ubuntu 22.04 x86_64**,而这正是厂商 SDK 的官方指定平台(`RobotSDK-0.2.0/README_zh.md`:
Ubuntu 22.04 / GCC 11.4 / CMake 3.8+ / Boost 1.74)。`lib/x86_64/librobot_sdk.so.0.2.0`
只依赖 libc / libgcc_s / libstdc++,最高要 GLIBC_2.34 与 GLIBCXX_3.4.30,22.04 的
glibc 2.35 与 libstdc++ 3.4.30 都够。所以这一趟顺带侦察 SDK。

## SDK 运动控制实测(2026-09-01 现场补)

真机跑通了 SDK 运动控制(站起 + 前进)。程序见 `motion/`(m0/m1/stand2/walk1/walkonly),日志见 `runs/field-logs/`。

| # | 结论 | 证据/说明 |
|---|------|----------|
| 34 | **SDK 控制口 = 8082(UDP)**,不是 8081;8081 恒 `ShakeHand failed`。/dev/tcp 探不到 8082 属正常(UDP) | `walk-*.log` |
| 35 | **运动控制必须用 SDK 0.2.0**:只有它有 `SwitchRemoteState`,能把机器从 `MachineStatus::IDLE` 唤醒到 `REMOTE`(电机上电)。0.1.1 无此接口,连站都站不起来(m1 失败) | `stand2` 成功 / `m1` 失败 |
| 36 | 开机/重启后机器在 IDLE、瘫软趴地。可靠站立时序:`Connect → TakeControl → SwitchRemoteState → StandUp`,站起给足 ~6s | `stand2.cpp` |
| 37 | 行走时序:站起后 `Gait() → Move(lat,fwd,yaw)`。**`Move` 量级是关键**:`fwd=0.11`(官方 'w' 键值)太慢几乎不动;`fwd≈0.3~0.5` 才明显走(官方文档 Move 例子用 0.5)。**之前"站起不走"实为量太小,非模式问题(此前的模式推断已被实测推翻)** | `walkonly.cpp` |
| 38 | `Move` 单位=百分比、受 SpeedLevel 限速,一条 Move 维持 1s(`docs/zh/sdk_client_api_zh.md`);fwd≈0.5 时约 0.5–0.6 m/s(与只读 `get_speed x=0.6` 吻合) | 文档 + 实测 |
| 39 | **遥测坑**:0.2.0 下状态上报解析报错 `key 'current_state' not found`,`OnRobotStateData/OnMcData/OnSpeedData` 不触发 → 读不到 machine/motion/里程/速度。0.1.1 遥测正常(data 例子出全量 IMU100/运控50/速度20Hz)。**控制用 0.2.0 却看不到状态,采数据用 0.1.1** —— 回去要厂商一个"既能激活控制又能正确解析遥测"的版本,或修 `current_state` 字段差异 | `sdk-data2.log`(0.1.1 全量) vs `walk-*.log`(0.2.0 machine=?) |
| 40 | **连接坑**:SDK 会话断开后偶发 `Controlled denial of service`;重启 RK3588 可清;但趁机器站着常可直接重连,未必每次都要重启 | `walk-*.log` |
| 41 | `SoftEmergencyStop(true/false)` 与 Ctrl+C 软急停可用;硬急停(机身按钮)仍是最终保障。控制权规则:App 在则 SDK 拿不到控制权(#21),做控制需先退 App | `motion/*` SIGINT |
