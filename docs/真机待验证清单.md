## 第 1 卷：电量、原点与起飞门槛（2026-09-11 补，尚未上机）

**这一卷做得最早，当时没建这份清单，所以一直是空的。** 它是门槛卷：
`run_preflight` 那七项决定狗出不出发。拦不住是安全问题；误拦是当天一条巡检都
起不来，而人会先去查导航、查任务包，查半天才想到是门槛卡的。
现场条目见《真机现场执行单》8.0.1–8.0.9 与 7.4a。

- **【最要紧的一条】`start_nav_return_home` 到底回到哪个点。** 我们整套回航设计压在
  一个从没验过的假设上 ——「调它，狗会回到我们 `save_home` 存的那个原点」。如果
  厂家的 home 是它自己的概念（建图起点／充电桩／上次重定位的位置），跟我们存的
  **不是同一个点**，那么 `departure_line_pct`、`battery_return_pct`、
  `battery_abort_pct` 三条线算的全是另一段路，`route_length_m(home.pose, poses)`
  的起终点是错的。**这是假设对不对，不是实现对不对** —— 仿真里永远问不出来，
  假后端就是按我们以为的样子回答的。跟第 8 卷 10.21（重新规划还是重放缓存路径）
  不是同一个问题：那条问"怎么回去"，这条问"回到哪儿"。
- **`estimate_cost_pct` 的每米耗电到现在还是拍的。** 出发线和返航线两条式子都建在
  它上面。跑完一整条线量一次真实耗电（起飞电量／路线全长／落地电量），拿真值回来
  校。前提是上一条判成"回的就是我们存的那个原点"，否则量的是另一段路。
- **`_check_removable` 里 `disks is None`（没扫过）和空列表（没有盘）在真机上说的话
  是不是不一样。** 两种情况都判不过，但**原因完全不同**：一个是"我不知道"，一个是
  "我知道，没有"。措辞一样的话，现场的人没法区分"扫描坏了"和"盘没插"。
- **`_check_storage` 的探针文件在 Orin 上真写得进去。** 它会在 `runs/` 下真写一个
  `.preflight_probe` 再删掉。只读挂载、权限不对、同名文件占位都只在真机上暴露 ——
  这一项假过，第一张照片就会存不下去，而那时狗在外面。
- **原点落盘之后跨进程重启还在不在。** `save_home` / `load_home` 在开发机上走的是
  本地文件系统；Orin 上 `runs/` 可能在 eMMC，掉电和 remount 的行为都不一样。
- **电量读数的真实刷新率和抖动。** 三条线（出发／返航／中止）都拿瞬时电量比阈值。
  如果真机电量是跳变的（负载一上来掉 5%，松开又回来），会在阈值附近反复触发。
  仿真里电量是我们喂进去的一个干净数列，**抖动这件事根本不存在**。

## 保留、基线与导出（2026-09-06 追加，来自整卷终审，尚未上机）

盘的行为在仿真里全是假的：`tmp_path` 不会满、不会被挂成只读、`shutil.disk_usage`
在开发机上读的是一块 SSD。下面每一条都是「只有真机能回答」的。

- **`runs/` 到底在哪块盘上。** `df -h`，看 `_disk` 读的是 eMMC 还是 NVMe。读错盘
  水位线就是个假数字——所有删除决策都建在它上面。顺带确认 `baselines/` 和
  `exports/` 是不是同一块（今天按构造是同一块，见第 2 卷待办 16）。
- **ext4 的 root reserve 是多少个百分点。** 默认 5%：非 root 进程会在 `used==total`
  之前约 5% 就吃到 ENOSPC。`STOP=0.90` 是否还留得住余量，要按实测值回头核。
- **把盘填到 100%，打开盘况页。** 期望：200，`notice_written: false`，页面照常显示
  用量和名单（这是 I1 的修复，仿真里只能 monkeypatch 出来）。
- **把盘 remount 成只读，走一遍盘况 / 清扫 / 导出。** EROFS 在 Orin 上极常见。
- **盘 90% 满的时候导出一个包。** 看它是在写 zip 的中途 ENOSPC，还是先拒绝。
- **导出一个区间，区间里有一趟正在跑的任务。** 这是 C1 的复现路径，期望被拒。
- **两个客户端同时刷盘况页。**（I6 复现）此后 `retention-notice.json` 必须仍是完整
  JSON，且**已有条目的时间戳一个都没变**——变了就是 7 天的钟被清零了。
- **两个客户端同时保存同一个任务。**（第 2 卷待办 17，尚未修）看 yaml 会不会写成半截。
- **手机浏览器和 Flutter app 各下载一次导出包**，两边都重算 sha256 对上。
  `ByteStream` 不带 `Content-Length`，截断在 HTTP 层不可见。
- **断电三处**：写 zip 的中途、`replace` 之前、写台账的中途。开机后分别应该是
  「没有这个包」「没有这个包」「台账是上一份完整的」。
- **走完一整轮 7 天的钟**：预告落盘 → 第 7 天之前不许删 → 第 7 天之后按水位删。
  这条只能靠改系统时间或等，但必须真走一遍。
- **在装满 2 万趟归档的盘上给 `scan_runs` 计时。** 它每趟做若干次 stat，eMMC 上很慢，
  而它挂在 HTTP 请求路径上。
- **量 `baselines/` 的真实体积**，按 4K 照片算。基线集永不删，它的增长是无上界的。
- **`runs/` 底下有没有人手工拷进去的目录。** 手工拷贝的时间戳目录会被 `scan_runs`
  当成正经归档，`_make_dir` 的 `-2`/`-3` 后缀也在解析范围内。

## 备份盘（2026-09-06 追加，来自第 3 卷，尚未上机）

1. 真的挂载点：`/media/<user>/<label>` 下能不能被 `MountRootProbe` 扫到，`os.path.ismount` 判得对不对。
2. 备份盘上跨文件系统的 `Path.replace`：exFAT / ext4 上原子改名是否真的原子；exFAT 上文件名带中文（任务名）能不能写。
3. `os.sync()` 在 Orin NX 上刷一块 2T 机械盘要多久——安全弹出会不会把 HTTP 请求卡到超时。
4. 拷一趟 500 MB 的归档 + 重算两遍 sha256 的耗时，以及这期间的 CPU 占用会不会影响正在跑的巡检。
5. 同步中途拔盘：`shutil.copyfile` 抛的到底是不是 `OSError`，会不会挂死。
6. 备份盘写满：ENOSPC 出现在拷贝中途时，`failed` 里那句话是否说得清。
7. 镜像盘装机的三种方式（甲 独立物理盘 / 乙 仓内短线 / 丙 超短 nano 盘）实测——**同一块盘再分一个分区不算备份，这条要在装机手册里写死。**
8. 一块盘先给 A 狗初始化，再插到 B 狗上。**真机才答得了的是挂载点这一半**：同一块盘在
   两台狗上的挂载路径很可能不一样（udev 按 label 还是按 UUID 命名），而认盘靠的是盘上的
   标记不是路径——要在两台真狗之间实测一次这个假设成立。顺带确认 B 狗的拒绝文案里两边
   的 SN 都真的打得出来。
9. 断电重启后 `.d1max-backup/state.json` 还读得出来（掉电测试）。
10. **拷贝途中拔盘。** 一趟大归档同步到一半直接把备份盘拔掉，确认根文件系统上的
    `/media/<label>` 里**一个字节都没有**，并且 `df` 看 eMMC 占用没涨。这条验的是
    「盘还在不在」的判据用的是盘上的标记文件而不是 `mount.exists()`——卸载之后挂载点
    通常作为一个空目录留在根文件系统上，而 `_copy_file` 第一行就是 `mkdir(parents=True)`。
    离机测得到「不写」，测不到的是**真机上卸载之后那个目录到底还在不在**。
11. **并发清盘与同步。** 同时发 `POST /api/backup/sync {"apply":true}` 和
    `POST /api/storage/sweep {"apply":true}`，确认后到的那个拿到 409 而不是两边一起
    动盘。离机那条测试是摆状态摆出来的，真机这一次要**真的并发**——两个 curl 同时发。
12. **自动同步的 60 秒周期没有真机依据。** 这个数是拍的。要实测的是两件事：归档攒到
    几百趟之后 `plan_sync` 那一趟递归 stat 要多久（`retention.py` 里算大小用的是
    `rglob("*")`），以及每分钟醒一次会不会让一块机械镜像盘永远进不了休眠。前者决定
    周期的下限，后者可能要求把周期拉到几分钟甚至改成「有新 run 落地才醒」。

## 装机、升级、回滚（2026-09-07 追加，来自第 4 卷，尚未上机）

`deploy/install.sh`、那一个 systemd 单元、`docs/装机清单.md` 都只在仿真里核过
约定（见 `tests/test_deploy_files.py`），没有一条在真的 Orin / systemd 上跑过。

1. **`ExecStartPre=-` 在 Orin 的 systemd 上真的是「先跑一遍、它失败也不拦
   服务」。** 守卫已经并进 `d1max-patrol.service` 的一行 `ExecStartPre=-`，
   单独的 `d1max-bootguard.service` 删掉了（原因：不带上装的机器升级走的是
   `systemctl restart`，根本不开机，`WantedBy=multi-user.target` 的老单元在
   那条路上一次也不会跑）。真机上要分三步确认：
   - 每一次 `systemctl restart d1max-patrol.service` 之后，`journalctl` 里
     都能看到守卫跑过一遍（不只是开机那一次）。
   - 守卫非零退出时服务照样起得来。`-` 前缀的语义只在 systemd 文档上核过，
     没在 Orin 那个 systemd 版本上实跑过。**手工验法**：把
     `/opt/d1max/bin/python` 临时改名，`systemctl restart`，服务应该照常起来。
   - 老机器上残留的 `d1max-bootguard.service` 被 `install.sh` 里那两行
     `disable --now` / `rm -f` 干净摘掉了（`systemctl list-unit-files | grep d1max`
     只剩一个）。
2. **`os.replace` 换符号链接在 Orin 的文件系统上是原子的。** 双槽 + 一个
   `current` 链能不能换版本、能不能回滚，全建在这条原子性假设上；开发机
   上是 NTFS/常规 ext4，Orin 上跑的是哪种根文件系统（可能只读、可能
   overlay）没有验过。
3. **拔电重启后守卫真的能数到第二次并退回去。** `boot_guard()` 的判据、
   `MAX_BOOT_ATTEMPTS` 的组合都只在测试里模拟过重启，没有真的拔电源、
   让 Orin 冷启动两次去触发这条自动回滚路径。
4. **整机重启那条路在装了上装的机器上会不会跟上装抢开机窗口。**
   `restart_plan(has_payload=True)` 选的是整机重启而不是只重服务，
   而 §7.1 的现场结论（`真机结果` #46/#47）是控制权一旦被上装拿走就抢不
   回来——整机重启之后我们的服务和上装谁先抢到 SDK 会话，没有实测过。
5. **`systemctl restart` 之后 SDK 会话真的抢得回来（没上装的机器）。**
   `restart_plan(has_payload=False)` 假设只重启我们的服务就够，重启期间
   SDK 会话会不会被别的东西（哪怕只是短暂的空窗）抢走，只有真机重启一次
   服务才知道。
6. **`User=robot` 在默认 polkit 下到底能不能 `systemctl restart` /
   `systemctl reboot`。** 单元里写的是 `User=robot`（`d1max-patrol.service:8`），
   而升级和自检回滚都要由这个进程去发重启命令。开发机上没有 polkit，这条
   一次都没真跑过。**危险在于失败是静默的**：`_spawn_restart`
   （`app/server.py:470-476`）只 `Popen` 就返回、不看返回码——被 polkit 拒了
   的话，界面上照样显示「已重启」，而机器一动没动。真机上先手工跑一次
   `sudo -u robot systemctl restart d1max-patrol.service`，拒了就得配
   polkit 规则（或者 sudoers 白名单），并且回头把 `_spawn_restart` 改成
   看返回码。
7. **`pip install <本地目录>` 是不是真的会往源目录里写 `*.egg-info/`。**
   这是 `install.sh` 里那两次 `mktemp -d` + `cp -a` 的**前提**（第 2/7、4/7 步）：
   直接对包目录 `pip install` 会就地生成构建产物，而这个目录随后要被
   `release install` 算树哈希——多出来的文件会让哈希跟 `release.json` 里
   记的对不上，第一次装机就自己把自己判成坏包。这个前提在 Orin 那个 pip
   版本（可能带也可能不带 build isolation）上没验过。**验法**：装完之后
   `ls <包目录>`，确认里面没有 `*.egg-info/`、`build/`、`__pycache__/`；
   要是 pip 本来就不会污染，那两次复制是白花的（但也无害，可以留着）。

### 视频

- [ ] **视频端到端延迟。**
      量法：手机拍一个跑着的秒表屏幕，把手机举到狗的相机前，同时拍到秒表和 app 里的画面，

- [ ] **视频掉线时摇杆确实变灰，而且够快。**
      量法：遥控中把相机的网线拔掉 / 把 RTSP 源停掉，看杆多久变灰。
      账：狗那头 `STALE_S = 2.0`，加手机这头一次 2 秒轮询，**最坏 4 秒**。
      **超过 5 秒就要把轮询调密。**
- [ ] **`anyLive` 判的是「任意一路有画面」，而屏上画的是 `front` 那一路。**

- [ ] **退避上限 16 秒，人的体感能不能接受。**
      `live_video.dart:278` 的 `_backoffMax = 16s`（2→4→8→16）。

- [ ] **狗真实吐的 `content-type` 是什么。**
      仿真里是我们自己造的。真机上抓一次 `GET /api/video/<name>` 的响应头，
      确认 multipart 的 boundary 解析走得通。解不开的话画面根本不出来。
- [ ] **`/api/video/<name>` 上 `Authorization: Bearer` 到底带没带。**
      `app/auth.py` 对几个浏览器 API 够不着请求头的路径破例认 `?token=`，
      **但手机 app 一律走请求头**。真机上抓一次包确认这条路上头是带着的 ——
      带错了的表现是 401，而不是画面花，容易被当成网络问题查歪。
- [ ] **轮询会不会跟 MJPEG 抢带宽（对照实验，这一条最花时间，安排一整段）。**
      量法：在 `mobile/lib/ui/widget/live_video.dart` 的**解码处打时间戳**，
      同一机位、同一距离、同一姿态，跑三段各 **120 秒**：
      **A** 不轮询 / **B** 3 秒轮询 / **C** 1 秒轮询。

      **这条测试的保护范围窄于它的名字** —— 真数拿回来之后改常量，不要在仿真里
      再堆一层猜出来的 dp。

## 第 8 卷：值守与远程接管（2026-09-10 追加，尚未上机）

### 接管完能不能接着跑（挂账 57，2026-09-10 人拍的板）

规则是人定的：人按「继续」时，狗**不在地图里就直接报错**（明说找不到下一个点），
**在地图里就接着跑下一个节点**。下面几条是这条规则**只有真机能答**的部分。

- [ ] **把狗开出地图范围，`LOC_LOST` 到底亮不亮、隔多久亮。**
  这是整条规则的地基。仿真里 `LOC_LOST` 是我们自己造出来的事件，
  真机上它由厂家定位模块（路线甲）或定位桥的时间窗（路线乙）说了算。
  **两条路线各测一次** —— 它们判丢的机理完全不同：甲是厂家黑盒，
  乙是 `local_nav.py` 的 `_refresh_loc()` 那个「单帧 TF 查不到不算丢」的时间窗
  （`_on_pose` 里 `ok=False` 不立刻判丢，改按位姿新鲜度算）。
  要记的数：**从走出地图到 `LOC_LOST` 亮，隔了多少秒。**
  这个延迟就是「人已经按了继续、系统还以为一切正常」的窗口。

- [ ] **反过来验：定位好着但规划不出路。**
  把狗从暂停点搬到**隔断另一侧**（定位不丢，但过不去），按继续。
  按我的实现读法这里该报「到不了下一个点」而不是「不知道狗在哪儿」。
  **要是真机上这种情况也直接把定位丢了，那我那半条实现读法就是多余的**，
  当场删掉，只留 `LOC_LOST` 一条。

- [ ] **正常情况别误伤。** 暂停 → 手动开出去几米 → 开回来 → 继续，
  必须能接着跑，不许因为动过就报错。这条是防「拦过头」的对照组。

- [ ] **报错之后人怎么办。** 报了「不在地图里」之后，
  人还有没有路把这趟任务救回来（重定位？中止重跑？），还是只能中止。
  这条现在没有答案，真机上跑一次就知道该不该补个出口。

### 返航途中被接管，接管完点继续（挂账 71 的另一半，Task 13 的真解）

- [ ] **BLOCKING：`start_nav_return_home` 到底是从当前位姿重新规划，还是重放一条
  缓存的路径。** 这一条不验清楚，「人中途接管后回航」那一整套的行为全是猜的 ——
  仿真里只能看到下发记录（我们确实又下发了一次返航），**看不到狗是不是真的重新
  找了路**。做法：返航途中让开腿，把狗**横向搬开几米**（不出地图），点继续，
  看它是**从当前位置重新规划回家**，还是先绕回被接管前那条老路上再走。
  **后者意味着 Task 13 的实现读法不成立**，那一整块要重做。

### 三条待标定常量、四个数值（挂账 72，现场标定之前不许当结论）

**口径先说清**：待标定的常量是 **3 条**（`AGGREGATE_WINDOW_MS`、`ESCALATE_AFTER_MS`、
`SUSPEND_STALE_MS`），要量的数值是 **4 个**（合并窗口 1 个、升级 2 个、挂起超时 1 个）——
升级那一条常量本身带两档，所以常量数和数值数不相等。
别的文档里的「三个」是在数常量、「四个」是在数数值，**两个数都对，
差别只在数的是什么**。

这几个数今天全是**拍的**，没有任何现场依据。每一条都要在一次**真实的**连续故障
或一次**真实的**接管上量，量完把数写回 `src/d1max_patrol/engine/alerts.py`
和 `engine/lease.py` 的常量注释里，并在这份清单上销掉。

- [ ] **合并窗口 15 分钟（`AGGREGATE_WINDOW_MS`）合不合适。**
  找一次真实的连续故障（比如一路走一路掉定位），看 15 分钟把它合成了几条。
  **合成一条就等于现场只看见一次** —— 合太狠，人会漏掉「它一直在犯」；
  合太松，屏上会刷屏到没人看。要记的数：那次故障实际发生几次、合成了几条。

- [ ] **升级 2 分钟 / 5 分钟（`ESCALATE_AFTER_MS`）。**
  这两个数问的其实是同一件事：**现场的人从告警响起到掏出手机，平均多久。**
  量法：找几次真实告警，记「屏上亮」到「有人按确认」的时间。
  超过 5 分钟才有人看的话，第二档（响铃）就白设了。

- [ ] **挂起超时 10 分钟（`SUSPEND_STALE_MS`）。**
  一次真实的接管平均多久 —— 从点「让开腿」到点「继续」。
  远超 10 分钟的话，现在这条超时会在人还没干完的时候就把它判成陈旧。

### 值守屏那六项在真机上是不是都拿得到

- [ ] **`usable` 和 `measured` 在真机上会不会长期不相等。**
  仿真里两个数一直一样（假盘不掉线）。真机上插着的盘掉一次线，
  `usable` 还是「声称能用」的那个数、`measured` 会掉下去 —— **这正是要报两个数的
  理由**。现场至少看见一次两者不等，才算证到了这个设计有用。

- [ ] **`battery_as_of_ms` 在真机上落后多少。** 仿真里电量事件是我们自己推的，
  想多新就多新。真机上要记：值守屏上那句「几分钟前」，实际最常见的是几分钟。
  **这个数决定要不要给它加一条「太旧就报警」的门槛** —— 现在**没有**门槛。
