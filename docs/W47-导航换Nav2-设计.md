# W47 导航换 Nav2 · 设计

> 2026-10-29 用户：导航和避障是整个项目的核心，要做到机器狗自主巡逻、不用太多人干涉。定的路子：
> **先做仿真基准，再加一个 Nav2 后端跟现在的导航并存、对比**；厂家导航不直接用，只借它的参数（真机项 §3aj）。
> W08 写死的切换条件「过不了 1.2 m 宽的通道就换 Nav2 的控制器」已经触发：现在最窄要约 1.34 m。

## 一、目标、不做的

**目标**
- 加一个导航后端 `--nav nav2`，跟 `planned`（现在的）并存，代理参数切换，引擎、站点、任务一行不改。
- 窄门（0.8–0.9 m）能过；局部避障、脱困用成熟的控制器和行为树，不再一条条手写规则；能用上横移。
- 仿真里同一批场景比两个后端的成功率，Nav2 明显好才上狗调参、改默认。

**不做的（这一单）**
- 不碰定位：定位器、可信度判断、重定位都照旧，Nav2 只吃代理认可的位姿。
- 不换站点、引擎、区域管理、告警。
- 地形层（坡、台阶、泳池边）、人的避让层、路网：后续单子，先把主体跑通。
- 不删 `planned`：Nav2 在真机上调顺、改成默认以后，留一阵当退路。

## 二、谁跑在哪

V2 起都在 3588 上（今天 C40221 上在厂家 Orin 上，一样的装法）：

```
传感器(厂家 Orin) ──► 感知节点(我们的)──障碍点云──┐
                   └► 定位器(MOLA)──位姿──► 代理 ──位姿──► nav2 转接节点 ──map→odom TF──► Nav2
                                              ▲   │                        ◄──cmd_vel──┘
                                              │   └─目标/取消──► 转接节点 ──NavigateToPose──► Nav2
                              守卫、禁行区闸 ◄─┘ cmd_vel(经套接字)
                                   │
                                   ▼
                                  HAL(旁路)
```

- **Nav2**（`d1max-nav2.service`，开源包，apt 装）：规划、控制、代价地图、行为树、速度平滑。
- **nav2 转接节点**（新，`d1max_nav2bridge`，rclpy，在 localizer 包旁边）：
  - 跟代理之间是本机 Unix 套接字，一行一个 JSON，跟定位桥同一套写法（契约 `navbridge.py`）。
  - 发 `/map`：当前地图 + 禁行区烧成致命格（keepout）；限速区发 speed filter 的掩膜。区域改了重发。
  - 发静态 TF：`base_link → front_lidar / rear_lidar`（`frames.json`）。
  - 发 `map → odom`：用代理送来的「可信位姿 + 那一刻的里程」算（见「三」）。
  - 收代理的目标、取消，调 Nav2 的 `NavigateToPose`；把反馈、结果回给代理。
  - 收 Nav2 的 `cmd_vel`，转给代理。
- **感知节点**多发一个话题 `/d1max/obstacle_points`：已经去了地面、去了机身的障碍格中心点（`base_link`）。Nav2 的障碍层吃它。这样两台半球雷达的地面分割、倒装雷达、自滤这些现场调好的东西都还用得上。
- **代理**：新后端 `Nav2NavBackend`，继承直线桥的状态机（跟 `PlannedNavBackend` 一样），只换 `goto`、`return_to`、`stop`、每拍 `step`。

## 三、几个要定死的地方

1. **谁说了算**：代理。
   - Nav2 出的每条速度都经代理：先过禁行区闸、守卫（只拦真看到的挡；两侧看不见的由 Nav2 的代价地图管，不再「看不见当挡」，那条规则就是 10-28 一串阻断的根）、限速，再给 HAL。
   - 定位不可信：代理撤目标、停车，跟现在一样；`map→odom` 不再更新，Nav2 那边 TF 过期自己也会停。
2. **`map→odom` 怎么算**：代理每收到定位器一帧可信位姿 `T_map_base(t)`，配上它自己那一刻的里程 `T_odom_base(t)`（HAL 的里程跟 `/tf` 的 `odom→base_link` 是同一个运控里程），送给转接节点。
   转接节点算 `T_map_odom = T_map_base · T_odom_base⁻¹`，按 20 Hz 发最新那份。定位跳了（重定位）就是 TF 跳一下，Nav2 当场按新位置重算。
3. **时钟**：这台狗的传感器时间戳比 Orin 的系统钟慢约 230 天。
   - Nav2 按系统钟查 TF、判点云新不新的话，全会被当成过期。
   - 所以 Nav2 一律 `use_sim_time: true`，转接节点按收到的最新 `/tf` 时间戳发 `/clock`。
   - 今天抄回来的厂家参数（3aj.1）先看它的 `use_sim_time` 是怎么配的，对照一下。
4. **转速死区、起步切步态**：
   - 代理按真机死区整形（低于一半当 0，另一半抬到死区）；不用 Nav2 的速度平滑器（见「速度归哪个目标」）。
   - 加速度上限按真机量的来，先用厂家参数。
5. **机身**：
   - 轮廓按矩形 0.93 × 0.48 m，加 5 cm 余量，规划和控制都按矩形算，不再按外接圆。
   - 规划用 Smac（State Lattice 或 Hybrid-A*），会转的地方才要外接圆那么大的空。
6. **横移**：
   - MPPI 用 Omni 模型，横移上限先给前进的一半。
   - HAL 报 `lateral` 能力才开；不报就用 DiffDrive 模型。
7. **脱困**：Nav2 行为树。顺序是：清掉局部代价地图里的旧障碍 → 原地等 → 后退 → 原地转 → 重规划；都不行就失败，报原因。
   - 现在的「挪 1.3 m」「先往后退」「转不动提速」都不进 Nav2 那条路。
8. **区域**：
   - 禁行区（含虚拟墙、硬禁区）烧进发给 Nav2 的地图，同时代理每拍的闸照旧，两道防线。
   - 限速区走 speed filter 的掩膜，代理再按限速截一刀。

## 七、风险

- **真机运动接口**：转速死区大、一条 `Move` 自带 1 s 保持、起步切步态。MPPI 默认按「发什么就走什么」算，真机上可能抖、可能到不了点，要调；W08 当时不选 Nav2 主要就因为这个。厂家用的就是 Nav2，说明调得通。
- **时钟**：靠 `/clock` 走传感器钟；狗上 chrony 一旦把 Orin 钟拨动，不影响，因为全用传感器钟。传感器钟要是跳了，Nav2 会出怪事，得在真机上观察。
- **算力**：Nav2 是 C++，比我们的纯 Python A* 快；MPPI 吃 CPU，3588 上采样数要调低。厂家的 Nav2 在 Orin 上约占 44%。
- **两侧盲区**：Nav2 代价地图里从没看过的格是「未知」，按什么代价算要调。太松会擦到侧面，太严就是 10-28 那种起不了步。

### 跑的时候发现的

1. **MPPI 要求控制周期不大于它的模型步长**，不然 controller_server 起不来：控制频率 20 Hz。
2. **参数文件不能有 YAML 别名**（ROS 不认）：生成时关掉，测试里查。
3. **Nav2 的动作服务在，不等于已经激活**：早发的目标会被拒。转接节点改成问生命周期管理器。
4. **Nav2 起步、收尾会发很小的速度**，运控有死区（低于它的前进速度 HAL 直接拒）：代理发之前整形（低于一半当 0，另一半抬到死区）。真狗同样需要。
5. **旁路的第二道净空许可按最高速算**：前方空出约 0.8 m 才放行，不管当时多慢。所以贴墙的点（工单 20）换哪个导航都到不了。
   - 改法：许可按「允许的最高速度」分档，离得近只许慢慢挪。
   - 要改旁路程序（C++）、上狗重编，另开一单。
   - 真狗上这道许可现在还没开（W11 真机验收之前不开），眼下不影响。

### 速度归哪个目标（外审 R7 到复查第三轮，转接协议 3）

Nav2 出的速度不带目标号。换目标时，上一个目标的控制器、平滑器、脱困还可能在出速度，代理不能拿它驱动新目标。现在这样保证：

- **自己起 Nav2 的节点**（`deploy/nav2/d1max_nav2.launch.py`，不再套 nav2_bringup 的 `navigation_launch.py`）：控制器 → `/cmd_vel_nav`，脱困动作（BackUp、Wait）→ `/cmd_vel_behavior`，**不起速度平滑器**（它会把旧目标的速度慢慢衰减着往外发；加减速由代理和机器人管）。转接节点两路都订，`cmd` 标上 `src`（`ctl` / `beh`）。
- **目标串行，看生产端自己停没停**（复查第四轮）：Nav2 取消下层动作只等 20 ms，等不到也照样报导航结束，所以「导航结束」不等于控制器、脱困、规划停了。转接节点订各动作自己的状态话题（`navigate_to_pose`、`navigate_through_poses`、`follow_path`、`compute_path_to_pose`、`compute_path_through_poses`、`backup`、`wait`、`spin`、`drive_on_heading`）。普通情况下，这些状态要等执行循环退出、最后一条输出发完才变终态；Nav2 停用超时时会提前置终态，那条路由下面「这个目标自己的生产端开跑了」的门槛挡住。它们**全都没有在跑的目标**，才把下一个目标发给 Nav2。
  - 新目标一律先排着，只排最新一个，被顶掉的回拒；只在事件循环一个地方派，不会越过排着的那个。
  - 5 秒还没停，回拒。
  - 代理断线时取消手里的目标，不清账。结果查询出错的也由动作状态兜着。
- **路线、速度都要「这个目标自己的生产端开跑了」**（复查第四、五轮）：派出新目标时记下各动作状态列表里已有的目标号；之后出现**新的目标号**，才算这个目标的那一类开跑了。
  - 规划出现新号：才认之后来的路线（时间戳不是代次：Smac 拿到锁才填）。
  - 控制器（`follow_path`）出现新号：才转控制器的速度。
  - 脱困动作出现新号：才转脱困的速度。
  - 看目标号不看「在跑」，因为状态话题只留最新一条，快的话「在跑」会被「完成」盖掉。
  - 脱困不要求「此刻还在跑」：状态和速度两路在两个线程里处理，「结束」常比最后几条后退速度先处理完，要求了就丢合法的后退（navbench 终点贴墙 4/5 → 0/3）。
  - 终点离目标超过 0.4 m 的路线也不算。
- **新目标号还要是派出以后收下的**（复查第六轮）：状态里每个目标带着 Nav2 收下它的时刻（Nav2 的钟就是我们发的 `/clock`）。收下时刻早于这次派出（留 200 ms 余量）的号，就算第一次见到也不开门。转接节点起来前就在跑的老目标，状态晚到也冒充不了。
- **连上代理先全取消**：转接节点每次跟代理连上，把 Nav2 里的导航目标全部取消（上一次留下的它不认识），取消要等它们真停了才派新目标。
- **起来先同步**：转接节点起来 2 秒内不派目标、不报就绪，让 Nav2 补发的动作状态先处理完；过了 2 秒，每秒的那一拍会自己派排着的目标。
- **服务没了、换了实例就清旧状态**：每秒查一次各动作状态话题的发布者身份，没了或者换了，旧实例记着的「在跑」清掉（Nav2 重启后新的空闲服务不发状态，旧标记会一直挡着）。
- `assisted_teleop` 也算会出速度的动作。
- **已知残留（用户 2026-10-30 认可记录）**：Nav2 的速度不带目标号，状态话题和速度话题是两条话题，DDS 不保证它们之间的先后。理论上上一个目标的生产端最后一条输出，可能晚于它的终态和新目标的开跑才到。真遇到时，代理最多按它走 0.4 秒（`CMD_FRESH_S`），期间禁行区检查、障碍守卫、限速、旁路许可照常。要彻底去掉，得让速度本身带上代次（Nav2 Humble 的控制器只发不带时间戳的 Twist，做不到）。
- **代理这头**：转接服务端给收到的报文按到达顺序编号，记下每个目标第一条路线是第几条到的。控制器的速度要对上目标号、这个目标的路线已经来了、而且**比路线晚到**才用。路线来之前缓存的一律作废。脱困的速度只要对上目标号（它常在规划不出来时做，那时没有路线）。
- 新目标收下后 0.2 秒内的速度不发（队里排着的旧速度）。

### 第二道许可按速度分档（2026-10-29 晚，旁路协议 10）

原来的许可只有「放 / 不放」：感知节点按 0.6 m/s 算前面够不够空，够就放，不够前进一点都不许。离墙、离东西不到约 1.1 m 就只能原地转，终点贴墙的场景 0/5。另一个问题是旁路把前进比例卡死在 0.5（真机约 0.5 m/s），仿真里的 1.0 m/s、90 秒到位在真狗上跑不出来。

- **许可带速度**：`clear` 多一个 `vmax`（m/s）。感知节点按「有效期里走的 + 帧龄里走的 + 刹停 + 0.3 m」反解出空这么多最多能跑多快（`permit_vmax`，最高 1.0）。旁路按 `--permit-mps-per-unit`（比例 1.0 最多多少 m/s，宁大勿小；低速档缺省 1.1，C40221 实测斜率 1.09）换成比例上限，夹前进分量。
- **最新的许可说了算**：障碍近了，许可的速度当拍就降；上限没升时有效期只往后延（老规矩，晚到的同档许可不截短）。
- **许可按连接认**（#208 首审 G1、复查 H1）：旁路给每条连上来的连接一个递增号，只认最新那条发过许可的连接。旧连接的报文永远不认，过期了也不认，不靠钟；同一条连接里帧序号要往上走。感知重启会是一条新连接，发许可就接管，旁路把旧连接关掉，它缓冲里没读完的旧许可一起作废。接管是**整条连接**退役（两头共用一个持有连接，复查第三轮 H1）：新连接只在一头发了许可，旧连接在另一头在途的报文也不认；判断和接管在同一把锁里。
- **超过 0.5 要有第二层**：旁路新参数 `--max-fraction`（0.5–1.0，缺省 0.5 = 老行为）。超过 0.5 的前进只在开了 `--require-clearance` 时放行；后退、横移、转向一直不过 0.5。握手报 `max_fraction`，代理（HAL、连接层）按它和自己的 `--max-fraction` 取小。
- **老的不乱**：9 号及更老的旁路会把任何许可当「0.5 随便走」，感知节点对它们照旧只在够 0.6 m/s 刹停时发、不带 `vmax`。代理认 3–10；老代理不认 10 号旁路（照惯例，重编旁路时代理一起升）。
- 仿真（Nav2，1.0 m/s，每个 5 次）：终点贴墙 0/5 → **4/5**；56 m 路线 5/5 在 90 秒内（中位 78 s）；C1 方块平均停车 2 → 0；6 个场景 29/30、0 撞。
- **真机要先量刹车距离**：感知节点算许可用的减速度（0.5 m/s²）、链路延迟（0.2 s）都是占位值。先 `--require-clearance` + 缺省 0.5 跑（3aj.9），量完改 `Config.decel`，再放到 1.0（3aj.10）。
