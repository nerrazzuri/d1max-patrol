# 真机现场执行单

## 0. 这份文档是干什么的

`docs/真机待验证清单.md`（下称"清单"）按"什么时候想到的"顺序累积记录，回答的是
"这条是哪来的、为什么要验"——**不要改它，继续留着当历史记录**。

这份文档回答的是另一个问题："现场到了，现在该做哪一步"。它把清单里跨第 1～6 卷、
约五十多条待验项，按**物理依赖**重排成一条能一次走完的执行序列：出发前先备齐东西，
上电先确认安全，网络通了才碰得到 Orin，部署稳了才谈 SDK，控制权拿到了才能动腿，
定位准了才谈导航，导航通了才谈巡检作业，最后统一做备份盘和断电这类"弄脏手"的收尾。
**目的是不让狗为了同一件事反复重启**——现场时间比什么都贵，来回折腾一次就是半天。

**怎么用**：带着这份现场打勾，`- [ ]` 一条条打。每条给了动作、判据、记录栏（要现场
量数值的）、失败怎么办（跳过继续 or 停）。真正现场发生的细节、报错原文、和清单不一致
的地方，回去继续写回清单——**新发现永远写进清单，不写进这份执行单**。

**每卷收尾要往这里追加的规矩**：清单每次新增一节（例如某一卷终审带出的真机待验证项），
如果那批条目对应的是一次**尚未做过**的现场访问，就把它们按本文件的十一段骨架拆开插进
对应阶段；如果是**已有阶段的补充细化**，直接在那个阶段追加条目并顺延编号。**不要**
在这份文档里保留"已经确认/已经结案"的条目——那些留在清单里当历史，这里只留还要
现场动手的。

**详细操作步骤这份文档不重复抄**：能引用 `docs/真机联调手册.md`（笔记本环境准备、
接线细节、SDK 会话操作、M12 航插线序表）、`docs/装机清单.md`（装机全流程）、
`docs/鉴权与控制权.md`（控制权模型）的地方，一律写"见 `docs/xxx.md` 第 N 节"，
不抄厂商协议报文样例、不抄 JSON 采样、不抄 SDK 内部实现细节。

**动作前的标签**：每条动作前标了执行工具——**【笔记本】**要 SSH／看日志才行，
**【手机】**是产品真正的现场使用形态、必须在手机上验一遍，**【两者】**两边都要各测一次，
**【Orin 本地】**要 SSH 上 Orin 直接跑。现场没有笔记本才是最终交付形态，但**真机验证
阶段允许带笔记本**——所以"手机上到底行不行"本身就是要验的东西，标出来才不会漏测。

## 1. 已知的现场事实（先背熟，别再去猜）

- **狗的 AP 热点**：SSID `XG2WIFI_C40221`，密码 `12345678`。连上后浏览器开
  `http://192.168.168.100:10010` 是厂商导航页面。
- **网段**：`192.168.168.0/24`。
- **SSH**：Orin NX `robot@192.168.168.100` 密码 `1`；RK3588 走 WiFi
  `robot@192.168.234.1` 密码 `bot`，走有线 `robot@192.168.168.168` 密码 `bot`。
- **导航 WebSocket**：两个地址都通，现场实际用 `ws://192.168.168.100:10010`
  （清单 #25，已实测确认）。
- **SDK 控制口**：`8082/UDP`，不是 8081（清单 #34）；**SDK 版本用 `0.1.1`**，
  0.2.0 遥测断裂，已停用（清单 #35/#39/#45，厂商口径已结案）。
- **控制权规则**：厂商侧没有正规的交接机制，控制权一旦被上装（机载上层系统）拿走
  就要不回来，只能在开机瞬间抢窗口（清单 #46/#47，厂商口径已结案）。`field-agent.sh`
  / `motion/patrol_agent` 就是干这个的，**抢到就不能松手**，`quit`/`shutdown` 不可逆。
- **走 WiFi 时必须加路由**：`sudo ip route add 192.168.168.0/24 via 192.168.234.1`，
  否则 Orin NX 够不着。**这条路由不持久**——机器每次重启、WiFi 每次重连都要重加
  （清单 #66）。
- **受限 shell 下后台起 python 会秒退**：看板类程序必须前台起（清单 #67）。
- **前雷达疑似装反**：建出的图内部朝向差 180°，机头朝向是反的（清单 #64）。
  **这条排在阶段六最前面**，见下文，不过则整段定位/导航结果都不作数。

## 阶段二 · 上电与自检

- [ ] **2.1 开机，记录初始状态。**【手机或笔记本均可，先看灯】
  动作：给机器上电，观察机身指示灯颜色。
  判据：白灯为正常；转黄灯 = 低电量告警（清单 #43 已确认，厂商文档未写此条）。
  记录栏：`开机灯色：______；能读到电量时记：______%`。
  失败怎么办：黄灯说明电量偏低，先充电；不阻断后续，但要留意可能影响阶段六的建图

- [ ] **2.2 硬急停位置确认，软急停连通性验证。**【笔记本，SDK 会话】

  `estop`（软急停 ON）再发 `clear`（OFF）（见 `docs/真机联调手册.md` S2，命令实体
  参照该节，不在此复述）。
  判据：`estop` 发出后机器停止响应移动指令；`clear` 后恢复响应。
  记录栏：无。
  失败怎么办：**停**——这是后续一切运动测试的安全垫，没确认之前不进入阶段五及以后
  任何运动相关条目。（本条实际执行时机在阶段五抢到会话之后，但纪律写在这里提前立好。）

- [ ] **2.3 电量监控贯穿全程。**【笔记本，SDK 会话】

  失败怎么办：N/A，纯记录；电量过低时优先保证阶段五～九跑完，阶段十一收尾可以放到

## 阶段四 · 部署（装机脚本、服务、双槽/回滚）

> 本阶段是本次现场唯一集中安排"多次重启/断电"的地方之一（另一处是阶段十一收尾）。
> **做完本阶段建议做一次干净重启**，从那次开机窗口开始进入阶段五抢控制权，
> 后续阶段（五～九）尽量不再主动重启狗。

- [ ] **4.0 若是首次装机或要升级：完整走一遍装机清单。**【笔记本 + Orin 本地】
  动作：见 `docs/装机清单.md` 二～四节（装机七步、验收五条、回滚演练四步）。
  判据：见该文档自身给出的判据。
  记录栏：见该文档自身的记录要求，此处不重复。
  失败怎么办：见该文档"五、出错时的三条退路"。
  （若这次现场机器已装过、不涉及升级，跳过本条，直接做下面几条真机独有假设的复核。）

- [ ] **4.1 `ExecStartPre=-` 守卫真的挡在每次 restart 前面。**【Orin 本地】
  （来源：清单"装机、升级、回滚"第 1 条）
  动作 a：连续 `systemctl restart d1max-patrol.service` 若干次，`journalctl -u
  d1max-patrol` 里应能看到守卫每次都跑过一遍。
  动作 b：把 `/opt/d1max/bin/python` 临时改名，`systemctl restart`，验证服务
  照常起得来（`-` 前缀语义）。
  动作 c：`systemctl list-unit-files | grep d1max` 只剩一个单元
  （老机器上的 `d1max-bootguard.service` 应已被 `install.sh` 摘掉）。
  判据：三条都如上所述。
  记录栏：`journalctl 里守卫出现次数：____；改名测试结果：______；
  list-unit-files 结果：______`。
  失败怎么办：就地跳过继续，**标红**——守卫失效是要立刻上报的缺陷，但不阻断
  后面继续验证别的项。

- [ ] **4.2 拔电重启，`boot_guard` 真的能数到第二次并回滚。**【Orin 本地，涉及断电】
  （来源：清单"装机、升级、回滚"第 3 条；连带验证第 2 条 `os.replace` 的原子性）
  动作：参照 `docs/装机清单.md`"四、演练一次自动回滚"故意做一个坏包升级，
  在自检判断出结果之前**真的拔电两次**，让 Orin 冷启动两次。
  判据：机器最终自动回退到上一版本；`release list` 里能看到回滚记录。
  记录栏：`拔电次数：2；最终版本：______；release list 的 rollbacks 记录：______`。
  失败怎么办：**停，找人**——自动回滚是装机可信的底线；不阻断继续测试其它不依赖
  回滚机制的项，但要重点上报。

- [ ] **4.3 整机重启后，有上装的机器谁先抢到 SDK 控制权。**【Orin 本地 + 现场观察】
  （来源：清单"装机、升级、回滚"第 4 条）
  动作：触发一次整机重启（`restart_plan(has_payload=True)` 路径），重启后观察是
  `field-agent.sh` 先抢到 8082 还是上装先占住。
  判据：现场直接观察结果即可，无预设对错——这是信息收集项（厂商侧已结案：
  没有正规交接机制，见清单 #46/#47）。
  记录栏：`重启后谁先抢到：______`。
  失败怎么办：记录即可，不阻断。

- [ ] **4.4 `systemctl restart` 之后 SDK 会话能不能抢回来（无上装机器）。**【Orin 本地】
  （来源：清单"装机、升级、回滚"第 5 条）
  动作：`systemctl restart d1max-patrol.service` 后，看 `patrol_agent` 能否重新
  抢到会话。
  判据：能重连。
  记录栏：`能否重连：______`。
  失败怎么办：记录，不阻断。

- [ ] **4.5 `User=robot` 能不能 `systemctl restart` / `reboot`。**【Orin 本地】
  （来源：清单"装机、升级、回滚"第 6 条——"危险在于失败是静默的"）
  动作：`sudo -u robot systemctl restart d1max-patrol.service` 手工跑一次，
  用 `systemctl status` 核对是不是真的重启了（不能只看命令没报错——
  `_spawn_restart` 只 `Popen` 不看返回码）。
  判据：服务真的重启了。
  记录栏：`结果：______`。
  失败怎么办：拒了的话记录现象，**不阻断**，回去配 polkit 规则或 sudoers 白名单，
  并把 `_spawn_restart` 改成看返回码。

- [ ] **4.6 `pip install <本地目录>` 会不会往源目录里写构建产物。**【Orin 本地】
  （来源：清单"装机、升级、回滚"第 7 条）
  动作：装完后 `ls <包目录>`，看有没有 `*.egg-info/`、`build/`、`__pycache__/`。
  判据：有污染说明 `install.sh` 那两次 `mktemp -d` + `cp -a` 是必须的前提；
