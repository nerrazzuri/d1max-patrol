## R1：在生效的那一份存下来

**改了什么**
- `nav_zones` 新列 `effective_body`（库结构 59 → **60**）：狗上**在生效的**那一份。升上来的老库这一列是空的，空就按原来的算法（当前草稿 + 确认过的那一份里没被盖住的），下一次改动起存下来。
- **改草稿**（`put`）：取上一份在生效的 `prev`。
  - 有确认过的底、而且新草稿跟 **`prev`** 比只收紧（原来是跟「最后确认的」比）→ 当场算确认，在生效的 = 新草稿。`prev` 本身不比最后确认的松（`covered` 可传递），所以这条比原来更严，仍满足决策 66。
  - 否则在生效的 = 新草稿 + `prev` 里没被新草稿盖住的（同 id 换名字）；装不下（> 200 个）整份守 `prev`。
- **确认**：在生效的 = 确认的那一份；跟原来在生效的不一样时修订号 +1（原有）。
- **到期**（`expire`）：草稿、确认过的、在生效的三份里到期的一起删，有一份变了就出新修订。
- 下发、补发、派单闸、运行配置摘要、遥控提醒、拦截点可达照旧都读 `effective()`，现在读的是存下来的那份。

**行为变化（请判断）**：**从没确认过的版本**，删掉区域现在也要确认才生效（原来从没确认过的版本「在生效的 = 草稿」，删了当场没）。这是按外审「放宽只能明确确认后生效」做的；新画的图在第一次确认前删错了区域，狗上照守到确认为止。

## R1-续1：无关临时区到期，不再顺带批准等确认的放宽（2026-10-27）

> 对应复查报告 `../reviews/2026-10-15-PR170-971da1e-8acf197-recheck.md`（FIX-THEN-APPROVE，剩 1 项 Important）。R2、R3、M1 复查已通过，这次没动。

**原因**：`expire()` 判「删完到期的还能不能带上确认」时，跟**最后确认的那一份**比。当前草稿里还有别的放宽在等确认（比如删一个后来加、已经在守的永久硬禁区）时，最后确认的那一份里根本没有它，比下来照样「只收紧」——于是一个不相干的临时区到期，就把那项放宽一起批了：在生效的换成草稿，硬禁区保护被撤，还标成「已确认」（`how = expiry`），派单照常。

**改了什么**（`nav_zones.py` 一行）：改成跟**原来在生效的那一份**比（`tightens(eff, new, now_ms=now)`，到期的不用再盖）。这样只解除到期的那一项；还有别的放宽，就照旧不确认，在生效的 = 新草稿 + 原来在生效、没被盖住的（原有的 else 分支）。在生效的那一份本身不比最后确认的松，所以条件只比原来严。仍然要有确认过的底（从没确认过的版本，到期也不算确认）。

**测试**（`test_site_zones_effective.py` 新 7 条，**4 条在旧代码上失败**）：
- 外审给的场景：确认「泳池 + 施工区」→ 改成「台阶 + 施工区」→ 再改回「泳池 + 施工区」（删台阶，等确认）→ 施工区到期：台阶照旧守、没确认、确认记录还是第 1 版人工确认。
- 放大的台阶等缩回、调低的限速等调回：到期后大台阶、0.1 m/s 照旧，没确认。
- 站点重启之后才到期：结果一样。
- 同名守着的（泳池去掉硬标记、换名字守着）再删台阶：到期后泳池按硬的守、台阶也守。（旧代码上本来就过，补着防回退。）
- 正向两条：等确认的那项放宽**只是提前删施工区**，到期后自动算确认（`how = expiry`）；全都确认过、只有到期，照旧自动确认。

外审复现 `test_repro_expiry_of_unrelated_zone_approves_pending_removal` 在修复后失败（= 缺陷不在了）；同文件另外 3 条照过。
