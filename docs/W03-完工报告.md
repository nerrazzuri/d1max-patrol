### 二之二、外部审核阻断项修复（`ceaba14`）

审核复现：删除计划是一次性快照，`plan_sweep` 之后、`apply_sweep` 之前 pump 仍可重开条目，`apply_sweep` 只查路径不查队列 → 有未传完条目的趟被 `rmtree`。另一个更宽的窗：判读/复核改写文件到 pump 下一拍 scan 之间（最长 15 s），队列全 done、`.uploaded` 还在，清盘照删。修法三条：

| 改动 | 位置 |
|---|---|
| `_why_not_uploaded(run, run_rel, queue)`：「可删」不再信盘上标记，对着**活队列和盘上文件**重算——目录在、标记在、settled、队列里该趟无未 done、**盘上每个白名单文件都在队列里、已 done、且 size/mtime_ns 与盘一致**（老条目 mtime 0 也不算，等下一拍补上）。`_mask_uploaded_by_queue` 改用它 | `app/server.py` |
| `UploadPump.coord_lock`（RLock）：`scan()`、`on_scan`、`on_done` 各在锁内；清盘路由从拿方案到重验到 `rmtree` 全程握锁；判读/复核/报告再生成的改写也在锁内。`run_once` 的网络等待不在锁内（它只把条目推向 done，不制造 pending） | `app/upload_pump.py`、`app/server.py` |
| 真删前对方案里凭 `uploaded` 进来的每一趟再调一次 `_why_not_uploaded`，不过的跳过并写进响应 `skipped: [{path, reason}]` | `app/server.py` 清盘路由 |
| `_stale_reports`（判读/复核后）与报告再生成路径**同步** `unmark_uploaded`，不等 pump | `app/server.py` |

## 四、已知边界

- 「可删」判据现在要求盘上每个白名单文件与队列记录 size/mtime 一致。升级到 W02/W03 后第一拍 scan 之前，老条目 mtime 为 0 → 该趟暂不可删，最长 15 s 后 scan 补上 mtime 即恢复；这是有意的保守方向。
- 协调锁只覆盖 pump 的 scan/回调与服务内的改写路径；**服务外**直接改归档目录（人手 scp、别的进程）不在锁内——盘 vs 队列的 size/mtime 核对仍能在下一次清盘时拦住它，但不能拦「改写与 rmtree 同一毫秒」。

- **内部评审复现的一条竞态，已修（`3174ef6`）**：清盘路由从 HTTP 线程读 `queue.all()`，而 pump 线程的 `_remember` 原来是"先进 `_order` 再进 `_items`"，两步之间被切走一次，`all()` 就会撞 `KeyError`（评审用 `sys.setswitchinterval(1e-6)` 5 秒内必现；正常调度下概率极低且只炸一次 HTTP 请求）。改为先进 `_items` 再进 `_order`，`all()` 先拍 `_order` 快照；加了一条逼切换的回归测试。`UploadQueue` 仍不是线程安全的——这只是堵住这条路由会踩到的那个洞。
- 优先级：`findings.json`/`review.json` 是二级，照片是三级，所以结论可能先于它引用的照片到达服务器；一趟的照片传完即自愈。这是有意的（结论先到比压在照片后面好），与 manifest/events 同级的理由一致。

- 遮罩只在**清盘路由**生效；`/api/storage` 的盘况/预告显示的 `uploaded` 仍读盘上标记，撤标那一拍之前可能短暂显示"已传"。只影响显示，不影响删除。
- `unmark` 与 `mark` 由同一条回调路径写，无并发写者；`_补打可删` 与 sweep 之间的互斥仍靠 sweep 自己的 `_sync_lock`，本单未改。
- 单机档（无服务器）下 `uploaded` 永远不会被打上，本单对它无影响；`exported` 路径未动。

## 四之二、内部评审（第三轮，针对 `ceaba14`）

结论 **APPROVE**，无阻断项。核过的点：`run_once` 在锁外只会把条目推向 done（`advance/defer/finish` 不碰 `done`，`rewind` 只作用于本就未 done 的条目），制造 pending 的只有锁内的 `scan()`；锁序单一（`coord_lock` → `_sync_lock`），备份同步那几处持 `_sync_lock` 时不碰 `coord_lock`，无环；清盘长时间 `rmtree` 期间 pump 的 `run_once` 与心跳照常，只推迟一次 15 s 重扫；key 形状与 `Uploader.scan()` 一致，`classify` 对 `.uploaded`/`state.json` 回 None；三条新测试各自钉住修复的一半（去掉重验、去掉盘检查、去掉同步撤标各红一条）；单机档行为不变。唯一非阻断备注：size+mtime 判据在粗粒度文件系统（FAT/部分网络盘）上有同秒碰撞的理论风险，与 W02 同源，ext4 上可忽略。
