# 装机清单

给现场的人用的单子，逐条能打勾。装机是一次性的、要能重复、要留痕——所以这份清单跟
`deploy/install.sh` 一一对应，脚本能重跑，这份单子也能重填。出问题按「五、出错时的三条退路」
走，不要凭记忆猜。

> **狗上只有一个服务：`d1max-agent`（机器人代理）。** 它往外连站点（庄园现场的服务器），
> 不开任何给手机连的端口；手机只连站点。以前狗上那个网页服务、设备 PIN、手机直连狗的模式
> 都已经退役，这份清单里不再有它们。**站点要先装好**（站点那一份装机说明在 `deploy/site/`），
> 这只狗要先在站点上登记过（见「一」最后一条）。

---

## 零、先在笔记本上把包造出来

**这一节在笔记本（开发机）上做，不在狗上做。** 狗上没有这个仓库，也跑不了下面这条命令——
狗上能跑的只有 `release install / activate / rollback / boot-guard`。

```sh
python -m d1max_patrol.cli release pack <源码树> <放包的父目录> --wheels dist/wheels-aarch64-py310
```

- **第二个参数是「父目录」**，包建在它底下，不是它本身。例如
  `python -m d1max_patrol.cli release pack . /tmp/out --wheels dist/wheels-aarch64-py310`，
  包出现在 `/tmp/out/<包名>/`。
- **`--wheels` 要带。** 现场的狗多半上不了外网；带上它，离线轮子就跟着包走（算进包的指纹），
  以后站点给这只狗下发新版本时，狗在自己身上建这一版的依赖只从包里的轮子装。
- **包目录名默认就是对的**：`<今天>-<git 短哈希 8 位>`，正好是 `install.sh` 和 `release.json`
  都要求的 `<日期>-<6 到 12 位十六进制>`。**不要自己起名**；真要起名（`--name`）也必须是这个
  格式，而且要跟包里 `release.json` 的 `name` 一字不差。
- 输出目录已经存在且非空时命令会拒绝；确认要覆盖就加 `--force`。

- [ ] **抄下屏幕上打出来的两行。** 打完包屏幕上会有：

      ```
      包目录         : /tmp/out/2026-09-20-77b2de
      content_sha256 : <64 位十六进制>
      ```

      这两个值**抄进现场记录栏**。包要经过 U 盘从笔记本走到狗上，中间任何一次拷贝掉了字节，
      能对得上账的就只有这个指纹——而对账的前提是打包那一刻有人把它抄下来了。事后补不出来。

- [ ] **确认包里只有该有的东西。** 包是一份**白名单**：`pyproject.toml`、`src/`、`config/`、
      `deploy/`、`packages/`、`wheels/`（带了 `--wheels` 才有）和 `release.json`。
      **`refs/`、`dist/`、`tests/` 不进包**：`refs/` 是厂商的私有协议文档，`dist/` 里还有手机的
      安装包。看一眼确认：

      ```sh
      ls <包目录>
      du -sh <包目录>
      ```

      看到 `refs` 或 `dist`，或者体积大到几十 M 以上，**停下来**，别往狗上拷。

- [ ] **出不了外网的站点：离线轮子也要一并拷进 U 盘。** 装机脚本自己（下面二、的 2/7、4/7）
      也要装依赖，它不看包里的 `wheels/`，要单独给一份。把仓库里的 `dist/wheels-aarch64-py310/`
      整个目录拷到 U 盘上（跟包目录并排放），到了狗上先校验一遍再用：

      ```sh
      cd /media/<U盘>/wheels-aarch64-py310
      sha256sum -c SHA256SUMS.txt
      ```

      每一行都要是 `OK`。有一行是 `FAILED` 就重拷一遍。

## 一、装机前要准备什么

- [ ] Orin NX 能上网（`curl -sS -m 8 https://pypi.org/simple/` 有响应），**或者**：
- [ ] **出不了外网的站点**：离线轮子在 U 盘的一个目录里，装机时这样跑：

      ```sh
      sudo D1MAX_PIP_ARGS='--no-index --find-links=/media/<U盘>/wheels-aarch64-py310' \
        bash deploy/install.sh <包目录>
      ```

      `D1MAX_PIP_ARGS` 会被原样传给脚本里**每一处** `pip install`。
      **那个目录里要带上 `pip`、`setuptools`、`wheel` 三个轮子**——脚本要在离线的 venv 里就地
      构建我们这个包，少了它们构建起不来。
- [ ] 装机用的包已经在这台机器上，而且是一个**目录**：`/home/robot/2026-09-20-77b2de` 这样的。
      **目录名不许带 `d1max-` 之类的前缀**，必须长成 `<日期>-<6 到 12 位十六进制>`，而且要跟包里
      `release.json` 的 `name` 一字不差——那是包校验的第二关（第一关是整棵树的哈希）。不对的话
      `install.sh` 在前置检查那一步就拒收（退出码 2，盘上一个字节都没动）。
      **`.tar.gz` 之类的归档 `install.sh` 不认**——拿到的是归档就**先在这台机器上解开**，再把解出来
      的那个目录当参数给它，并且**解出来的目录名要保持原样**。
- [ ] 知道这台机器的**机身序列号（SN）**——现场贴在机身上的标签。厂商 SDK 和导航接口都不报它。
- [ ] **站点上已经登记过这只狗。** 站点主机上：

      ```sh
      d1max-site enroll <这只狗的编号>
      ```

      它打出一个目录，里面是这只狗的证书包（`ca.crt`、`robot.crt`、`robot.key`）和注册文件
      `registration.json`。**把这四个文件拷进 U 盘带到狗上**，二、里要用；再记下站点主机的地址。证书包就是这只狗的身份，**别放进工单、截图
      或者聊天记录**。

## 二、装机（跑一趟 `install.sh`，再填现场值、放证书包）

> **动手装之前，先去把「七、卸载（撤场）」的第一节做掉。**
> `deploy/footprint.sh snapshot` 必须在 `install.sh` 跑**之前**跑掉——跑晚了那张快照就作废，
> 而且事后补不出来，「我们没覆盖上装的文件」这句话在这台机器上就永远证不出来了。

```
sudo bash deploy/install.sh <包目录>
```

- [ ] **1/7 建目录。** 屏幕上看到 `建目录 /opt/d1max`，`/opt/d1max/releases` 和 `/opt/d1max/bin`
      建出来了，属主是 `robot`。
- [ ] **2/7 装版本无关的解释器。** 第一次装机会新建一个 venv，重跑不会重建（幂等）。
- [ ] **3/7 把包落进槽里。** 屏幕上看到 `落槽了: <名字> (版本 ...)`。只落槽，不切换。
- [ ] **4/7 给这一版建自己的 venv。** 屏幕上没有报错。**这是每版一个的 venv**——退回上一版要把
      依赖也一并退回去。依赖装齐之后脚本会在 `<槽>/venv/.deps-ok` 落一个哨兵文件，重跑看见它就
      整段跳过。**这一步中途断了（网断、盘满、Ctrl+C）哨兵不会落**，重跑会把半成品推倒重装——
      断了就直接再跑一遍，不用手工清理。
- [ ] **5/7 装代理单元与环境文件；清掉老服务。** 屏幕上看到 `装代理单元与环境文件;清掉老服务`。
      - **单元只有一个**：`d1max-agent.service`，装上并设成开机自启。它的启动参数不在单元里，在
        每一版自带的启动脚本里（站点以后给这只狗换版本时，参数跟着版本走）。
      - **老机器上以前装过的东西会被这一步停掉删掉**：老服务 `d1max-patrol.service`、老的守卫
        单元、老的特权助手和它那条 sudo 白名单、老的任务包目录 `/opt/d1max/bundles`。新机器上
        本来就没有，这一步什么也不做。两种都正常。
      - 顺带在 `/etc/d1max/env` 写一份模板——**只在这个文件不存在时写**，已经填过的机器重跑
        `install.sh` 不会被抹掉。老机器的 `env` 里要是还有老服务用的几行（设备 PIN、回传地址），
        屏幕上会提示一句「已经没人读了，可以删」，脚本自己不动它们。
- [ ] **6/7 看一眼站点签发的证书包与注册文件。** 第一次装机这里会说「还没有」，并打出下一步怎么
      做——**这是预期的**。没有注册文件代理就不起，不会刷日志。
- [ ] **7/7 切到刚装的这一版并起代理。** 这一步跑的是 `release activate`。屏幕上看到
      `切到 <名字>,上一版 无。重启代理(systemctl restart d1max-agent)之后连上站点才算成;…`，
      随后 `systemctl stop`（第一次装机报错被吞掉是对的）、`数据根   : /var/lib/d1max` /
      `搬过的槽 : (没有要搬的)`、`systemctl start d1max-agent.service` 没有报错。
      `/etc/d1max/env` 里 `D1MAX_SN` 还空着的话，这里会有一行 `警告: … D1MAX_SN 还没填`——
      下一步填上即可。
      **升级老机器时**这里会看到 `搬过的槽 : <老版本名>`——那是把老版本槽里的数据搬到
      `/var/lib/d1max`，只搬一次，重跑什么都不做。
      **老服务那一代留在 `/var/lib/d1max` 里的东西（`runs/`、`queue.jsonl`、`baselines/`、`exports/`、
      `slam/`、`bags/`）以后没人传、也没人清**：代理的发件箱在 `/var/lib/d1max/outbox`，只管它自己
      写的。要留就拷走（照片、报告），拷完手工删掉这几样。

### 装完之后：放证书包、填现场值、起代理

- [ ] **放证书包**（「一」最后一条从站点带来的）：

      ```sh
      sudo mkdir -p /etc/d1max/tls
      sudo cp <U盘>/ca.crt <U盘>/robot.crt <U盘>/robot.key /etc/d1max/tls/
      sudo cp <U盘>/registration.json /etc/d1max/registration.json
      sudo chown -R robot:robot /etc/d1max/tls /etc/d1max/registration.json
      sudo chmod 0600 /etc/d1max/tls/robot.key
      ```

- [ ] **填现场值**：

      ```sh
      sudo nano /etc/d1max/env
      ```

      - `D1MAX_SN=`：机身标签上的编号（只收字母、数字、点、下划线、减号）。
      - `D1MAX_SITE_MQTT=`：站点 broker 的地址，`mqtts://<站点主机>:8883`。
      - `D1MAX_MAP=`：狗上现在载着的地图 `<地图号>:<版本>`；`D1MAX_HOME=`：这张图上的原点
        `x,y,yaw`。站点以后下发过地图，就以站点下发的那张为准。
      - `D1MAX_HAL=`：**先留着 `sim`**。`sim` 是仿真，动不了真狗。
        **真机验收（`docs/庄园场景待真机测试.md` §3b）过了，才改成 `d1max`**，同时在
        `D1MAX_AGENT_ARGS=` 里带上验收时量出来的换算参数。
      - 临时硬盘到了：`D1MAX_OUTBOX=` 指到它上面，并写 `D1MAX_OUTBOX_MOUNT=` 挂载点（没挂上
        代理就不起，不会悄悄写到系统盘上）。

- [ ] **起代理**：

      ```sh
      sudo systemctl restart d1max-agent
      ```

- [ ] 填了 SN 想让它也记进版本的在途标记（留档用）：原样重跑一次 `install.sh`。脚本看见「这一版
      已经在跑了」会**跳过切换**，但 `systemctl stop` → `release migrate-data` → `systemctl start`
      是**无条件执行**的。这一步不影响代理能不能用，可以不做。

## 三、装完的验收（五条都要过）

- [ ] `systemctl is-enabled d1max-agent` 是 `enabled`，`systemctl is-active d1max-agent` 是
      `active`。
- [ ] `journalctl -u d1max-agent -n 50` 里有一行
      `d1max-agent 起来了:transport=mqtts://… hal=… robot=<这只狗的编号>`，之后没有反复重启。
      **`hal=` 后面是 `sim` 还是 `d1max`，跟你在 `env` 里填的一致。**
- [ ] 手机（站点模式）里这只狗出现在狗列表上，在线、状态新鲜；点进去，能力里有 `patrol`、
      `goto`，版本那一栏写着刚装的这一版（手机「版本」屏）。
- [ ] 老服务没了：`systemctl status d1max-patrol` 说找不到这个单元；`ls /usr/local/sbin/d1max-privileged`
      说没有这个文件。
- [ ] `sudo /opt/d1max/bin/python -m d1max_patrol.cli release list` 里「现在跑的」是刚装的这一版，
      没有「在途」（代理连上站点之后会把这一次坐实）。

## 四、演练一次自动回滚（每台机器装完做一次）

回滚这条路要**真跑过一次**，而且演练里必须有一个**故意做坏的升级包**。这一节就是那次演练——
照抄下面的命令即可，不用懂代码。**看到「拒收」就是对的**，那说明校验在工作：一个被人动过手脚、
或者传输途中损坏的包，进不了这台机器。

`<包目录>` 就是「二、装机」给 `install.sh` 的那个参数（形如 `/home/robot/2026-09-20-77b2de`），
`<包名>` 是它的目录名。**别拿 `/opt/d1max/releases/` 底下的目录来做**——那里面建过 `venv/`，
用它演练的话哪一步失败说不清楚。

```bash
# 1. 复制一份装机用的包。**目录名要原样保留**——包校验的第二关就是核对
#    目录名跟 release.json 里的 name 对不对得上。
sudo mkdir -p /tmp/演练
sudo cp -a <包目录> /tmp/演练/

# 2. 故意改坏它：往包里随便挑一个文件，末尾加一个字节。
#    **不要动** /tmp/演练/<包名>/release.json —— 那份自述里记着整棵树的
#    哈希；改坏了文件却不改哈希，正是我们要演练的那种坏包。
echo -n x | sudo tee -a /tmp/演练/<包名>/pyproject.toml >/dev/null

# 3. 拿它去装。**期望它被拒收。**
sudo -u robot env D1MAX_RELEASE_ROOT=/opt/d1max \
  /opt/d1max/bin/python -m d1max_patrol.cli release install /tmp/演练/<包名>

# 4. 收工，把演练用的包删掉
sudo rm -rf /tmp/演练
```

- [ ] 第 3 步**报错退出了**，屏幕上写的是「包的哈希对不上」，后面跟着自述里记的和实际算出来的
      两串哈希。**这就是通过**。
- [ ] 第 3 步要是**没报错、还说落槽了**，那就是不通过。**停下来找人**，别继续交付这台机器。
- [ ] `sudo /opt/d1max/bin/python -m d1max_patrol.cli release list` 再看一眼：「现在跑的」还是
      演练之前那一版。
- [ ] 第 4 步跑过了，`/tmp/演练` 已经删掉。

以后的升级都从站点做（手机「版本」屏：装、切、退）；新版起不来的话，狗上的开机守卫数够次数会
自己退回上一版，站点会出一条告警。

## 五、出错时的三条退路

- [ ] **`sudo /opt/d1max/bin/python -m d1max_patrol.cli release list`**——看局面：现在装着哪几版、
      现在跑的是哪版、有没有在途的升级还没坐实。
- [ ] **`sudo -u robot /opt/d1max/bin/python -m d1max_patrol.cli release rollback`**——退回上一版，
      再 `sudo systemctl restart d1max-agent` 生效。
- [ ] **`journalctl -u d1max-agent -n 100`**——看最近 100 行日志，先看代理是不是在无限重启刷屏
      （`Restart=always` 但 `RestartSec=5`，正常情况不该几秒钟就刷一大片）。常见的是站点地址、
      地图、原点没填，或者证书包不是这只狗的。

## 六、装机之后要留的痕迹

- [ ] 装机的日期、执行人、这台机器的 SN、站点上登记的编号，记进现场的登记表（或者机身贴纸旁边）。
- [ ] `docs/真机待验证清单.md` 里跟装机相关的几条，装完之后回来勾掉「待测」改成实测结果。

## 七、卸载（撤场）

> **卸载是撤场动作，不是维护动作。**
>
> `deploy/uninstall.sh` 会停掉 `patrol_agent`，也就**把 SDK 会话放掉了**。按
> `docs/真机待验证清单.md` 里 #46 / #47 的现场结论：**控制权一旦被上装收回去就抢不回来——厂商侧
> 没有正规交接机制，只能重启运控主机、再抢开机窗口。**
>
> 所以在一台**还要继续干活**的机器上跑它，代价是**一次运控主机重启**。要卸，就是这台机器今天
> 不再干活了才卸。

### 先取证，再装（**这一步跑晚了就永远补不回来**）

静态审计只能证明我们**打算**往哪儿写，证明不了那台机器上实际发生了什么。装机前后两张快照的
差集，才是「我们到底往这台机器上写了什么」的全部证据。

- [ ] **装之前**跑一次快照：

      ```sh
      sudo bash deploy/footprint.sh snapshot
      ```

      不给文件名的话落在 `runs/footprint/` 底下，文件名带 UTC 时间戳。**这个文件要留着**——它是
      装机前那一刻的盘上状态，事后补不出来。脚本本身**只读**：被勘察的那几处目录，一个字节都
      不写；它唯一写盘的地方就是这个输出文件。
- [ ] **看一眼端口那几行。** 我们自己占的端口只有旁路进程那两个：8090、8091（代理只往外连站点，
      不监听端口）。装机**之前**它们就有人占着的话，`snapshot` 会当场在屏幕上喊出来。
- [ ] **装完之后**，拿刚才那份快照跑一次 diff：

      ```sh
      sudo bash deploy/footprint.sh diff runs/footprint/<装机前那一份>
      ```

      它分三档报：新增的、被改动的、消失的，每一条都判一次「是不是我们的」，末尾给出结论和越界
      条数。
- [ ] **装之前那一次没跑，后面就再也证不出来了。** 所以这一条排在第二章之前，不是排在第七章里
      等着。

### 我们只往这几处写

`deploy/install.sh` 开头有一段**给机器读的对账声明块**：它往盘上写的每一处都记一行 `@写盘`，
`deploy/uninstall.sh` 里对应地记一行 `@删除` 或 `@保留`，`tests/test_deploy_coexist.py` 把两边
对起来——一边新加一处而另一边没跟上，那条测试当场红。**下面这张表是照抄它的。**

**一、`/opt/d1max`**

- `/opt/d1max`——根目录
- `/opt/d1max/releases`——版本槽（只有代码和 venv）
- `/opt/d1max/bin`、`/opt/d1max/bin-venv`——跟版本无关的解释器和它的 venv
- `/opt/d1max/current`——版本链
- `/opt/d1max/pending.json`——在途升级标记（切版本到坐实之间才有）
- `/opt/d1max/rolled_back.json`——开机守卫退回上一版时留的条子（代理报给站点后删掉）

**二、`/var/lib/d1max`**——数据根：代理的发件箱（断网时暂存、传到站点就删）、事件簿、幂等记录。
升级、回滚、`prune` 都不碰它。

**三、`/etc/d1max`**——配置目录：`env`（现场值）、站点签发的证书包 `tls/` 与注册文件（人拷来的）。

**四、`/etc/systemd/system/d1max-agent.service`** 和它的开机自启链
`/etc/systemd/system/multi-user.target.wants/d1max-agent.service`。

**五、只删不写的（老机器上可能还在）**：`d1max-patrol.service` 与它的自启链、`d1max-bootguard.service`、
`/usr/local/sbin/d1max-privileged`、`/usr/local/sbin/d1max-restart-now`、`/etc/sudoers.d/d1max`、
`/opt/d1max/bundles`。`install.sh` **从来不写它们**，只把它们清掉；`uninstall.sh` 也负责收掉它们。

**除此之外盘上没有别的。** 所有 `pip install` 都落在 `/opt/d1max` 底下的 venv 里，
`python3 -m venv` 只读系统 `python3`，不往系统 `site-packages` 里写东西。

### 怎么卸

`deploy/uninstall.sh` 分五步跑：说清楚要干什么 → 收掉 `patrol_agent` → 停服务、关自启、清我们的
systemd 单元 → 清盘上的东西 → 打回执。这台机器上没有的那一半会自动跳过；什么都没装过的机器上
跑一遍，干净退 0。

- [ ] **先看它打算删什么（这一步无风险，先做）：**

      ```sh
      sudo bash deploy/uninstall.sh --dry-run --agent-root <仓库根>
      ```

      `--dry-run` 下每一条都只打印 `[dry-run] 会删：……`，**一个字节都不动**。
- [ ] **真删：把 `--dry-run` 去掉就是真删。**

      ```sh
      sudo bash deploy/uninstall.sh --agent-root <仓库根>
      ```

      **默认就是彻底卸干净，不需要再加任何「确认」参数，脚本也不会问你第二遍。** 想先看一眼的人
      走上面那条 `--dry-run`。
- [ ] **只想重装、不想重新向站点登记这只狗的，加 `--keep-data`：**

      ```sh
      sudo bash deploy/uninstall.sh --keep-data --agent-root <仓库根>
      ```

      它留下 `/etc/d1max`（证书包、注册文件、`env`）、`/opt/d1max` 根目录本身、`/var/lib/d1max`
      （**发件箱里可能还有没传到站点的东西**）。其余照删——**包括 `/opt/d1max/releases`**，它里面
      只有代码和 venv，重装会重建。
- [ ] **`--agent-root <目录>` 什么时候要指。** 不给的话脚本按「自己在仓库里的位置」去找：仓库根。
      **脚本被单独拷到别处跑的时候必须指**，要指的是**放 `runs/` 的那个目录**。
- [ ] **`--purge-agent-binary` 是干嘛的。** 不加它，`motion/patrol_agent` 留着——它是源码目录里
      编出来的产物，不是装机脚本装上去的。**要把这台机器上我们的东西清到一个不剩，才加它。**
- [ ] **收 `patrol_agent` 走四级，一级比一级硬：** 往 FIFO 写一条 `shutdown`（带 5 秒超时）→
      有 pidfile 就等它自己退，最多 15 秒 → 还在就 `TERM`，等 5 秒 → 再不走就 `KILL`。
- [ ] **卸完之后，第三次跑 `footprint.sh diff`：** 判据是回零——新增、改动、消失三档都该回到
      装机之前那一刻的样子。没回零的每一条都要逐条抄下来。
- [ ] **站点上把这只狗吊销**：`d1max-site revoke <这只狗的编号>`。狗撤场了，它的证书就不该还能
      连站点。

> **不动的东西**：别家的栈、机载上层系统、ROS、任何不叫 `d1max-*` 的 systemd 单元，一个字节都
> 不碰。这不是靠自觉——`rm` 之前有两把锁：目标不许为空，且目标必须长成允许的那几个形状之一，
> 不符合就打印「拒绝删除……这是护栏，不是错误」然后跳过。

### 卸不掉的痕迹——**这些我们收不掉，你得知道**

- **systemd 的历史日志。** 卸完之后 `journalctl -u d1max-agent` 照样查得到。要清得用
  `journalctl --vacuum-time=` 之类，而**那会把别人的日志一起清掉**，所以这个脚本不替你做这个决定。
- **`~/.cache/pip` 里的轮子缓存。** 留在跑装机那个账号的家目录底下。
- **shell history。** 跑过装机、跑过卸载的人在 `~/.bash_history` 里留下的那些命令。
- **`runs/` 底下的快照文件本身。** `footprint.sh` 写在 `runs/footprint/` 底下的那几张快照
  **不删**——它们正是你要留着当证据的东西。
- **`motion/patrol_agent` 这个二进制。** 不带 `--purge-agent-binary` 就留着。
- **厂商那一侧收到过的东西。** 我们通过 SDK 下发过的导航指令、建过或加载过的地图和路径，留在
  运控主机和上层系统那一侧。**我们够不着**。
- **`dmesg` / 内核环形缓冲区。** 插拔过外接设备的痕迹在里面，重启之后才会滚掉。
- **站点上的东西。** 这只狗传上去的证据、录包、建出来的图、审计记录，都在站点上，卸狗不动它们；
  要删在站点上删。
- **`rm -rf` 不擦盘。** 删掉的是目录项，字节还躺在未分配块里。要真正抹掉得另外做（填盘或
  `shred`），这个脚本不做。
- **现场每一台手机上的东西。** 装过的那个 app、它存着的站点地址与证书指纹、登录状态。撤场的时候
  要挨台把 app 卸掉，并在站点上把不再用的账号停用。
- **登记表和机身贴纸。** 卸载不会去改它们。

另有一条性质不同、但同样要在动手之前说清楚的：

- **默认模式会把 `/var/lib/d1max` 整个删掉。** 发件箱里**还没传到站点的证据**也就没了。要留，
  先等它传完（值守屏上这只狗的证据积压回到 `0`），或者改用 `--keep-data`。
