# 装机清单

给现场的人用的单子，逐条能打勾。§7.9 说得很直白：装机是一次性的、要能重复、
要留痕——所以这份清单跟 `deploy/install.sh` 一一对应，脚本能重跑，这份单子
也能重填。出问题按「五、出错时的三条退路」走，不要凭记忆猜。

---

## 一、装机前要准备什么

- [ ] Orin NX 能上网（`curl -sS -m 8 https://pypi.org/simple/` 有响应；
      出不了外网就提前准备好 aarch64 离线 wheel 包，见 `scripts/orin-survey.sh`
      第 5 节）。
- [ ] 一块**备份盘**（不是 U 盘）已经按镜像盘装机的方式初始化过（若这台是
      第一次装，跳过这一条）。
- [ ] 装机用的包已经在这台机器上：`/home/robot/d1max-<日期>-<短哈希>` 这样
      的目录，或者能被 `pip install` 认的路径/归档。
- [ ] 知道这台机器的**机身序列号（SN）**——现场贴在机身上的标签，不是厂商
      SDK 或导航 WebSocket 接口能报出来的字段（它们都不报这个）。
- [ ] 知道这台机器**有没有装上装**（机载上层系统）。这决定装完之后
      `PUT /api/identity/payload` 要填 `true` 还是 `false`。

## 二、装机（对应 `deploy/install.sh` 的七步）

```
sudo bash deploy/install.sh <包目录>
```

- [ ] **1/7 建目录。** 屏幕上看到 `建目录 /opt/d1max`，`/opt/d1max/releases`
      和 `/opt/d1max/bin` 建出来了，属主是 `robot`。
- [ ] **2/7 装版本无关的解释器。** 屏幕上看到
      `装一个跟版本无关的解释器到 /opt/d1max/bin`。第一次装机会新建一个
      venv，重跑不会重建（幂等）。
- [ ] **3/7 把包落进槽里。** 这一步跑的是 `d1max cli release install`，
      屏幕上看到 `落槽了: <名字> (版本 ...)`。只落槽，不切换，不影响正在
      跑的服务（如果有的话）。
- [ ] **4/7 给这一版建自己的 venv。** 屏幕上没有报错。**这是每版一个的
      venv，不是共用根解释器**——回滚要把依赖也一并退回去，这一步就是
      为那件事准备的。第一次给这一版建会花一点时间装依赖，重跑不会重建。
- [ ] **5/7 装 systemd 单元与环境文件。** 屏幕上看到
      `装 systemd 单元与环境文件`。**单元只有一个**：`d1max-patrol.service`。
      版本守卫不再是单独的 `d1max-bootguard.service`，它现在是这个单元里的
      一行 `ExecStartPre=`——这样它在**每一次服务启动**时都数一次，而不是
      只在真开机时数（不带上装的机器升级走的是 `systemctl restart`，根本
      不开机）。老机器上装过的 `d1max-bootguard.service` 会被这一步自动
      停掉删掉，屏幕上可能会看到一句 `Removed ...` 或者什么都没有，两种
      都正常。
      这一步还会顺带在 `/etc/d1max/env` 写一份模板——**只在这个文件不存在
      时写**，已经填过 SN 的机器重跑 `install.sh` 不会被抹掉。
- [ ] **记下屏幕上打出来的设备 PIN（§7.9 第 2 步）。** 第一次装这台机器时，
      5/7 步会在屏幕上打一行
      `>>> 这台机器的设备 PIN 是 <六位数字>`。**把它抄进现场登记表**——手机
      app 第一次连这台机器要输它，屏幕关了就找不回来了（还能在机器上看：
      `sudo grep D1MAX_PIN /etc/d1max/env`）。
      **PIN 不能空着。** 服务是带 `--host 0.0.0.0` 起的（手机 app 要连它），
      而没有 PIN 的话服务会拒绝启动，还会每 5 秒重试一次刷满日志；所以
      `install.sh` 在 restart 之前会检查这一行，空的就停下来报错（`exit 3`），
      不会把机器丢进启动循环里。
      **想换成好记的**：编辑 `/etc/d1max/env` 里的 `D1MAX_PIN=` 那一行，再
      `sudo systemctl restart d1max-patrol.service`。
- [ ] **6/7 记上装。** 这一步脚本替不了你（§7.1 纪律 1：只有站在机器旁边
      的人看得见）。照屏幕上给的 `curl` 命令，把这台**有没有装上装**记
      一次。**没记过之前这台机器不许升级**——升级流程不知道该怎么重启它。
- [ ] **在切到这一版之前，先编辑 `/etc/d1max/env`，把 `D1MAX_SN=` 那一行
      填上现场的机身标签。** 这一步不填的后果：命令行 `release activate`
      记进 `pending.json` 的 SN 和重启后 HTTP 服务侧解析出来的 SN 会不
      一致（HTTP 侧会拿兜底的 MAC 值去比），重启后自检第四项
      （`identity`）会假失败，把这一版**好版本判成失败并自动回滚**。
- [ ] **7/7 切到刚装的这一版并起服务。** 屏幕上看到
      `切到 <名字>,上一版 无。重启之后会自检,没过会自己退回去。`，随后
      `systemctl restart d1max-patrol.service` 没有报错。

## 三、装完的验收（五条都要过）

服务听的端口是 **8095**（`app/server.py` 的 `DEFAULT_PORT`）。
厂商导航 WebSocket 用的是另一个端口，不是我们的，别往那儿发。

**先换一个 token。** 服务的 `ExecStart` 带 `--host 0.0.0.0`，所以它必须有
PIN；而**从 127.0.0.1 发过去一样要 token** —— 没有「本机豁免」这回事（本机
上跑着的别的进程不比网上的人更可信）。裸 `curl` 会全部返回 401：

```sh
D1MAX_PIN=$(sudo sed -n 's/^D1MAX_PIN=//p' /etc/d1max/env)
TOKEN=$(curl -sS -X POST http://127.0.0.1:8095/api/auth   -H 'Content-Type: application/json'   -d "{\"pin\":\"$D1MAX_PIN\",\"operator\":\"装机\"}"   | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
test -n "$TOKEN" || echo "换 token 失败：PIN 不对，或者服务没起来"
```

**别把 PIN 敲进命令里。** 上面那条是从 `/etc/d1max/env` 取的；照抄一条带真
PIN 的命令进任何文档或工单，等于把这台机器的钥匙印在纸上。

下面五条都要过：

- [ ] `curl -sS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8095/api/release`
      返回里 `current`（当前版本）有值，不是空。
- [ ] `curl -sS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8095/api/selfcheck`
      里四项（`process`、`control`、`bridges`、`identity`）全绿
      （`verdict` 不是 `rollback`）。**`identity` 这一项就是靠上一节填好的
      `D1MAX_SN` 才能过。**
- [ ] `curl -sS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8095/api/identity`
      里 `payload_recorded` 是 `true`（第 6 步记过上装了）。
- [ ] `curl -sS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8095/api/identity`
      里 `provisional` 是 **`false`**（§7.9 第 1 步）。是 `true` 说明这台机器的
      SN 还在拿网卡 MAC 兜底 —— 也就是 `/etc/d1max/env` 里的 `D1MAX_SN` 没填
      上、或者填了但服务没重启。**`provisional` 是 `true` 的机器不许出厂**：
      MAC 兜底值跟 `release activate` 记下的 SN 一旦对不上，以后每次升级都会
      把好版本判成失败退回去。填好 SN、
      `sudo systemctl restart d1max-patrol.service`，再查一遍。
- [ ] 同一份返回里 `hand_written` 是 **`true`**（§6.2）。是 `false` 说明这台
      的 SN 是从设备树里读出来的**模组序列号**，不是机身上贴的那张标签。它够
      稳定，所以 `provisional` 查不出来 —— 但换一次主板它就变了，而归档、备份
      盘、任务包的 `targets` 全是按 SN 归堆的。**把机身标签上的编号填进
      `D1MAX_SN`，重启，再查一遍。**

**装完把 token 忘掉就行**，它 12 小时不用自己失效。控制权、接管、热点上为什么
只发只读凭证，都在 `docs/鉴权与控制权.md` 里。

## 四、演练一次自动回滚（每台机器装完做一次）

§8.5 要求回滚这条路**真跑过一次**，而且演练里必须有一个**故意做坏的升级包**。
这一节就是那次演练——照抄下面的命令即可，不用懂代码。**看到「拒收」就是对的**，
那说明校验在工作：一个被人动过手脚、或者传输途中损坏的包，进不了这台机器。

下面四步照抄。`<包目录>` 就是「二、装机」那一步给 `install.sh` 的那个参数
（形如 `/home/robot/d1max-2026-09-20-77b2de`），`<包名>` 是它的目录名
（形如 `d1max-2026-09-20-77b2de`）。**别拿 `/opt/d1max/releases/` 底下的目录
来做**——装机时往那里面建过一个 `venv/`，用它演练的话哪一步失败说不清楚。

```bash
# 1. 复制一份装机用的包。**目录名要原样保留**——包校验的第二关就是核对
#    目录名跟 release.json 里的 name 对不对得上。
sudo mkdir -p /tmp/演练
sudo cp -a <包目录> /tmp/演练/

# 2. 故意改坏它：往包里随便挑一个文件，末尾加一个字节。
#    **不要动** /tmp/演练/<包名>/release.json —— 那份自述里记着整棵树的
#    哈希；改坏了文件却不改哈希，正是我们要演练的那种坏包（也正是包在
#    传输途中损坏、或者被人动过手脚时的样子）。
echo -n x | sudo tee -a /tmp/演练/<包名>/pyproject.toml >/dev/null

# 3. 拿它去装。**期望它被拒收。**
sudo -u robot env D1MAX_RELEASE_ROOT=/opt/d1max \
  /opt/d1max/bin/python -m d1max_patrol.cli release install /tmp/演练/<包名>

# 4. 收工，把演练用的包删掉
sudo rm -rf /tmp/演练
```

- [ ] 第 3 步**报错退出了**，屏幕上写的是「包的哈希对不上」，后面跟着自述里
      记的和实际算出来的两串哈希。**这就是通过**——这台机器的包校验是活的，
      一个坏包进不来。
- [ ] 第 3 步要是**没报错、还说落槽了**，那就是不通过。**停下来找人**，别继续
      交付这台机器：包校验没在工作，意味着一个损坏的升级包能被装进去，
      而自动回滚指望的正是它挡在最前面。
- [ ] `curl -sS -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8095/api/release` 再看一眼：`current` 还是演练
      之前那一版，一个字节都没被这个坏包动过。
- [ ] 第 4 步跑过了，`/tmp/演练` 已经删掉。

## 五、出错时的三条退路

- [ ] **`sudo /opt/d1max/bin/python -m d1max_patrol.cli release list`**——
      看局面：现在装着哪几版、现在跑的是哪版、有没有在途的升级还没坐实。
- [ ] **`sudo /opt/d1max/bin/python -m d1max_patrol.cli release rollback`**——
      退回上一版。重启生效：`sudo systemctl restart d1max-patrol.service`。
- [ ] **`journalctl -u d1max-patrol -n 100`**——看最近 100 行日志，先看
      服务是不是在无限重启刷屏（`Restart=always` 但 `RestartSec=5`，正常
      情况不该几秒钟就刷一大片）。

## 六、装机之后要留的痕迹

- [ ] 装机的日期、执行人、这台机器的 SN、有没有上装，记进现场的登记表
      （或者机身贴纸旁边）。
- [ ] `docs/真机待验证清单.md` 里跟装机相关的几条，装完之后回来勾掉
      「待测」改成实测结果。
