## W38-I1：未确认的放宽不再下发

**改了什么**
- `NavZones.effective(map_id, version)`：**在生效的**那一份。没有确认过的底（新版本、从没确认过），或者当前这一份就是确认过的 → 就是当前这一份。当前这一份没确认 → 当前这一份 + 最后确认过的那一份里**没被它盖住**的区域（`covered()`，跟决策 66 的收紧判定同一个函数）。狗守手上的每一个区域，所以这一份不比两者任何一份松：**收紧的当场生效、删除和放宽等确认**（混合修改里新加的保护照样当场生效）。
- 同 id 冲突（例如同一个泳池去掉了硬标记）：确认过的那个换名字 `<id>-held1` 一起守，不重复 id。
- 合起来超过契约上限 200 个：退回只守确认过的那一份（这次新加的也等确认），记警告。
- **同一个修订号的内容永远不变**（狗对同号不同内容回 `stale`，摘要核对也会报错）：
  - 确认一份放宽了的 → 修订号 +1（内容不变；改的人、时刻不动），确认接口**马上**把在生效的发给狗（回包多 `pushed`）。
  - 确认过的那一份里的临时区到期 → `expire()` 从草稿、确认过的那份里一起删，出新修订号（原来只看草稿）。`effective` 本身不按此刻的钟过滤。
- 全部改用在生效的：改区域后的下发、确认后的下发、到期下发、补发（`sync_zones`）、派单闸（修订、`enforced`）、运行配置的区域摘要（R3）、遥控开场「老狗不守硬禁区」提醒、拦截点可达性。
- `view()` 多一项 `held`：还没确认、狗上照旧守着的那几个（给界面用；网页、手机这次**没**加显示）。

**行为变化**：管理员删掉硬禁区后、确认之前，遥控、自主导航、狗重启都还守着它；确认一份放宽了的，修订号比提交时 +1。没确认时自主派遣照旧被拒（W38 原有）。

**旧版本**：狗收到的就是普通的区域集（可能多几个 `-held` 区域），老代理照收。老 App 确认后看到修订号 +1，照常刷新。

**测试**：`packages/site-node/tests/test_site_zones_effective.py` 12 条——存储层 9 条（从没确认、删硬禁区、又加又删、去掉硬标记换名、调高限速、被盖住的不重复带、确认放宽修订 +1、确认没放宽修订不动、到期由站点删并出新修订）；经站点接口到仿真狗 3 条（删硬禁区没确认 → 狗内存和落盘都还有、确认后才没；又加又删 → 新加的马上到狗；运行配置摘要按在生效的对上）。**10 条在旧代码上失败**（另 2 条是两边都该过的基准）。改动的旧测试：`test_site_teleop_desk.py` 假区域对象补 `effective`。

**请重点看**：`covered()` 判「被盖住」的保守性（同外审之前对 `tightens` 的关注）；确认接口在提交后才发、发不出去靠补发；`-held` 改名后摘要、规划都按新 id。
