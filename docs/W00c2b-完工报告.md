## 交付

- **优先级由站点按任务来源定**（`priorities.py`）：回待命点 `-10` < 排程巡检 `10 + clamp(条目 priority, 0..39)` < 人手动派单 `60` < 外部事件 `80`。站点 API 不再认请求体里的 `priority`（原来登录的人填 1000 就能打断一切）。代理的机制不变：严格更高才抢占。命令表多一列 `priority` 留痕（老库自动补列）。
- **被打断的巡检**：排程账的 `result` 记 `preempted`，不自动续跑。
- **待命点**：每台狗若干个命名点（地图、版本、x、y、yaw），一个默认；API `GET/POST /api/robots/<id>/standby`（含删除）、`POST …/standby/return`；CLI `d1max-site standby ROBOT NAME --map M:VER --pose x,y,yaw [--default]`。站点派的任务**正常完成**后自动派回默认点（`-10`，task_id `standby-…`）；排程执行器把「正在回待命点」看成空闲。

## 验收（`test_site_standby.py` 等）

- 排程巡检跑到一半、人手动派 goto → 巡检 `preempted`、账上 `result = preempted`、goto 完成后回待命点。
- 请求体填 `priority: 1000` → 命令表里是 `60`。
- 回待命点途中排程到点 → 派出去的巡检 `accepted`，被抢占的正是那条回程。
- 没有默认待命点 → 不回。

## 设计取舍

1. **只在 `task_done` 之后自动回**（内部评审阻断 2 条改的）：人按 abort 是要狗停下；失败可能是急停、丢定位、安全裁定（前面有人），这时让狗自己再动是错的，而且站点靠「狗没就绪」来拦不可靠（事件可能先于 status 到，安全裁定也不一定改就绪位）。这两种停在原地，人可以按「回待命点」。
2. **待命点记地图版本**，狗加载的地图或版本对不上就不回，并推 `standby_failed`（地图重建后旧坐标不可信）。
3. **手动「回待命点」也是最低优先级**：狗在跑别的任务时回 `busy`；排程到点能抢它。
4. **站点重启后补投的旧 `task_done` 仍会触发回程**（内部评审建议 1）：事件的 `stamp` 是狗的钟，不可信，没有好的判据；回程本身优先级最低、可被任何任务抢占，风险小，记在这里。

## 测试与突变

- 突变（每条看到红再还原）：回待命点也算忙、认请求体的 priority、回程结束也回、被抢占也回、不自动回、排程优先级不走表、默认点不唯一、老库不补列、abort 后也回、失败后也回、不查地图版本、默认标记被清、回不去不推 —— 13 条全红。「失败后也回」起初活了（测试用急停，站点的就绪检查替它挡了），改成 HAL 拒速度（狗一直就绪）后红。

## 内部评审

阻断 2 条（abort 后自动开走、失败后自动开走）已修（取舍 1）。建议：旧事件补投触发回程（记为取舍 4）、地图版本（已做）、输入校验（超大整数 500、字符串 `"false"` 当真、改点清掉默认标记、不能删 —— 都已修）、回不去要可见（`standby_failed`）、收尾时取消在途回程（`StandbyManager.close`）、手动回程优先级（记为取舍 3）、API 文档里残留的 `priority`（已删）、测试加强（被抢占的是回程、巡检 accepted）。
