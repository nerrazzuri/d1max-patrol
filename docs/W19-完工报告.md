# W19 CCTV 接入 · 设计与完工报告

> 工单：「ONVIF/RTSP + 人形/区域入侵检测 → W16」。分支 `w19-cctv` → PR。设计与报告合一份。

## 用户决定（2026-10-05）

- 决策 33：庄园的摄像头**还没装、牌子不清楚**。所以先做通用接入，到现场再对。
- 决策 34：人形、区域入侵检测**用摄像头 / NVR 自带的**（推荐）。站点不跑检测模型，不占算力；准不准看摄像头。

## 怎么做的

走通用标准 **ONVIF**，几乎所有网络摄像头、NVR（海康、大华、宇视……）都支持：
1. 站点向每台摄像头订阅事件，然后一直拉消息、定时续订。
2. 摄像头报「区域入侵」「越线」「有人」这类规则触发，就按这台摄像头登记的防区，当成一条入侵交给 W16 的事件派遣：
   - 来源是 `cctv-<名字>`；
   - 照样限流、同防区合并、派最近的狗去拦截点；
   - 一来就响铃（决策 29）。

几处要紧的判断：
- **只认「由没有变成有」的那一下**。订阅一开始摄像头报的现状（`Initialized`）不算，不然站点一重启，正好有东西在画面里的那几台全报一遍入侵。一直有也不重报。
- **普通「画面动了」默认不算**：树影、车灯、雨太容易误报。按摄像头打开（`--motion`）。
- 同一台摄像头 30 秒内只报一条；W16 那头同防区 60 秒内还会合并。
- 各家规则名不一样，认这些关键词：海康 `FieldDetector`、`LineDetector`；大华 `CrossRegion`、`CrossLine`；ONVIF 分析规则 `ObjectsInside`；人形 `People`、`Human`、`Person`；还有 `Intrusion`、`Tripwire`。到现场看实际报的是什么，不在表里就加。
- 鉴权：WS-Security 口令摘要，再加 HTTP Digest（有的摄像头两样都要）。
- **连不上要让人知道**：断了 5 分钟报一次 P2 `cctv_offline`（「这一路的入侵现在收不到」）。断了退避重连，5 秒到 60 秒。

### 站点

| 块 | 内容 | 文件 |
|---|---|---|
| ONVIF | 取设备能力里的事件服务地址 → 订阅（10 分钟有效、5 分钟续一次）→ 拉消息（每次最多等 20 秒）→ 退订。命名空间不挑（各家前缀、版本不一） | `cctv.py`（`OnvifClient`、`parse_event`） |
| 每台一条线程 | 连上、订阅、一直拉；断了退避重连；记下连没连上、从什么时候起、最近一次报的什么、错在哪 | `cctv.py`（`CameraWatch`） |
| 管 | 每 30 秒照库起停订阅：命令行加、删、改了不用重启站点，改了地址、口令就换一条订阅。断太久报告警。入侵跳回站点事件循环交给事件派遣 | `cctv.py`（`CctvManager`、`incident_reporter`）、`main.py` |
| 实时画面 | 站点拉 RTSP、转 MJPEG（最高 720p、每秒 8 帧），观众共用一条，没人看了 10 秒后收掉。RTSP 地址里没带账号就把这台摄像头的账号塞进去 | `cctv.py`（`CctvView`）、`api.py` |
| 接口 | `GET /api/cameras`：名字、防区、连没连上、最近一次报的，**不带口令**。`GET /api/cameras/<名字>/live`：MJPEG。都是谁都能看（`view`）。不收 POST：加、删只走命令行 | `api.py` |
| 命令行 | `d1max-site camera-add NAME --onvif http://ip --user U --zone Z [--rtsp rtsp://…] [--motion]`，口令从 `D1MAX_CAMERA_PASSWORD` 或交互输入；`camera-rm NAME`；`camera-list`（不显示口令） | `main.py` |
| 库 | `cameras` 表（库结构升到 20）。口令存在站点库里，库只许站点用户读 | `db.py` |

狗的画面和摄像头画面共用同一段 MJPEG 输出（`_mjpeg`）：令牌每隔一会儿复查，注销、过期、停用了画面跟着断。

### 手机、桌面

事件页右上「摄像头…」：
- 每台显示防区，连着（绿）还是连不上（红，写明「这一路的入侵收不到」），最近一次报入侵的时刻，「画面动了也算入侵」的标出来；
- 每 15 秒刷新；
- 有画面地址的点进去看实时画面（走 app 钉证书的那条连接）。

## 外审第一轮（2026-10-06）：FIX-THEN-APPROVE，4 条阻断，已修

**阻断 1：摄像头恢复了，「连不上」告警也一直挂着，几台摄像头还合成一条。**
- 原来所有摄像头都记在站点名下（`robot="site"`）、同一种 `cctv_offline`。告警台按「谁 + 哪一种」聚合，两台同时断就合成一条，后一台盖掉前一台的标题。
- 恢复时也不解决。

修法：
- 每台摄像头记在自己名下：`cctv:<名字>`。
- 管理器记着哪几台报过「连不上」。连上了、或者从库里删掉了，就自动解决这一台的那条（`AlertDesk.resolve_all`，只动这一位这一种）。
- 恢复后再断，再报。

**阻断 2：删掉、改了配置之后，旧订阅还可能派一次狗。** 旧订阅只叫停、不等。它可能正卡在一次拉消息里（最长约 30 秒），回来后照样按旧的防区报入侵：删了的摄像头还派狗，改了防区的还往旧防区派，新旧订阅重叠；站点收尾后还往收掉的事件循环里交东西。

修法：
- 锁里摘下、叫停，锁外等它退干净，再起新的。
- 拉回来的每一条处理之前、`handle` 一进来，都先看停没停。
- `close()` 也等全部退出。

**阻断 3：实时画面的 ffmpeg、临时文件没收干净，还会给旧画面。**
- ffmpeg 自己退了，只把指针清空：不回收进程、不关错误输出文件、不关管道。
- 站点收尾不管 API 里的画面：有观众或在 10 秒空闲等待里的 ffmpeg，站点退了还活着。
- 新起一条不清上一条的画面：摄像头已经断了，新观众先看到上一轮缓存的那张。

修法：
- 一代一条进程。起新的就换一代、清掉旧画面；旧一代的读线程看见换代就不再动状态。
- 新观众只给加入之后来的帧。
- 收尾都走一处 `_reap`：杀进程、回收、关管道、关错误输出文件、删清单。用在 ffmpeg 自己退了、没人看了、改了配置、站点收尾这几种情况。
- `close()` 幂等，关了之后不再起。
- 站点收尾时 `close_cctv_views` 全关。

**阻断 4：摄像头口令写在 ffmpeg 的命令行里。** 原来把 `rtsp://账号:口令@…` 直接放进 ffmpeg 参数，同机别的用户用 `ps`、`/proc/<pid>/cmdline` 看得到。

修法：
- 带口令的地址写进一个**只许站点用户读（0600）**的 concat 清单，ffmpeg 从清单里打开，命令行里只有清单路径。画面一出来就删清单，收尾也删。
- ffmpeg 5 起清单里再加一句走 TCP。Ubuntu 22.04 带的 4.4 不认这一句（实测「unknown keyword」），不加，用 ffmpeg 默认的：先 UDP，收不到转 TCP。
- 实测 4.4：从这种清单里打开一条不断的网络流照样出画面。
- ffmpeg 的报错（可能带地址）进日志之前、状态里的错误回给手机之前，都过 `scrub` 抹掉账号口令。

威胁模型（写明）：
- ONVIF 口令在站点进程里用，不进任何命令行。
- 口令存在站点库里（明文，摄像头鉴权要用）。站点库、清单都只许站点用户读，站点按部署跑在自己的系统账号下。
- 能以站点用户身份登录主机的人看得到口令，这跟看得到站点库一样。

补的测试：
- 两台同时断各一条，只恢复一台就只解决那一台，删掉断着的那台也解决，恢复后再断再报；
- 告警台只解决这一位这一种，别的摄像头的不动；
- **删除时订阅正卡在拉消息里**：删除要等旧线程退干净，那时回来的入侵不派；
- 站点收尾等订阅线程退出；
- ffmpeg 自己退了：进程回收、错误输出关了、清单删了；
- 重起不给上一轮的旧画面；
- 站点收尾收掉画面进程，关两次也没事，关了不再起；
- 口令不在命令行，清单 0600、里面有口令、出画面就删；ffmpeg 5 带走 TCP，4 不带；
- ffmpeg 报错里的口令在日志里抹掉，状态接口也抹掉。

突变 18 条全杀：
- 单条的 15 条：告警记回站点名下、连上了不解决、删了不解决、不等旧线程、ffmpeg 自己退了不收、口令进命令行、出画面不删清单、日志不抹口令、状态接口不抹口令、ffmpeg 5 不走 TCP、关了还能再起、告警台不分种类全解决，等等。
- 成对的 2 条：「拉回来先看停没停」「`handle` 一进来先看停没停」是两道防线，「起新的清旧画面」「收尾清画面」也是两道。单去一道时另一道挡着，所以单条突变活着；两道一起去掉，测试就红。
- 原来写的「新观众只给加入之后来的帧」没必要：旧画面靠换代时清空就挡住了，观众加入一条正在跑的流时马上拿到最新那张更好。已改回。

修完全量 Python 0 失败。

**非阻断备注（记着，接真摄像头时看）**：
- 有的摄像头订阅一开始报现状时不写 `PropertyOperation`，第一条「有」会被当成由无到有，站点重启时可能误报一条。接真摄像头时记下原始事件，必要时按牌子适配。
- 还没有摄像头数、同时转码数的上限。第一版摄像头少，正式部署前加。

## 外审复查（2026-10-07）：FIX-THEN-APPROVE，剩 2 条，已修

原来的 4 条里：
- 旧订阅不再派、口令不进命令行：通过；
- 离线告警隔离、画面收尾：主路径通过，重启路径和「配置变化时有人在看」两处还有缺口。

**1. 站点重启之后，已经恢复的摄像头不解决旧的「连不上」。**
- 原来只有名字在内存集合 `_offline` 里才去解决，可进程一重启这个集合就是空的。
- 断着时报的那条落了库：站点重启、摄像头已经连上，旧告警永远挂着。
- 停机期间删掉的摄像头也一样。
- 而且原来是先改内存、再报或解决，报、解决失败了内存已经前移，不会再试。

修法：**告警簿（落库的）才是真理源**。
- 摄像头连着，就去解决告警簿里它的「连不上」（`resolve_all`，幂等），不看内存里记没记过。
- 报之前先看告警簿里是不是已经挂着（`has_open`）。站点重启时还断着的，不重报。
- 每拍把库里已经没有的摄像头留下的「连不上」都解决掉（`resolve_except`），停机期间删的也算。
- 报、解决**成了**才在内存里记一笔（省得每拍都去问）；失败了不记，下一拍重试。
- 这几样都经 `LoopAlerts` **同步**跳进事件循环做完、拿到结果（出错照样抛），不再是交出去就不管。

**2. 删掉或改了摄像头，已经在看的旧画面不关。** 原来只在下一次有人打开画面时才比配置、换掉旧的：删掉的摄像头再也不会有人打开，改了地址、口令没人重开，就一直用旧的。这既是资源问题，也是权限撤销问题。

修法：
- 同步摄像头时，删掉的、改了配置的，都通知 API（`on_changed` → `drop_cctv_view`），当场摘下、关掉它的画面。
- 正在看的流当场结束，ffmpeg 收掉，不等任何客户端再来。

**非阻断备注也一起改了**：等旧订阅线程超时没退的话，`join` 回「没退」，记一条错（线程还在，只是叫停后 `handle` 不再派），不再当成退干净了。

补的测试：
- 离线告警落库 → 新建告警台和管理器模拟重启 → 摄像头已经连上：旧告警解决。同一次测试里：停机期间删掉的摄像头，它的告警也解决；还断着的那台不重报（次数还是 1）。
- 报不出去：不记，下一拍报。解决不了：不记，下一拍解决。确认解决了：不再每拍去问。
- 有人在看时删掉摄像头：正在看的流当场结束，ffmpeg 收掉，摘掉之后再也打不开。
- 有人在看时改了 RTSP 地址：旧流关掉、旧 ffmpeg 收掉，再打开（真走一遍 HTTP）按新地址起。

原来的管理器测试改用真的告警台（落库）：「两台同时断」那条现在直接看告警簿里还挂着哪几条。

突变 7 条全杀：
- 只在内存记过才解决（原来的写法）；
- 不解决库里已经没有的；
- 报之前不看库里；
- 报之前就记；
- 解决之前就记；
- 配置变了不通知；
- 通知了不关画面。

调测试时踩过一个坑：「改了地址再打开」那条一开始让真 ffmpeg 去连一个不存在的地址，测试客户端先超时、收尾卡住。改成接口那边留一个造画面对象的口子（`cctv_view_factory`），测试里换成一直出帧的假 ffmpeg。

## 已知限制、要你做的

- **没有接过真摄像头**：ONVIF 各家实现差别不小。到现场按 `docs/真机联调手册.md` 的思路一台一台接：
  1. `d1max-site camera-add …` 登记；
  2. 手机「摄像头…」看是不是连着；
  3. 在摄像头上配好区域入侵规则、人走进去；
  4. 看事件页有没有来一条 `cctv-…` 的入侵、狗有没有出动。
  
  没报的话看站点日志里这台摄像头报的主题是什么，不在关键词表里就加。
- 海康、大华的私有接口（ISAPI、HTTP 事件推送）没做：ONVIF 够用就不做；牌子定了、ONVIF 事件不全再说。
- 用的是摄像头自带的检测（决策 34），误报、漏报看摄像头和规则配得好不好。站点自己跑检测没做。
- 固定摄像头的画面不录（W18 录的是狗的相机）。NVR 自己会录；要站点也录再加。
- 摄像头的口令存在站点库里（明文，摄像头鉴权要用）；站点库只许站点用户读，不进命令行（见外审第一轮的威胁模型）。
