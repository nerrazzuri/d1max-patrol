# 建图回环（可选的一步，2026-10-14）

MOLA 雷达里程计建图走一圈回到原处会差一点（漂移），同一面墙就扫成两层。这一步在**打包之前**把建图存下的
simplemap 交给 MOLA 的离线回环工具 `mola_sm_loop_closure`，改好关键帧位姿，再从改好的 simplemap 重出
点云、定位先验，轨迹跟着挪，然后照原来的打包。**狗上没装这个工具就跟原来一模一样**，装了才跑；跑不成、
没找到回环、改得离谱都退回原来的打包，`build.json` 里写着为什么。

一句话结论（开发机，三份办公室图）：点云上的双层墙确实收拢了（最明显的一处 15 cm 的鬼影墙并回一层），
有一份图基本不变；**5 cm 的规划栅格看不出差别**（这几份图漂移只有 5–24 cm）；定位回放不比原来差。
真狗、大场地都没验过（第六节）。

## 一、工具从哪来

apt 上只有 1.3.0，要 MRPT 3（多装 23 个包、换掉开发机的 MOLA 底子），不装。改成在**临时 colcon 工作区里
从源码编** MRPT 2 那一代、跟装着的 MOLA 3.2 / MRPT 2.15 对得上的版本：

| 包 | 从哪来 | 版本 | 为什么是这个 |
|---|---|---|---|
| `mola_sm_loop_closure` | github.com/MOLAorg/mola_sm_loop_closure | 提交 `e737aa8`（2026-09-05，develop；`package.xml` 里还写 1.2.2） | 移植 MRPT 3（#25，2026-09-19 合进去，出 1.3.0）之前的最后一个提交，跟 MOLA 3.2（ROS 包 2026-09-08 编的）同一时期；比 1.2.2（6 月）多了「真回访被候选下限拒掉」等修正 |
| `mola_georeferencing` | **不在单独的仓库**，在 github.com/MOLAorg/mola_state_estimation 里（rosdistro 这么登记的） | 标签 `2.4.2`（2026-06-04），只取这一个子目录 | 装着的 `mola_gtsam_factors`、`mola_state_estimation_simple` 都是 2.4.2；3.0.x 是 MRPT 3 那一代 |
| `mrpt_libtclap` | github.com/MRPT/mrpt_ros | 标签 `2.15.21` | 回环工具和 georeferencing 的命令行要 TCLAP 头文件；apt 有 `ros-humble-mrpt-libtclap` 但没装、不装。它的 CMake 会去拉 MRPT 2.15.21 的源码装头文件 |

没编：`third_party/kiss-matcher`、`robin` 两个子模块（只给另一种算法 FrameToFrame 用，可选）。

编法（开发机验过；狗上照抄，`--install-base` 换成 `/opt/d1max/loop-closure`）：

```bash
mkdir -p ~/lcws/src && cd ~/lcws
git clone https://github.com/MOLAorg/mola_sm_loop_closure.git src/mola_sm_loop_closure
git -C src/mola_sm_loop_closure checkout e737aa8
git clone https://github.com/MOLAorg/mola_state_estimation.git /tmp/mse
git -C /tmp/mse archive 2.4.2 mola_georeferencing | tar -x -C src      # 只要这一个包
git clone --depth 1 --branch 2.15.21 https://github.com/MRPT/mrpt_ros.git /tmp/mrpt_ros
cp -r /tmp/mrpt_ros/mrpt_libtclap src/
# mrpt_libtclap 看到这个目录就不自己去克隆 MRPT（要带子模块，不然配置时报「git submodules missing」）
git clone --depth 1 --branch 2.15.21 --recurse-submodules --shallow-submodules \
    https://github.com/MRPT/mrpt.git build/mrpt_libbase/mrpt-build/src/mrpt
. /opt/ros/humble/setup.bash
colcon build --merge-install --install-base /opt/d1max/loop-closure \
    --packages-up-to mola_sm_loop_closure \
    --cmake-args -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
echo "mola_sm_loop_closure e737aa8 + mola_georeferencing 2.4.2 + mrpt_libtclap 2.15.21 (MRPT 2.15.21, MOLA 3.2.0)" \
    > /opt/d1max/loop-closure/share/mola_sm_loop_closure/d1max-build.txt
```

- 开发机（28 线程，`MAKEFLAGS=-j12`）：三个包 **64 s**；装出来 **3.3 MB**（`bin/mola-sm-lc-cli` + 两个 .so）；
  源码 + 编译目录约 540 MB（MRPT 源码占 214 MB，编完可删）。
- 链的是 `/opt/ros/humble` 里的 GTSAM 4.2.0（开发机 `/usr` 下另有 `libgtsam-notbb-dev` 4.3.0，没被用上，
  `ldd` 核过）、MRPT 2.15、mp2p_icp 2.14、MOLA 3.2。
- 踩到的：①MRPT 浅克隆要带子模块；②`mola_georeferencing` 没有单独的仓库；③程序**不带 RPATH**，库要在
  `LD_LIBRARY_PATH` 里 —— 所以用 `--merge-install` 装成一个前缀，打包时由 `build.py` 把 `<前缀>/lib` 加到最前
  （开发机上只 source ROS、不 source 工作区，按环境变量找到工具，整条跑通，出的栅格与 frames 跟 source 了工作区
  跑的逐字节一样）；④`mola-sm-lc-cli --version` 只会说 `none`，版本记在上面那个 `d1max-build.txt` 里，
  `build.json` 抄它；⑤上游给 3D 雷达的参数（`loop-closure-lidar3d-gicp.yaml`）是给室外 100 m 量程配的：
  3 m 以内的点全扔、0.7 m 的体素，室内几米宽的房间基本没点了，要改（第二节）。

**许可证**：`mola_sm_loop_closure`、`mola_georeferencing`、`mola_lidar_odometry` 都是 **GPLv3**（厂家说可以
另买闭源许可）。我们按外部命令调用、不链接我们的代码，跟现在用 apt 装的 MOLA 一样；但要是我们**自己编好、
随产品发给客户**，就是在分发 GPL 程序，得同时给出（或指明）对应源码 —— 上游仓库 + 上面的提交号 + 编法就够。
`pipelines/loop-closure.yaml` 是从上游 GPL 的参数文件改的，文件头保留了上游的版权声明。顺带：
`docs/厂家建图定位调研.md` 第三部分的表里把 MOLA 写成「开源（BSD）」，不对，是 GPLv3（这次在表下补了一句）；
`docs/仓库与知识产权审计-2026-10-12.md` 第三节的依赖表里没列 MOLA（没改，留给定许可证那件事）。

## 二、接进建图（`packages/localizer/src/d1max_localizer/build.py`）

`package()` 开头先跑 `loop_close()`（离线建图 `d1max-loc build` 和边走边建打包的 `--reuse` 都走这里）：

1. **找工具**（`find_loop_closure`，`d1max-loc build --loop-closure auto|off|<路径>`，默认 `auto`）：环境变量
   `D1MAX_LOOP_CLOSURE`（路径或 `off`）→ `PATH`（以后 apt 装进 `/opt/ros/humble/bin` 的那种）→
   `/opt/d1max/loop-closure/bin/mola-sm-lc-cli`。都没有 = 不回环；给的路径不是能跑的程序也当没有（可选的一步
   不能让建图失败）。
2. `mola-sm-lc-cli -i work/map.simplemap -o work/lc/map.simplemap -p pipelines/loop-closure.yaml`（算法用默认的
   `SimplemapLoopClosure`：按 10 s 切子图、子图之间 GICP、GNC 剔除错的回环再优化）。日志里读回环数。
3. `sm-cli export-keyframes` 导出前后的关键帧位姿；**轨迹**（`traj.tum`，每帧一个）按关键帧的改动挪
   （`correct_traj`：每个关键帧的改动左乘，夹在两个关键帧之间的帧两边各挪一份、按时刻插）。栅格的真射线、
   `frames.json` 的标定、`coverage.json` 都用挪过的轨迹。
4. `sm2mm -p pipelines/prior-from-simplemap.yaml` 从回环后的 simplemap 重出**定位先验**：跟 MOLA 建图存的局部
   地图同一个图层名（`localmap`）、同一个类（`mola::KeyframePointCloudMap`），每帧的处理照
   `lidar3d-default.yaml`（1 m 内的点不要、按存的速度去畸变、0.15 m 自适应降采样到约 1 万点）。
5. 点云照原来的 `sm2mm` + `mm2ply`，只是读回环后的 simplemap。然后照原来的打包。

都在 `work/lc/` 里做（回环工具还会往当前目录写 `sm_lc__initial.tum` / `sm_lc__final.tum`，所以在这个目录里跑它）。
用到的命令除回环工具外都是狗上已经有的（`sm-cli`、`sm2mm`、`mm2ply` 跟 MOLA 一起装的 mp2p_icp 里）。重出的先验
每次跑字节不完全一样（多线程降采样），关键帧数、点数一样；栅格、`frames.json`、`coverage.json` 逐字节一样。

**退回原来的打包**（`build.json` 的 `loop_closure.why` 写原因）：没有工具；工具退出码不为 0（带日志尾巴）；
日志里没有回环数；回环数是 0；前后关键帧对不上；把关键帧挪得超过 max(1 m, 路程 × 5%) 或转超过 15°（多半认错了
地方；**只拦得住离谱的**，见第三节「切 5 s 子图」那一组）；中间出别的错。

`build.json` 多一项 `loop_closure`：

```json
"loop_closure": {"ran": true, "used": true, "cli": "/opt/d1max/loop-closure/bin/mola-sm-lc-cli",
  "version": "mola_sm_loop_closure e737aa8 + …", "pipeline": "…/loop-closure.yaml",
  "closures": 7, "keyframes": 163, "path_m": 22.7, "max_shift_m": 0.058, "end_shift_m": 0.051,
  "median_shift_m": 0.03, "max_turn_deg": 0.9,
  "timings_s": {"lc_s": 5.6, "keyframes_s": 0.6, "prior_s": 1.5}}
```

没装工具时是 `{"ran": false, "why": "没有回环工具(mola-sm-lc-cli)"}`，别的文件跟原来逐字节一样（开发机上拿
10-08 的 work 目录重打，跟 `runs/w35-lowq/prior-v1` 一致）。`timings_s` 里多一项 `loop_closure_s`（跑了才有）。

回环的参数（`pipelines/loop-closure.yaml`，改了什么写在文件头）：不用 GNSS / IMU 重力（我们的 simplemap 里
没有；RTK 另从 `rtk.jsonl` 配）；量程 30 m；降采样体素 0.05 m、近处 1 m；ICP 最后的阈值 0.05 m；
`assume_planar_world` 不开（MOLA 的系是第一帧雷达系，RS-Airy 的 X 竖着，z 不是上）。

先验的参数（`pipelines/prior-from-simplemap.yaml`）里 `max_search_keyframes` 改成 4（MOLA 默认 3）：simplemap
的关键帧只有局部地图的三分之一左右（10-08 那张 163 对 456），照 3 重出的先验在另一趟录包上比原来差一点；
这个选项存在先验文件里，定位器载图时就用它（第三节）。

### 定位回放（先验就是狗定位用的那张图）

`d1max-loc replay`（MOLA 只定位 + 狗上同一份定位核心 + 代理同一份 `BridgeLocalizer`）。同一个先验同一个录包
重跑结果逐位相同。

| 录包 → 先验 | ICP 质量 p5 | 质量 < 0.9 的帧 | 代理信的时间 | 跟另一趟建图轨迹的位置差 p50 / p95 | MOLA 每帧 p95 |
|---|---|---|---|---|---|
| office-1 → office-1 原先验（MOLA 自己存的局部地图） | 0.998 | 0% | 99.6% | 同一趟，不比 | 22.6 ms |
| office-1 → office-1 回环后先验 | 0.998 | 0% | 99.6% | 同一趟，不比 | 29.0 ms |
| dual → office-1 原先验 | 0.955 | 2.4% | 94.9% | 4.6 / 7.4 cm（参照：dual 未回环的轨迹） | 25.9 ms |
| dual → office-1 只重出、不回环（`max_search_keyframes` 3） | 0.936 | 3.6% | 94.0% | 4.5 / 7.3 cm | 22.1 ms |
| dual → office-1 只重出、不回环（4） | 0.962 | 2.7% | 94.7% | 4.6 / 7.4 cm | 29.8 ms |
| dual → office-1 回环后先验（4） | 0.962 | 2.8% | 94.7% | 4.3 / 11.2 cm（参照：dual 回环后的轨迹） | 33.8 ms |
| office-1 → dual 原先验 | 0.842 | 8.7% | 84.0% | 4.0 / 8.0 cm（参照：office-1 未回环） | 25.6 ms |
| office-1 → dual 只重出、不回环（4） | 0.898 | 5.2% | 87.0% | 3.9 / 8.0 cm | 28.4 ms |
| office-1 → dual 回环后先验（4） | 0.896 | 5.4% | 86.9% | **2.5 / 5.7 cm**（参照：office-1 回环后） | 28.3 ms |
| office-2 → office-2 原先验 / 回环后先验 | 0.993 / 0.998 | 0.1% / 0% | 99.6% / 99.6% | 同一趟 | 24.4 / 28.8 ms |

读法：

- **回环本身不改变匹配得好不好**（「只重出」跟「回环后」质量、代理信的时间一样）；匹配好坏变的是「重出先验」那一步：
  照 MOLA 默认的 3 个关键帧比原先验差一点，改成 4 跟原先验持平或更好（`max_search_keyframes` 5：0.981 / 97.6%、
  每帧 p95 33 ms；6：0.986 / 99.6%、39 ms —— 更好但更费，没用）。代价：**MOLA 每帧多花 10–30%**（开发机 p95
  22–26 → 28–34 ms；Orin 上没量）。
- 两趟独立建图对得上对不上（没有真值，只能看两份图互相印证）：office-1 录包在 dual 图上定位，跟 office-1 自己的
  轨迹比，两边都不回环 4.0 / 8.0 cm，两边都回环 2.5 / 5.7 cm —— 回环让两趟独立的图更一致；反过来那组（dual 录包
  在 office-1 图上）p50 4.6 → 4.3、p95 7.4 → 11.2 cm，变差。所以只能说「不比原来差、有一点变好的迹象」，不能说
  定位更准了。
- 同一趟回放的「位置差」没列：回环后先验上定位出的轨迹跟按关键帧插值挪出来的轨迹差 p95 5 cm —— 这就是轨迹插值的
  精度（`coverage.json`、栅格里狗身走过的那条线用它，5 cm 够了）。

用到的东西都在开发机临时目录（不进仓库）：编好的工具、三份图回环前后的打包结果、墙的散布脚本、回放结果。
看过的图：office-1 / dual / office-2 回环前后的栅格 4 倍图、墙带点密度图、office-1 左墙和 dual 右上墙的
前后对照（1 cm、4–6 mm 一格）。

另外顺带看到：**站点预览跟开发机离线重建的这份是上下镜像的**（台阶状的墙、桌子的位置都对得上，但上下翻了），
没查原因 —— 可能是在线那份标「上」的方向（`frames.json` 的 `up`）跟离线这份相反，值得在狗上拿 `build.json`
的 `frames` 那句核一下。

## 四、上狗（arm64）

建图打包在狗上做（W09c2：`mapping start` → MOLA 在线建 → 停 → `d1max-map-build --reuse` 打包 → 上传），所以回环
工具要在狗上。几条路：

| 办法 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| **甲：在 Jetson 上编（推荐先这么试）** | 第一节的编法原样在狗上跑（装到 `/opt/d1max/loop-closure`）。要先确认狗上有：`git`、`cmake`、`g++`、`python3-colcon-common-extensions`、`libeigen3-dev`、`libtbb-dev`（可选）—— 开发机这些都有，狗上没核；ROS 的 MOLA / MRPT / GTSAM / mp2p_icp 包自带头文件和 CMake 配置，apt 装的那份就够 | 跟狗上的 MOLA / MRPT / GTSAM 版本天然对上 | 狗要能上 GitHub（不能的话把上面的源码在开发机上打成一个包拷过去，约 220 MB，其中 MRPT 源码只为了装 TCLAP 头文件）；Orin 上编估计 5–10 分钟（没量）；缺 dev 包就得在狗上 apt 装 |
| 乙：编一次，拷前缀 | 在一只狗（或 arm64 的 `ros:humble` 容器，开发机上用 qemu 跑）编好，把 `/opt/d1max/loop-closure`（3.3 MB）打成 tar 或 deb，别的狗解压到同一处 | 别的狗不用编译环境、不上网 | **只在 MOLA / MRPT / GTSAM / mp2p_icp 的 apt 版本跟编它那只完全一样时能用**（C++ 的 ABI）；狗上哪天升级了 MOLA 就得重编。打 deb 要列依赖：`ros-humble-gtsam`、`ros-humble-mola-*`（3.2）、`ros-humble-mp2p-icp`（2.14）、`ros-humble-mrpt-lib*`（2.15）、`ros-humble-mola-gtsam-factors`（2.4.2） |
| 丙：在站点主机上回环 | 狗把 `map.simplemap` + `traj.tum` 传给站点（办公室这种 100 MB 级；关键帧多的大场地几百 MB 到 GB），站点回环、出先验，再发回狗 | 狗上不装、不费算力；站点是 x86，开发机这套直接用 | 要改 W09c2 的流程（现在是狗上打包好再传，站点不碰原料）；栅格的真射线要读录包（在狗上，几个 GB），所以要么只在站点回环 + 出先验，栅格还在狗上画，要么把整个打包挪到站点；多一来一回的传输 |

建议：先按甲在 C40221 上装一次、量时间内存（第五节）；量下来可以，以后的狗按乙拷前缀（版本对得上的前提下）。
丙等到大场地真有需要、狗上算不过来再说。

狗上不用改配置：装在 `/opt/d1max/loop-closure` 就会被找到；要关就在代理的环境里加
`D1MAX_LOOP_CLOSURE=off`（或者不装）。W09c2 的「走完到图可用 ≤ 5 分钟」：开发机上这一步 6–9 s；Orin 上按慢
3–4 倍估 30 s 左右（没量）。大场地关键帧多，回环候选随之变多，时间会长不少（没数据）。

**狗上定位的代价**：用了回环，先验换成重出的那份，MOLA 每帧多 10–30%（第三节）；Orin 上定位本来就紧
（W34 的 3d.55），这一条必须在狗上量过再默认开。

## 五、真机 / 现场要验的

记在 `docs/庄园场景待真机测试.md` 3d.57–3d.58：

1. 狗上编（或拷）好工具，边走边建一圈（最好走大一点、回到起点）：`build.json` 的 `loop_closure` 是
   `used: true`、回环数、各步耗时、峰值内存；同一个 work 目录 `--loop-closure off` 再打一份，两张栅格、点云对比，
   看墙的双层少没少、有没有被拉歪的地方。
2. 在回环后的先验上定位：MOLA 每帧耗时（`traces.csv` 或诊断）、`dropped_frames_ratio`，跟原先验比；定位器、
   代理信不信。每帧多出来的那 10–30% 在 Orin 上吃不吃得消。

## 六、没验过的

- 狗上编译、运行（arm64、Orin 的时间和内存）—— 全部是开发机 x86 上的数字；
- 大场地、长路线、室外（漂移大、回环多的情况）—— 三份测试图都是 23–27 m 的办公室，漂移 5–24 cm；
- 错误回环：自动拦只拦得住离谱的（第三节「5 s 子图」那组就没拦住），大场地头几次要人看图；
- 前后雷达合并话题（`/d1max/merged_lidar`，W09i）建的图没试；
- 带 RTK（`rtk.jsonl`）的图：回环挪了轨迹，`geo.json` 的配准用的是挪过的轨迹，没有带 RTK 的数据验；
- 回环后先验上定位的 CPU 代价在 Orin 上的影响；
- 许可证（第一节）要不要买闭源许可，没定。
