## 问题（为什么做）

1. `release pack` 不打 `deploy/`，OTA（`POST /api/release/install` + `activate`）升上来的机器，`/etc/systemd/system/d1max-patrol.service` 永远是装机那天的版本：没有 `D1MAX_DATA_ROOT`（W01）、`StartLimitIntervalSec` 在错的段（W01c）。W01 只在启动时打一句警告。
2. 服务以 `User=robot` 跑，写 `/etc/systemd/system/`、`daemon-reload` 都要 root。
3. 同一个进程要发 `systemctl restart`/`reboot`。`真机待验证清单` 第 6 条一直悬着：默认 polkit 下 `robot` 多半发不出去，而 `_spawn_restart` 只 `Popen` 不看结果——界面显示「已重启」，机器一动没动。
4. OTA 路径上没人做 W01 的槽内数据迁移（只有 `install.sh` 7/7 做 stop → migrate → start）。

## 方案（设计文档里比较了四种，采用 A）

root 拥有的小助手 `/usr/local/sbin/d1max-privileged` + `/etc/sudoers.d/d1max` 一行白名单（`robot ALL=(root) NOPASSWD: /usr/local/sbin/d1max-privileged`）。助手四个子命令：`check`、`install-unit <版本名>`、`restart`（stop → 以 robot 跑 `release migrate-data` → start，与 `install.sh` 7/7 同一条路）、`reboot`。由 `install.sh` 装（基础件），**不随 OTA 更新自己**（它是提权面；改它重跑 `install.sh`）。

否决的：polkit 规则只解决重启不解决写单元；`ExecStartPre=+` 在自己启动过程中替换单元并 `daemon-reload`，systemd 行为不可靠；服务改 root 跑不可接受。

## 设计取舍（审核请重点看）

1. **为什么先装单元再切链。** 单元只引用 `current` 和几条稳定路径，新单元配老代码是安全的；反过来（链切了、单元没装上、或切了却重启不了）机器就挂在「在途」里等人——正是本工单要消灭的状态。所以 `ensure_can_restart` 和 `install_unit` 都放在 `activate()` 之前，失败 409 且一动没动。
2. **回滚不被单元拦。** 三条回滚路（人工、开机自检、CLI）都装回旧版单元，但失败只记一笔——回到能跑的代码比单元一致更要紧。
3. **助手是提权面，护栏挡的是「借单元变成 root」。** robot 已经能以 robot 跑任意代码，所以护栏不是防 robot 跑代码，而是防 `User=`/`ExecStartPre=+`/`EnvironmentFile`/`LD_PRELOAD`/能力集这些把 robot 的代码升成 root 的写法。不在白名单里的键一律拒。真机上 `robot` 本来就在 sudo 组（厂商出厂配置），这条护栏在今天的机器上是纵深防御；在客户按我们清单交付的机器上它是唯一一道。
4. **TOCTOU。** 内部评审前我自己发现：校验源再拷源之间 robot 能换文件。改为拷进 root 目录后校验拷贝再 `mv`。源上的 `-L`/`-f` 检查只为报错清楚，不是护栏。
5. **助手不随 OTA 更新。** 让一个 sudo 白名单脚本从 robot 可写的目录更新自己 = 把 root 送给 robot。它必须小而稳，改它重跑 `install.sh`。设计里写明。
6. **开发机 / W01b 之前装的机器退回现状。** 助手不在 → 单元不装（回 `skipped:` 并说怎么补）、重启走裸 `systemctl`。只有「助手在、sudo 不通」才是喊出来的错。
7. **数据迁移放在助手 `restart` 里而不是 `ExecStartPre`。** `Restart=always` 每次重试都会跑 `ExecStartPre`；迁移只该在 stop 之后、没人写槽时做一次，这跟 `install.sh` 7/7 是同一条路。整机 `reboot` 那条路上不迁移——开机后槽内数据仍在原名、prune 不删，下一次服务重启（任何一次 OTA）会搬。
8. **boot-guard 不动。** 开机前守卫回滚时没有 app 进程、单元已被 systemd 读入；新单元向后兼容，留到下次 `activate` 对齐。设计里写明。
9. **sudoers 不限参数**（`NOPASSWD: /usr/local/sbin/d1max-privileged` 允许任意参数）。参数安全全在脚本里：子命令只有四个，版本名过正则，测试模式参数在 root 下一律拒。

## 真机待验证（狗开机时做，都不动机器）

1. 重跑 `sudo bash deploy/install.sh <本版包>`（W01b 的助手和 sudoers 只有 `install.sh` 会装）；看 5/7 那一步没报错。
2. `sudo -u robot sudo -n /usr/local/sbin/d1max-privileged check; echo $?` → `0`。
3. `sudo -u robot sudo -n /usr/local/sbin/d1max-privileged install-unit <当前版本名>` → `unchanged`。
4. 用两个包演一次 OTA：`POST /api/release/install` 新包 → `POST /api/release/activate`；响应里 `unit` 是 `installed`；`systemctl cat d1max-patrol` 是新版包里那份；`systemctl show d1max-patrol -p ActiveEnterTimestamp` 变了（真重启了）；journal 里有「单元文件: installed」；`/var/lib/d1max` 出现搬过来的数据（如果槽里还有）。
5. `POST /api/release/rollback` → 响应 200，journal 里「退回 …,单元文件: installed|unchanged」。
6. 把 `/etc/sudoers.d/d1max` 临时改名再 `POST /api/release/activate`：应 409「重启命令发不出去」，链未动；改回后恢复。
