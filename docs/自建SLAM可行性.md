# 不用厂商 nav，自己跑 SLAM：能不能，怎么做

写于 2026-09-01，第一次现场之后。

> **2026-09-02 追记：现场走的是路线 A，而且当天就出了图。**
> 见 [`建图定位与巡检管线.md`](建图定位与巡检管线.md)。这不推翻下面对路线 B 的推荐 ——
> 现场用 A 是为了当天出结果，而第五节风险 1（话题名）和路线 A 的 2D 局限**两条都应验了**：
> 厂商 `/laser_scan` 用 Livox 窄 FOV + 图像分割，漏家具，只能改用速腾 `/front_lidar` 拍扁；
> 密集家具区 2D 匹配确实会退化。**家具级完整图仍然要走路线 B。**
> 另有一条这里没预料到的：**zenoh 传不了 latched 话题，AMCL 那条路是死的**（清单 #63）。

结论先说：**能，而且不是黑魔法 —— 厂商自己把这条路当成二次开发的正路写进了文档。**
但它是一条独立支线，不是第二卷的必经之路。下面把「能不能」「怎么做」「什么时候做」
分开讲，最后给一条现在就该做的动作。

---

## 一、为什么能：机器上该有的东西一件不缺

《SDK 开发指南》第四章把 Orin NX 上的传感器全部以**标准 ROS2 话题**暴露出来。
这不是我们从协议里逆出来的，是厂商写在文档里的接口：

| 东西 | 话题 | 类型 | 频率 / 备注 |
|------|------|------|------------|
| 前雷达点云 | `/front_lidar` | `sensor_msgs/PointCloud2` | 10 Hz，QoS `best_effort` |
| 后雷达点云 | `/rear_lidar` | `sensor_msgs/PointCloud2` | 10 Hz，QoS `best_effort` |
| 前雷达 IMU | `/front_lidar/imu` | `sensor_msgs/Imu` | 雷达自带 |
| 后雷达 IMU | `/rear_lidar/imu` | `sensor_msgs/Imu` | 雷达自带 |
| 车规级 IMU | `/imu_driver/imu_central` | `sensor_msgs/Imu` | **文档明说可能拿不到**，「涉及硬件改动，若无法获取请联系售后」 |
| 超声波 | `/uss_driver/uss_{left,right}/range` | `sensor_msgs/Range` | 近距补盲 |
| RTK | `/rtk_pvh` | 厂商自定义 | 室外才有意义 |
| 前后相机 | `/{front,rear}_camera/image_compressed` | 压缩图 | 来自 RK3588，不是 NX |

雷达是**前后各一个 96 线的 Airy**，装在机身 ±404.3 mm 处（2.10 节给了全部传感器
相对 BASE 原点的毫米级安装坐标 —— 这份表就是外参标定的起点，省掉了自己量的活）。

链路也是现成的：Orin NX 跑 ROS2 Humble + **zenoh** 中间件，`ROS_DOMAIN_ID=24`，
router 在 `tcp/192.168.168.100:7447`。笔记本装 `ros-humble-rmw-zenoh-cpp`、把 IP 设成
`192.168.168.xxx`（xxx 不能是 100/168/255）、改一行 router 配置，就能直接
`ros2 topic echo`、录 bag、开 rviz、跑自己的节点。见清单 #32。

**一句话：点云、IMU、外参、通信中间件，四件齐了。剩下的都是我们这边的活。**

## 二、缺的那一块：里程计，正好是我们今天刚做完的东西

SLAM 缺的不是传感器，是**位姿来源**。厂商没有文档化的 `/odom` 话题，也没说他们发不发
TF 树。这一块得我们自己接。

好消息是今天已经接好了一半。`motion/patrol_agent.cpp` 从 SDK 的 `OnMcData` 里拿到的
`MotionData`，本身就是一份腿式里程：

```
position[3]   世界系位置（米）
quat[4]       姿态，文档写的是 [w,x,y,z]
v_world[3] / v_body[3] / omega_body[3]
time_stamp    纳秒
```

`patrol_agent` 已经把它降频到 20 Hz、算好 yaw、以 `odom` 帧从 TCP 口吐出来。
再写一个几十行的 rclpy 节点，把这条 JSONL 流转成 `nav_msgs/Odometry` +
`odom→base_link` 的 TF，ROS2 那边就齐活了。

**但这份里程有两个没验过的假设**（清单 #51 / #52）：`position` 到底是不是可用的世界系
位置（会不会恒零、会不会重连清零），以及 `quat` 到底是不是 `[w,x,y,z]` —— 同一份头文件
里 `ImuData` 用的是 xyzw，顺序搞反了 yaw 会**错得看起来像对的**。

而且更根本的问题是：**四足的腿式里程漂得厉害**。脚打滑、上下台阶、原地转身，都会让它
偏。它适合当短时插值和安全兜底，不适合当建图的骨架。

这直接决定了下面选哪条技术路线。

## 三、两条路线，推荐第二条

### 路线 A：拍扁成 2D，`slam_toolbox` + Nav2

`pointcloud_to_laserscan` 把点云切一层压成 `/scan` → `slam_toolbox` 建 2D 栅格图 →
存图 → Nav2 用 AMCL 定位。

- **好处**：最省事，生态最成熟；产物是 2D 占据栅格图，和厂商 nav 的 PGM 图是同一个心智
  模型（他们的 `get_pgm_map` 就说明他们自己也是 2D 栅格那一套），第一卷做的地图/点位
  抽象基本能直接复用。
- **坏处**：**它要求有 odom TF**，也就是必须依赖上面那份没验过、而且会漂的腿式里程。
  四足的机身在走路时是持续俯仰晃动的，把 3D 点云拍成单层 `/scan` 会切出一堆假障碍
  （切到地面）或者漏掉真障碍（切到空中）。这不是调参能完全绕过去的。

### 路线 B（推荐）：先做 3D LIO，再投影成 2D 图

用 **FAST-LIO2**（或 Point-LIO）做前端：输入只要 `PointCloud2` + `Imu`，输出高频位姿
和 3D 点云地图。要闭环就在后面接 SC-PGO / interactive_slam。

- **好处**：**它根本不需要外部里程计。** 一步跨过 #51/#52 这两个没验过的假设，也跨过
  腿式里程漂移的问题 —— IMU 预积分本来就是干这个的。机身晃动由 IMU 建模，不会像拍扁
  成 2D 那样变成噪声。96 线雷达喂 LIO 是很舒服的输入。
- **代价**：要编一个 ROS2 包，要把雷达和 IMU 的外参、时间同步弄对。
- **产物**：3D 点云地图 → 用 `octomap` 或直接切高度带投影成 2D 栅格图给 Nav2。
  腿式里程降级成**交叉校验**（和第一卷定的真理源规则同一个思路：一个源做主，另一个只
  用来发现「两边对不上」）。

**推荐 B。** 理由是它把依赖压到最少：只依赖厂商已经文档化并且我们能直接 `echo` 验证的
两个话题，不依赖任何我们还没验过的东西。

**先只用前雷达。** 两个雷达合成一片点云需要准确外参 + 时间同步，是独立的一摊活；
前雷达单独跑 LIO 先把链路走通，合成留到后面。

## 四、怎么做：四个阶段，每一段都能独立验收

### 阶段 0：打通 ROS2 链路（半天，**不用动机器**）

> 这一段的逐步操作已经写成现场手册：[`R阶段-ROS2与建图手册.md`](R阶段-ROS2与建图手册.md)。


笔记本装 zenoh、配 IP、改 router 配置、`ros2 topic list` 能看到那几个话题、
`ros2 topic echo /front_lidar --once` 能出数据。

**然后录一包 bag：**

```bash
ros2 bag record /front_lidar /rear_lidar /front_lidar/imu /rear_lidar/imu \
                /imu_driver/imu_central /uss_driver/uss_left/range \
                /uss_driver/uss_right/range /tf /tf_static -o d1max-walk-01
```

录的时候让机器走一圈（遥控或 SDK 都行）。这一步零风险、只读、不改机器上任何东西。

### 阶段 1：离线跑通（PC 上，完全不碰机器）

拿 bag 在笔记本上跑 FAST-LIO2，调外参和时间同步，看轨迹和点云图对不对。
**所有算法调参都在这一步做完** —— 现场时间贵，机器更贵。

### 阶段 2：在线建图

把验好的配置搬到实时链路，走一圈存图。这时候要考虑跑在哪：

- **跑在笔记本上**（推荐起步）：不跟厂商栈抢 Orin 的算力，出问题拔网线就完事。
- 跑在 Orin NX 上：省了网络带宽（96 线 ×10 Hz 的原始点云不小），但要用
  `robot-launch` 停掉厂商的部分节点腾算力 —— 而停错节点可能连遥控都不能用。**别早做。**

### 阶段 3：定位 + Nav2，换掉 `NavBackend`

这一步的架构工作**第一卷已经做完了**。`NavBackend` 是个抽象口，现在的实现是走 WebSocket
的厂商实现；自建这条路就是再加一个 `Nav2NavBackend`，巡检任务那一层一行都不用改。
当初选「混合导航：先厂商、后自建」就是为了留这个口。

**但这里有一个非常具体、非常容易踩的坑：**

Nav2 输出的是 `/cmd_vel`（`geometry_msgs/Twist`），要经由旁路进程翻译成 SDK 的
`Move(lat, fwd, yaw)`。而现场实测（清单 #37/#38）：

> `Move` 的量是**百分比**不是 m/s；`fwd=0.11` 几乎不动，`fwd≈0.3~0.5` 才明显走。

也就是说 SDK 的 `Move` **有一个不小的死区**。Nav2 的控制器在接近目标时会自然把速度降到
0.05 m/s 这个量级做精细对准 —— **在 D1 Max 上这些指令会被静默吞掉，机器一动不动，
Nav2 却以为自己在走**。这不会报错，只会表现为「到不了点」。

处理办法：控制器的 `min_vel_x` / `min_speed_theta` 必须配在死区之上，或者把最后一段
改成离散脉冲（走一下、停一下、再看误差）。这条已经记进清单 #56（转向那一路的死区
一次都没量过，仿真里是按平移的量级猜的）。

## 五、风险清单：现场必须先确认的几件事

1. **话题名可能已经变了。** 固件更新记录里明写过一条「修改前后激光雷达 IP 地址及
   rostopic」。文档里的 `/front_lidar` 未必是当前固件上的名字，第一件事是
   `ros2 topic list`，不是照着文档写代码。
2. **点云里有没有逐点时间戳。** FAST-LIO2 靠它做运动去畸变。要看
   `ros2 topic echo /front_lidar --once` 里 `fields` 有没有 `time` / `t` /
   `offset_time` 这类字段。没有的话去畸变要另想办法，精度会掉。
3. **车规级 IMU 可能是坏的** —— 文档自己写了这句。备选是雷达自带的 IMU
   （`/front_lidar/imu`），但那个的噪声特性和标定质量是未知数。
4. **厂商 nav 栈会不会和我们抢。** 它自己也在用这两个雷达。同时跑两套的算力和 TF 冲突
   要现场看。
5. **zenoh 链路本身没验过**（#32），配置踩坑的可能性不小。
6. **电量**。#43：一天从 71% 掉到 17%，低电量还很可能是建图被拒（#42）的直接原因。
   录 bag 之前先看电量。

## 六、什么时候做：现在**不**切，但现在就该录 bag

第二卷的目标是定点拍照巡检。厂商的导航本身是通的 —— #42 被拒的是**建图**，不是导航。
所以自建 SLAM 是一条独立支线，乐观估计 1~2 周（阶段 0/1 各半天到一天，阶段 2/3 是大头），
不该插在第二卷前面。

反过来说，**厂商建图被拒、前置条件文档里一个字都没有**（#42），这本身就是自建 SLAM
最强的理由：如果建图这条路一直卡在厂商那边，我们就得有自己的图。

**所以现在就该做的只有一件事：下次去现场，录一包 bag 回来。**

录 bag 是只读的、零风险的、五分钟的事；而没有 bag，阶段 1 的所有离线工作就一天都开不了工。
这也是唯一一件**必须在机器旁边**才能做、其余全部可以在办公室做的事。
