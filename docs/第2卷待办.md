# 第 2 卷待办（第 1 卷有意留下的账）

这些不是遗漏，是第 1 卷收尾时**明确裁定"本卷不做"**的事项。每条写明：是什么、
为什么本卷不做、第 2 卷该怎么做、以及不做的代价。

裁定原文见 `第1卷决策记录.md`。

## 1. 测试时间预算已经贴到天花板

**现状（已经在越线，不是"余量小"）**：收尾时连采 6 次全量，同一棵树、同一台机器：

    88.36 / 88.53 / 88.76 / 89.12 / 92.75 / 93.45 秒     硬预算 90 秒

**六次里有两次越线**。这不是噪声边缘，是预算已经饱和：套件的墙钟时间由仿真器的
异步等待主导，机器负载一波动就过线。内环（`-m "not contract and not scenarios"`）
427 条 54.5~55.5 秒 / 预算 60 秒，仍宽裕。

第 1 卷交付时全量测试**全部通过、退出码 0**；越线的是项目自己定的时间预算，不是测试失败。

**本卷不做的理由**：预算是设计文档里的全局约束，第 1 卷执行期间我两次拒绝放宽它
（Task 16、Task 17），理由是当时的超支全部来自 `close()` 的那个缺陷。那个判断是对的 ——
缺陷修掉后，两条预算都不改一个数字就回到了线内。

**但收尾时的连采推翻了"回到线内"这个结论的稳定性**：单次测量看是 88.5 秒过线内，
连采 6 次才看出分布已经骑在 90 秒上。第 1 卷剩余的时间不足以做并行化改造，
所以留给第 2 卷 —— 但要说清楚：**这是"来不及做"，不是"不用做"。**

**第 2 卷怎么做**：抬预算，或者上 `pytest-xdist` 并行。
**明令禁止用"删测试"来达标** —— 这条预算的本意是"别让套件慢到没人肯跑"，
不是"套件里别放东西"。

**不做的代价（已经在发生）**：现在就已经有三分之一的运行越线。再加十几条走仿真器的测试，越线会变成常态，然后有人会想去删测试。

## 2. `NavConfig` 的 `close_timeout_s` 必须从 `connect_timeout_s` 里拆出来

**现状**：`close()` 用的关闭超时和连接超时共用一个配置项。终审修复轮把它从 3.0 降到 2.0，
是为了给 IMP-1 那条守 TCP 泄漏的回归测试拓宽检测余量（原本只有 7 毫秒）。

**本卷不做的理由**：拆配置项会改公开的 `NavConfig` 形状，属于接口变更，
不该在收尾轮里顺手做。

**第 2 卷怎么做**：`NavConfig` 里独立出 `close_timeout_s`，两个超时解耦。

**不做的代价（已知且已量化）**：IMP-1 那条测试**现在仍然抓不住**
"外层超时恰好等于 close_timeout"这个历史写法 —— 历史上真出过这个 bug（M4 那次的
`wait_for(ws.close(), ...)` 永久 TCP 泄漏）。解耦之前，这个形状复发时测试不会红。

## 3. 全局约束的措辞与 `tests/` 的既成约定不符

**现状**：设计文档写的是"标识符与日志键名英文"。`src/` 严格做到了（tokenize 全树复扫 0 处）；
但 `tests/` 里有 **90 处**中文测试函数名（`test_关闭时轮询器手上有已结清的在飞请求也必须立刻返回`
这种），是从 Task 1 起就形成的既成约定，可读性上是**加分**的。

**第 2 卷怎么做**：把约束原文改成 **"产品代码标识符与日志键名用英文"**，让文本对上实际。

**不做的代价**：下一个读约束的人会以为 `tests/` 那 90 处是违规，然后要么去大改测试名
（纯损失），要么开始怀疑约束本身没人执行（更糟）。

## 4. MIN-8：`EventEmitter[_E]` 的泛型契约只靠 docstring 约束

**现状**：子类必须调 `super().__init__()`、必须传对事件类型 —— 这些只写在 docstring 里，
没有任何静态检查兜底。

**本卷不做的理由**：正解是引入 mypy 或 pyright，那是工具链决定，超出第 1 卷范围。

**第 2 卷怎么做**：定工具链时把它纳进来。注意 Python 3.10 没有 PEP 695 泛型语法，
现有写法是 `typing.Generic` + `TypeVar`，类型检查器要按这个配。

## 5. MIN-10：`websockets>=13` 这个下界从未验证过

**现状**：`pyproject.toml` 写 `websockets>=13`，开发和测试全程用的是 **16.0**。
13.x 一次也没跑过。已在那一行旁边加了中文注释说明这件事。

**本卷不做的理由**：`>=13` 是设计文档的全局约束，而且新版 asyncio 接口
（`websockets.asyncio.server.serve` / `websockets.asyncio.client.connect`）确实是 13.0 落地的。
抬下界等于拿一条**未经用户确认的收紧**去换一个还没发生的问题。

**第 2 卷怎么做**：加一条 13.x 的 CI 矩阵真跑一遍。跑通就保持 `>=13`，跑不通再抬下界 ——
那时候是有证据的收紧，不是猜。

**不做的代价**：有人在 13.x 环境上装了这个包然后撞到没验证过的行为差异。

# app 这一轮（19 个任务）留下的账

**现状**：VLM 判读走 `ANTHROPIC_API_KEY`。没有密钥时每张照片落 `pending`，

**这一轮不做的理由**：工程版是手动触发的，现场大概率没外网。"没网也走得完"

**第 2 卷怎么做**：要么给判读排队、回到有网的地方补跑，要么上本地模型。
选哪条取决于现场到底有没有网 —— 现在还不知道，所以不猜。

**代价**：现场当场看不到模型的结论，只有人自己看图。

**现状**：判断建图子进程"起来了"靠匹配 stdout 的一行日志，那几个正则是照着

**第 2 卷怎么做**：拿 `runs/logs/*.log` 里真实的启动日志逐条核，对不上就改。

**代价**：模式对不上时 app 会一直等到超时，然后报"建图没起来"，而实际上它起来了。
这个错误方向是安全的（不会误以为在建图），但会让人以为链路坏了。

## 8. 雷达朝向 180° 只在待验证清单里挂着（#64）

**现状**：app 里**不做显示端修正**。摆歪的外参在显示端兜住，只会让下一个人
以为它是对的。

**第 2 卷怎么做**：`static_transform_publisher --yaw 3.14159` 重建图，从源头正过来。

**代价**：在改之前，app 上画出来的机器头朝向是反的。这条必须在现场用图之前解决。

## 9. `ip route` 不持久（#66）没折进 `field-agent.sh`

**现状**：机器重启或 WiFi 重连之后要手工重加那条路由，否则 Orin 不可达。
现在靠人记得。

**第 2 卷怎么做**：折进 `field-agent.sh` 的开场，或者做成 app 起飞检查的一项。

**代价**：每次现场开工都可能在这一步上耗十分钟，而症状（`/tf` 进不来）看起来像别的问题。

**现状**：全量 1288 条 215 秒。第 1 卷收尾时是 90 秒预算贴天花板，现在整整多了一倍多 ——

## 11. 手机端与狗之间那条 HTTP 契约，没有任何测试钉住

**现状**：`mobile/`（Flutter）与 `src/d1max_patrol/`（Python）是两棵独立的树 ——
各自的构建、各自的测试、零共享代码。耦合面只有一条 HTTP 契约，
`mobile/lib/model/robot.dart:52` 的 `defaultPort = 8095` 加 `baseUrl`。

**spec 已经盖住的部分**（不要重复造）：§8.4 把**服务器**当成契约测试的第三个 target，
同一份 `/api/*` 用例指向狗跑一遍、指向服务器跑一遍；§8.7 把**手机端自己**那三条
核心行为（摇杆吸附单轴、松手主动发停、视频掉线变灰）钉成离机纯逻辑测试。

**没盖住的正是中间那一段**：手机端**解析**的 JSON 形状，跟 `app/server.py` 实际
**吐出**的 JSON 形状，没有任何一条测试同时看着两边。Python 侧 1559 条测试全绿、
Dart 侧测试全绿，`server.py` 改一个字段名照样两边都不红 —— 红的地方在现场。

**今天还没出事的原因不是设计，是还没接上**：`mobile/lib` 一共 7 个 dart 文件，

（`registry.dart` 里那个 `GET /api/identity` 只出现在注释里）。遥控屏那一卷
一旦开始发请求，这条缝就开始承重。

**第 2 卷怎么做**：归「手机遥控屏」那份计划。最小做法是让狗那侧导出一份
接口样本（复用 §8.4 已经要建的那套 target 的输出），`mobile/test/` 拿它当
fixture 解一遍 —— 样本对不上就红。**不要为此起真机**，那会违反 §8.7。

**代价**：不做的话，「一套界面同时对得上狗和服务器」（§3.7 的地基）在手机这一侧
没有证据。而这类不一致的发现地点是客户现场，不是 CI。

## 12. spec 自身的四处措辞问题（终审带出来的）

「电量原点与起飞门槛」那一卷的终审在 spec 层面报了四条。**它们不是代码缺陷，
改代码解决不了**，但放着不管，下一个照字面读 spec 的人会做错事：

1. **§1.3 说原点「存进地图」，实现存的是 sidecar**（`<map_id>.home.json`）。
   实现是对的 —— 那个 yaml 是 slam_toolbox 生成的，重建图会原样覆盖，
   写进去等于写在沙滩上；sidecar 也躺在 `maps_dir` 里跟着地图一起被拷走。
   **该改的是 spec 那句话**，否则下一个人照字面又去改 yaml。
2. **§1.2 的出发线公式**被这一卷重读成「中止线 + 全程预计 × 1.5」，
   理由是 `route_length_m` 算的全程已经含回程。论证充分，但 spec 是权威 ——
   **这条重读要回写进 §1.2**，否则半年后有人按字面再加一份返航储备。
3. **§7.5 与 §7.6/§11 自相矛盾**：§7.5 字面是「认到外插盘时，禁止起飞」（任何盘），
   §7.6 与 §11 映射表是「`role != mirror` 就拒绝」。实现跟的是后者，是对的。
   **§7.5 那句该改成「认到非镜像盘时」。**
4. **§7.6 的 SN 绑定**（记 SN 是为了拦住把 A 狗的备份盘插到 B 狗上）
   在起飞门槛上原本没落地，已在那一卷的终审修复里补上。

**第 2 卷怎么做**：动 spec 之前先确认这四条的裁定仍然成立，然后一次改完并提交。

## 13. 标原点不校验图名，打错了照样 200

`app/server.py` 的 `_map_home_put` 只把 `map_id` 过一道 `_safe_id`（防路径穿越），
不问这张图存不存在。把图名打错一个字，接口回 200、盘上多出一个
`<打错的名字>.home.json`，人以为标上了 —— 真相要等起飞那一刻才露出来。

**飞行是安全的**：真跑那张图的时候 preflight 读不到原点，硬拦。所以这是「误导」
不是「危险」，不拦本卷合并。

**留到后面办的原因，是「哪个才算这张图存在」本身是个设计问题**：

- `mapping.list_maps()` 是本地 `*.posegraph` 的 glob；
- `server.py:1027` 那个 `/api/maps` 用的却是 `self._call(nav.list_maps)` —— 后端说了算。

两者按构造就会不一致（甲、乙两条路线各有各的图库）。而走后端那条要把这个端点
拖进 `_call` 和超时里，正好推翻 `_map_home_put` 文档里那段「文件读写不过桥」的
论证。**先定「图名的权威登记处是谁」，再回来改这个端点。**

## 14. `scan_or_unknown` 只接 `OSError`，而探针是公开 Protocol

`engine/removable.py:133` 的兜底只 `except OSError`。今天全仓只有两个
`RemovableProbe` 实现（`MountRootProbe` 和测试替身），都只抛 `OSError`，所以现在
接得住。但 `RemovableProbe` 是公开 Protocol —— 第三方实现（网络盘、厂商工具）抛
一个 `ValueError` 或自定义异常，整份七项检查报告就一项都写不出来，正是这个函数
存在的意义所在。

放宽到 `except Exception` 会撞 ruff `BLE001`，得连着写清楚为什么这里是「兜底边界」
而不是「懒得分类」。等真有第二个外部实现的时候一起办。

# 保留、基线与导出这一卷（8 个任务）留下的账

整卷终审提了 2 Critical / 7 Important / 8 Minor。其中 C1、I4、I6、I1、M2、M7 已在
`22f799e` 修掉。下面是**当时裁定不修**的，附裁定理由——理由不成立的那天，账就该还。

## 15. 盘况屏没有任何客户端在看（终审 C2）

`GET /api/storage` 是全仓唯一一个把删除预告落到盘上的地方，而 `static/` 和
`mobile/lib/` 里**没有一处调它**（grep 零命中）。于是在单机档下：预告台账永远是空的
→ `_deletable` 的 `first is None → False` → 一趟都删不掉 → 盘涨到 90% 之后
`storage.STOP` 永久拦住起飞。整条保留链在真机上是死的。

**引擎侧是对的**：不是先删再告诉你，而是没告诉你就一趟都不删。缺的是那一屏。

**留到「手机遥控屏」那一卷的原因**：本卷 8 个任务里没有任何一个是 UI 任务，硬塞一屏
进来会绕开那一卷已经定好的导航、状态和布局约定。**但这是那一卷的硬进入条件**，不是
可选项——那一卷的计划里必须有一个任务是这一屏，否则保留策略仍然是死的。

## 16. 导出包跟归档共用同一块盘（终审 I2 / I3 / I5 / I7）

`AppContext.exports` 是从 `runs_root.parent` 推出来的，所以：盘 88% 的时候要腾地方，
第一步是导出，而导出**先把包写到同一块盘上**——峰值用量不降反升，很可能在写 zip
的中途 ENOSPC。`ZIP_DEFLATED` 对已经压过的 JPEG 基本无效，一个包约等于原件大小。

**第 3 卷只答了一半。** 备份盘本身有了（`engine/backup.py`、四条 `/api/backup/*` 路由、
自动同步协程），但 `AppContext.exports` 仍然是从 `runs_root.parent` 推出来的——导出包
照旧写在跟归档同一块盘上。剩下的一半是「导出目标可以指向备份盘」或者「边算边发不落盘」，
两条都还没做。本卷把导出做成
「先落盘、再算哈希、客户端重算确认」是有意的——`ByteStream` 不带 `Content-Length`
且强制 `close_connection`，截断在 HTTP 层完全不可见，只有客户端自己重算的 sha256
能证明收全了。改成流式的时候这条不许丢。

## 17. 固定的 `.tmp` 名还剩四处，其中一处是活的

I6 只换了本卷点名的四处。剩下的：

- **`engine/mission.py:363` 的 `save_mission` 是活缺陷**——它由 `app/server.py:1036`
  从 HTTP 线程**直接调用**，而服务是 `ThreadingHTTPServer`。两个客户端同时保存同一个
  任务，能写出半截 yaml，现场丢的是整条路线。
- `archive.py:49`、`homing.py:91`、`judge.py:143` 目前只由引擎单线程写，暂时安全。

规矩已经有一份现成的了：`retention.unique_tmp(target)`，公开就是为了给这些地方用。

## 18. M2 的正确性靠调用顺序，没有机制保证

`forecast(..., noticed=...)` 里那个「台账缺席就取 `now`」之所以精确，是因为调用方
紧接着的 `write_notice` 记下的正是同一个 `now`。今天 `forecast` 和 `write_notice`
各只有一个调用点且相邻，所以成立。将来出现第二个调用点、顺序反了，文案会**多报七天**
——偏保守（催人早导出），且删除判据根本不经过 `forecast`，所以不会误删。

## 19. 没有「高水位触发」这个常数

只有 `SWEEP_TARGET_RATIO = 0.70`（删到哪儿为止）和 `storage.WARN/STOP = 0.80/0.90`
（提示与拦停）。**「涨到多少才开始删」没有常数。** 本卷靠人点一下盘况页触发，所以不需要；
将来「备份盘」或「服务器与值守」那一卷放一个常驻巡盘任务进来，第一件事就是找这个常数，
而现成最像的 `SWEEP_TARGET_RATIO` 是**错的那一个**——拿 0.70 当触发线等于每次出任务
都在删。加常驻巡盘的时候先补这个常数。

## 20. 「备份盘满了」只有一句话，没有 P2 通道

规格 §7.6 要求「备份盘满了不删旧的，报 **P2** 停同步」。第 3 卷把**行为**做齐了：
`plan_sync(...).full` 判满，`backup_notice(..., full=True)` 出一句 PUSH 级的话，
`/api/storage` 的 `backup` 块把它带出去，而且明说「不会删盘上的旧归档——那些常常是
唯一副本」。

**缺的是 P2 这个等级本身。** 这个仓里没有分级告警通道：`NoticeLevel` 只有
OK / NEUTRAL / PUSH 三档，而 P0/P1/P2 是规格里另一套词，没有任何代码认得。
今天「满了」和「落后 5 趟」在值守屏上长得一模一样，都是一块红。

做告警分级那一卷要一起解决的：谁定义 P0-P3、落在哪个数据结构上、`BackupNotice`
是并进去还是被它取代。**在那之前不要单独给备份盘发明一套 P2**——发明出来的那一套
和将来真正的那一套对不上，是比现在只有一句话更贵的债。

## 21. 没初始化的盘看不到容量（第 3 卷终审 I2 的残留）

`_backup_targets` 现在先确认 `marker_path(t.mount).is_file()`，不成立就把容量字段报成
`null`。这挡住了「一块刚被拔掉的盘把根文件系统的容量报成自己的」，但代价落在**这一屏
最主要的用途**上：客户插一块新盘进来准备初始化，屏上那一行没有容量,而人正是靠容量
决定要不要用这块盘。

**正确判据是 `os.path.ismount`**，三行就够。不在第 3 卷做的原因只有一个：**离机一行都
验不了** —— pytest 的 `tmp_path` 不是挂载点，写出来的测试只能证明我们把函数调对了，
证明不了判据本身成立。要跟真机清单第 1 条一起做。

**别退回原样。** 退回去就是拿根盘的容量冒充备份盘的容量，那比看不见更坏。

## 22. 弹出之后有个静默窗口

`eject()` 停同步、`sync`、回「可以拔了」，但**不在任何地方留下「刚弹出，别碰」的痕迹**。
第 3 卷新加的自动同步协程每 60 秒醒一次，它认盘只看标记文件——于是它完全可能在人看到
「可以拔了」之后半秒钟开始往同一块盘上写。

只在**换镜像盘**这一种场景成立（取走盘 `role != mirror`，自动同步不碰）。做值守或者
多盘管理那一卷时一起解决：弹出要留一个带时限的静默标记，自动同步认这个标记。

## 23. `/api/storage` 上一块坏盘理论上还能 500

不是第 3 卷引入的，是旧账。这条路由现在能扛住扫盘失败和单块盘的 `OSError`，但它调用
的那一串（`scan_runs`、`_disk`、`plan_sync`）里仍有几处没有逐个包 `OSError`，今天不炸
是因为被调方碰巧都不抛。一块半死不活的盘（读得动但会间歇 EIO）能让盘况屏整个 500 ——
而这正是唯一一个「盘出毛病时必须还能打开」的页面。

要做的时候一次做透：这条路由上每一个碰盘的调用都要能单独降级，而不是整条 500。

## 24. 落槽之后没有第二次哈希核对（第 4 卷终评 I-4 的另一半）

`release install` 落槽时算过一遍 `tree_sha256` 并跟 `release.json` 对账，但 `activate`
那一刻**不再核第二次**。装完到切过去之间那段时间里，槽里的东西如果被动过（人手改、
盘出错、半次失败的升级），我们看不出来。

之所以没顺手补上：跑起来的服务会往槽里写 `__pycache__/`，装机时又在槽里建了
`venv/`，pip 还可能留 `*.egg-info/`。要在 activate 时重算哈希，就得带一份排除名单，
而**带排除名单的哈希是一个更弱的哈希**——它守不住「有人往槽里塞了一个 .pyc」这种
坏法，反而给人一种守住了的错觉。

这是个规格层面的决定，不是实现层面的：要么规定「槽里只放不可变的源码，venv 和
缓存都挪到槽外」，要么明说「落槽之后不再校验，信任文件系统」。挑一个写进 §7.3，
再来做。

## 25. `_spawn_restart` 不看退出码（第 4 卷终评 I-5）

`app/server.py` 里起 `systemctl restart` / `systemctl reboot` 的那一段，起完就不管了。
真机上 `User=robot` 能不能在默认 polkit 下执行这两条命令**还没验证过**（已挂进
`真机待验证清单.md`）。如果不能，现在的表现是：日志里一行没有，人只看到「说要重启，
但什么都没发生」。

至少要把退出码读回来，非零时发一条 `release.restart_failed` 事件。真机核过 polkit
之后一起做。

## 26. `read_manifest` 的三条异常分支没有测试

`engine/release.py` 的 `read_manifest` 对 `ValueError`（JSON 坏了）、顶层不是 dict、
`schema` 不是整数这三种输入各有一条分支，一条都没测过。这三条都是「客户现场手改了
`release.json`」时会走到的路。

## 27. `POST /api/release/rollback` 缺一条 HTTP 层的 409 测试

engine 层「没有上一版可退」的行为测过了，但走 HTTP 那一路返回 409 的形状没有测试钉住。

## 28. `tests/app/test_api_release.py:125-127` 那次 `write_payload()` 是多余的

同一个夹具里前面已经写过一次，这三行删掉不影响任何断言。留着会让下一个读的人以为
这条用例依赖「写两次」。

## 29. `_check_results_wire` 跟 `_checks_wire` 是两份几乎一样的代码

`app/server.py:356` 和 `:366`。两者都把自检结果转成上线的字典，差别只在入参类型。
合成一个，或者说清楚为什么不能合。

## 30. CLI 层的 `GuardAction.REPAIRED` 分支没有测试

`boot_guard` 返回 `REPAIRED` 时 CLI 怎么打印、退什么码，没有测试。engine 层那一侧测过了。

## 31. `release` 子命令退 2，别的 CLI 子命令退 1

不一致。现场写脚本的人按 `$? -eq 1` 判失败会漏掉 release 这一路。统一成一个，或者
在 `docs/装机清单.md` 里写明白哪条退什么。

# 任务包与排程这一卷（11 个任务）留下的账

## 32. 打包器盖章时用的是非递归 glob

**现状**：`engine/bundle.py` 的 `_盖章`（打包器给每个任务重写规范形式、盖
`schema` 的那一步）用的是 `d.glob("*.json")`（`d` 是 `missions/` 目录），
只扫这一层。于是 `missions/sub/deep.json` 这种**嵌套**在子目录里的任务文件
既不经过 `parse_mission` 校验、也不被盖上 `schema`，就原样跟着
`shutil.copytree` 进了包 —— 打包器对它形同不存在。

`missions/` 目录本身并没有约定「只能放一层」，`verify_pure_data` 的四道闸
（纯数据）是递归 `os.walk` 的，会照样把嵌套文件里的后缀、可执行位等查一遍，
所以这不是「危险内容漏检」；漏掉的是**任务格式校验**和 **schema 盖章**这两
件事，两者都只发生在打包器这条路径上。

**顺带一个跨平台差异**：`Path.glob` 在 Windows 上大小写不敏感、在 Linux 上
大小写敏感。同一份源目录（比如 `Night.json` 和 `night.json` 并存）在两边
可能打出内容不同的包——这在开发机上永远测不出来，因为开发机就是 Windows。

**本卷不做的理由**：`missions/` 目前的约定就是「一个任务一个文件、都在这一
层」，改成递归扫描是给任务目录结构本身做设计决定（子目录算不算命名空间？
`mission` 字段要不要带路径？），这属于将来 schema 工作的范围，不该在打包器
这个 Task 里顺手定。

**将来怎么做**：定夺 `missions/` 是否允许子目录；如果允许，`_盖章` 换成
`d.rglob("*.json")` 并把大小写在两个平台上的行为写成一条测试钉住。

**不做的代价**：现在往包里塞一个嵌套任务文件，打包器不报错、也不盖章，
狗收到之后能不能正常跑这个任务全看运气；同一份源树在 Windows 和 Linux 两台
打包机上可能打出不一样的包，而没有任何告警会响。

## 33. `verify_pure_data()` 对着一个不存在的路径会静默放行

**现状**：`os.walk` 对一个不存在的目录不抛错，直接产出空序列，所以
`verify_pure_data(不存在的路径)` 会「通过」—— 那不是「干净」，是「没查」。
这一卷已经在两个调用点各自先确认路径存在（`build_bundle`：`if not
src.is_dir(): raise BundleError(...)`；`land`／收包校验同理），代码里也留了
注释指着这件事（`engine/bundle.py:405` 附近）。

**本卷不做的理由**：把「路径必须存在」塞进 `verify_pure_data()` 本身会改掉
Task 6 已经定下并测过的契约——那道闸的职责就是「查给定目录里的文件是不是
纯数据」，不是「确认这个目录存在」，两件事混在一起会让将来想单独测「目录
不存在时该怎么办」的人无从下手。

**将来怎么做**：如果 `verify_pure_data` 将来长出更多调用点，**新调用方必须
自己先确认路径存在**，不能假设这道闸会替它把关。要是这类调用点多到重复代码
明显，再考虑给这个函数加一个可选的「路径必须存在」参数，而不是改默认行为。

**不做的代价**：新调用点如果忘了先确认路径存在，会把「路径写错」误判成
「这里没有可疑文件」，而不是报错——这类 bug 的症状是「静默的假阴性」，
比崩溃更难发现。

## 34. 三道校验共用一个 `BundleError`，想区分只能匹配错误消息子串

**现状**：`parse_manifest`、`verify_pure_data`、`land` 等一整条链路上的校验
失败全部抛同一个 `BundleError`。Task 10 的 `POST /api/bundle/apply` 要把
「状态冲突（该回 409：换到一个退过的版本）」从「参数错（该回 400）」里挑出来，
用的办法是 `"退过的那一版" in str(exc)`——**靠匹配错误消息里的中文子串**来
分流 HTTP 状态码。

**这不是完全没有防护**：有一条专门的测试
（`test_退过的那一版从这条路也上不去`）盯着这个字符串，改了错误文案的措辞
这条测试就会红，不会悄无声息地把 409 错判成 400。但这仍然脆——分流逻辑和
错误文案耦合在一起，是两个不该耦合的东西。

**第 2 卷怎么做**：给 `BundleError` 加一个可判别的字段（比如 `kind:
Literal["conflict", "invalid", ...]`），路由层按字段分流，不再摸字符串。

**不做的代价**：现在测试兜着，代价是**将来**的——如果这条测试被改动或者
错误文案在不经过测试的地方（比如日志里另起一份措辞）被复制粘贴走样，分流
会悄悄失效，而失效的方向是把「换到一个已退过的版本」误判成普通参数错、
回错 HTTP 状态码（400 而不是 409）。**换版本身仍然会被 `apply_bundle` 拦住
——`BundleError` 照样会抛，客户端只是收到一个语义不对的状态码**，不是被
放行；但状态码错了，靠状态码分流重试逻辑的调用方（比如自动化脚本按 409
判断"这是状态冲突，不该无脑重试"）会被带偏。

## 35. §3.4「推送不打断正在跑的任务」整卷无人实现

**规格出处**：`docs/superpowers/specs/2026-09-06-商业化交付架构设计.md` §3.4
——「推送不打断正在跑的任务，新包在当前任务结束后生效」。第 5 卷计划的定夺 11
（`plans/2026-09-07-任务包与排程.md:144-146`）把 land／apply 拆成两步，正是为了
兑现这一条，并明写「换链是 `apply()`，**由调用方在『当前任务结束』这个时机
调**」。

**现状**：本卷唯一的调用方是 `POST /api/bundle/apply`
（`app/server.py` 的 `_bundle_apply`），它**完全不看有没有 run 在跑**，请求来了
就换链。定夺 11 交出去的那个义务，没有任何一个调用方接住——engine 这一侧
（`apply_bundle`）也不该接，它够不着 run 的状态（分层：`engine/` 不认识 app 的
`AppContext`）。

**第 5 卷全卷终评（F5）把它挑出来**，同一轮里改掉了 `docs/任务包格式.md` 那句
把它当既成事实写给客户的话，并留下「有任务在跑的时候别点 apply」这句实话。
**这一卷只做了『别说谎 + 记账』这两件事，功能没做。**

**将来该在哪一卷补**：**第 8 卷（值守与接管）**。理由是那一卷才是「谁在跑、
跑到哪儿了」这件事的主场——排程循环、自动回退扳机、停机指令都在那儿，
「有任务在跑就别换链」跟它们读的是同一份 run 状态。

**第 8 卷怎么做**：`_bundle_apply` 在换链之前查一次「现在有没有 run 在跑」，
有就回 409（**不是 400**：请求本身没毛病，是这台机器现在的状态不允许——跟
「退过的那一版」「没有 previous」在相邻路由上给的是同一个答案）。再往前一步是
「排到当前任务结束后自动换」，那需要一个能记住『待生效』意图的地方，属于第 8 卷
排程循环的设计，不是一个补丁。

**不做的代价**：值守员照着交付文档在任务跑到一半时点了 `apply`，狗脚下的
`current` 链当场被换掉。正在跑的那个 run 已经把任务读进内存了，所以它不会当场
崩；真正会咬人的是**跑完之后**——归档里那条 run 记的是哪一版包、下一轮排程读的
是哪一份 `schedule.yaml`，两者跨过了一次换链，事后对不上账。现在靠文档里那句
「有任务在跑的时候别点」兜着，**而文档兜不住手滑**。
