# 导航 V1 设计

- 2026-11-07 第 2 版，用户已批准开工；之后按批准时的要求补了 `plan` 协议细节（第 2 节）和人/车场景统计量的说明（第 1 节）。改了哪些见文末「修订记录」。
- V1 的范围是用户定的；这份文档写怎么做、先做哪个、拿什么验收。

## 目标

V1 = 经典导航 + 确定性的智能恢复。要做到四件事：

- 客户现场能连续跑；
- 遇到常见异常不傻住；
- 危险时一定停；
- 真过不去时能说清楚为什么。

学习型的东西放到 V2：3B 导航监督、强化学习局部规划、现场自动学习。

## V1 范围

```
出发前路线检查（Route Validator）
        ↓
Smac Lattice 全局规划
        ↓
MPPI 主控制器 ──没进展──→ 全局重规划 ──还不行──→ [备用控制器，候选 RPP，仿真决定要不要] ──还不行──→ 停 + 报原因 + 等人接管
        ↓
安全守卫：SAFE / SLOW / STOP + 遮挡限速
        ↓
紧急停（确定性，不依赖上面任何一层）
```

外加：

- 卡住和打转检测；
- 结构化失败原因；
- 仿真放行门槛；
- 8–12 小时连续巡逻测试。

**不进 V1**：

- 3B 导航监督；
- 强化学习局部规划；
- TEB；
- DWB（除非仿真证明明显有用）；
- 多模型决策；
- 现场自动学习；
- 复杂人群社交导航。

## 车身尺寸：只有这一套口径

代码、报告、现场阈值都用这三层，常数只在一处定义（`nexwar_contract`），别处引用，不再各写各的「车宽」。

| 层 | 尺寸（长 × 宽） | 是什么 | 谁用 |
|---|---|---|---|
| 物理车身 | 0.93 × 0.48 m | D1 Max 实际外廓 | 仿真判「真实碰撞」 |
| + 基础安全余量 0.05 m/边 | 1.03 × 0.58 m | 守卫、Nav2 footprint 现在用的 | 守卫扫过区、Nav2 代价地图 |
| + 路线检查余量 0.20 m/边 | 1.43 × 0.98 m | 出发前路线检查用的 | Route Validator |

- **有效车身 = 物理车身 + 基础安全余量 + 路线检查余量。**
- **0.98 m 只是「直通道」的最小宽度。** 转弯要多宽，看有效车身沿路线扫过的面积，不是一个数。
- 路线检查余量 0.20 m 是 D1 Max 的临时值。以后按当时的定位质量加上定位误差。

| 1 | 安全 | 仿真 + 真机，测试样本中观测到的真实碰撞 = 0，人/车场景尤其要 0。5 cm 余量侵入单独统计，不跟真撞混在一起 |
| 2 | 完成率 | 在 Validator 判为可行的场景里，**整个系统自动完成 ≥ 95%**：MPPI 直接到 + 重规划后到 + 备用控制器救回来，三者合计。人工介入不算自动完成 |
| 3 | 不可通行 | 在 Validator 判为不可行的场景里（太窄、目标贴墙、死胡同、目标被永久占住）：正确识别、安全停下、讲清原因，正确拒绝率达标 |

| 5 | 可观测 | 每次失败都带一个结构化原因码（第 5 节），不能只报「navigation failed」 |

### 场景怎么分「该过」和「该拒」

**不按通道宽度分**：1.0 m 直道和 1.0 m L 弯不是一回事，1.0 m 的 L 弯本来就可能几何上过不去。

仿真里每个场景先用**几何判定器**判一次：

- 在真实地图上用有效车身做 (x, y, 朝向) 全搜索，判断几何上能不能从起点到终点。
- 它跟 Validator 是**两套独立的实现**：Validator 只检查 Smac 给出的那一条路线，判定器搜索所有可能的位姿。这样才能测出 Validator 有没有误判。

| 判定器结果 | 要考的指标 |
|---|---|
| 可行 | Validator 误拒率 < 2%；系统自动完成率 ≥ 95% |
| 不可行 | Validator 正确拒绝率达标；测试样本中真实碰撞 = 0 |

## 1. 安全守卫：D 方案 + 遮挡限速（一起做，POC 前 P0）

两部分是同一个守卫设计，**不分开上线**。只上 D、不上遮挡限速，就等于明知道它处理不了从车缝冲出来的人。

按障碍分三类处理：

| 类别 | 判据 | 处理 |
|---|---|---|
| 地图上的墙 | 挡住的格子离地图墙 ≤ 0.2 m（墙不会动） | **SLOW**：余量跟速度挂钩（0.2 m/s 时多留 0.05 m，0.6 m/s 以上多留 0.3 m）。先按原速查；不行再把前进和转向按同一比例压到 0.3、0.2 m/s 各查一遍，哪档过得去走哪档，走的还是 Nav2 算的那条弯 |
| 看得见的地图外物体 | 人、车、地图上没有的箱子 | **STOP**：按全余量查，也就是往前推「延迟 + 刹停距离 + 0.3 m」 |
| 看不见、可能冒出东西的区域 | 雷达视野里被停着的车、柱子、墙角挡住视线的阴影 | **遮挡限速**：主动限速，保证从阴影里冒出来的东西够刹得住 |

另外：

- 先按全余量查，没挡 → **SAFE**，原样放行。
- 蠕行速度最低 0.2 m/s。真机前进命令低于 0.13 m/s 只踏步不走，0.15 离这个死区太近。

**遮挡限速（新）。** 仿真数据：A 组在人/车场景里撞了 3/200 次。3 次进到 5 cm 时，守卫都还在发 0.3 m/s 前进，也就是根本没看见。做法：

- 沿前进方向找「挡视线的边」：地图上的车、柱子、墙角，加上感知到的停着的障碍。
- 估计边后面冒出东西的最坏情况：人 1.5 m/s、车 2 m/s，再加上感知延迟。
- 按冒出点到机身的距离，算出能刹住的最大速度，作为上限。

先在仿真里试两种算法，取在人/车场景里碰撞最少、对通过率影响最小的那种：

- 按旁边障碍离机身的距离分档限速；
- 按「看不见的那段距离」算刹停速度。

**已实现（2026-11-07，分支 nav-v1-guard）：** `nav2_nav._occ_cap`，E1 / E2 都在，`OCC_ALGO` 切换（仿真比完定默认）；结果并进「看得清就快」的上限，也送给 Nav2 当限速。开工时定的两处（用户可改）：

1. **机身两侧的盲区不算阴影。** C40221 实测雷达视野是锥形（obs-3f4：机头外 ±0.6 m，往外每米加宽 0.9 m），机头两侧 1 m 内永远看不见。把它当阴影，真机就永远压在蠕行：越慢越看不见，出不来。盲区照旧归守卫，按「看不见当挡」处理（上表原来把盲带写在第三类里，改了）。阴影只算视野锥里、却看不见的格子。仿真用的是整个前半球视野，所以仿真结果对视野锥里的阴影照样有效。
2. **最近 2 秒里见过的格子不算阴影。** 再久，人就可能走进去了。

**验收**：

1. 按真碰才判停重跑 B/D，看 D 本身的「必须通过」（`runs/nav-sweep-phys-1107`，正在跑）。
2. 加上遮挡限速后，人/车场景每组 40 个种子：测试样本中真实碰撞 = 0；人/车 < 5 cm 的次数比 D 少。
3. 遮挡限速对「判定器可行」场景完成率的影响 < 3 个百分点。

**40 次只是 POC 的回归门槛，不代表安全统计已经充分。** V1 商业发布前，人/车冲出这类高风险动态场景要扩到几百到上千次参数扫描，扫这些参数：

- 行人速度、车辆速度；
- 遮挡距离、出现时机；
- 延迟：300 ms 上下扰动；
- 机器人自身速度。

## 2. Route Validator

### 职责边界

代理不直接碰 ROS。Nav2 一侧照旧由 nav2bridge 隔离（W47 的边界）：

```
代理（Route Validator）
  ↓ plan 请求（只规划，不走）
nav2bridge
  ↓ ComputePathToPose 动作
Nav2 规划器
  ↑ 路线 + 规划结果
nav2bridge
  ↑ plan_result（路线点、成功否、原因）
代理（Route Validator）
```

- 代理拿到路线之后的几何检查是纯 Python，不依赖 ROS，单测好写。

### 协议（`nexwar_contract.navbridge`，协议号加一）

```
plan        {req_id, start?: [x, y, yaw], goal: [x, y, yaw]}
plan_result {req_id, ok, poses: [[x, y, yaw], ...], reason}
```

- **两条通道分开，不混用**：
  - 执行导航照旧走 `goal → path → cmd → goal_state`；
  - 只规划不走的请求单独走 `plan → plan_result`。
- **`req_id` 独立于导航的 `goal_id`**：plan 请求不影响正在执行的导航，也不出现在 `goal_state` 里。
- **`poses` 必须带 Smac 给出的 yaw。** 不能用相邻两点的连线方向代替：倒车段路径切线方向跟机器人朝向相反；原地转、小半径转弯时，位置几乎不变而朝向在变。
- **不经过现在给站点画路线用的抽稀**（`path` 报文每 0.2 m 留一个点、最多 256 点、只有 [x, y]）。`plan_result` 原样转 Smac 的位姿。
- **长度上限**：先定 5000 个位姿，按 Smac 的 2.5 cm 分辨率约 125 m。超长的报 `reason: "too_long"`，不截断，以后需要再分段传。
- `start` 不给就用机器人当前位姿。
- 代理侧 Validator 自己把位姿插值到 ≤ 5 cm 一个再扫，朝向按最短角插值。

### V1.0（POC 前）：代理每段出发前做

1. 发 `plan`，拿到 Smac 规划出的路线（已经按车身方向规划）。规划失败就直接报 `goal_unreachable`，不再往下查。
2. 沿路线每 5 cm 放一个「物理车身 + 基础安全余量」的矩形（1.03 × 0.58），每边再按余量 m 往外扩，查跟地图墙碰不碰。
3. 用二分法求出能通过的最大余量 m*。m* < 0.20 m 就拒绝出发，原因码 `route_too_narrow`，并报出最窄的那一处，例如：「(12.3, 4.5) 这处转角，按 Validator 余量需要约 1.08 m 净宽，当前路线只有 0.96 m，无法安全通过」。
4. 目标点本身：有效车身放不下、离墙太近，或原地没有转身的空间 → `goal_too_close_to_wall`，说明里写清是哪一种。

### V1.1（POC 后）

站点编辑任务、放航点时就做同样的检查，在地图上标出不合格的点，不等派到现场才发现。

### 验收（按几何判定器分场景）

- 判定器可行的场景：误拒率 < 2%。
- 判定器不可行的场景：正确拒绝率 > 50/60。现在只有 33/60，而且那只是过不去，不是主动拒绝。

## 3. 恢复链和备用控制器

目标顺序：

```
MPPI → 没进展 → 全局重规划 → 清代价地图 → 短后退 0.3 m → 再试 → [备用控制器] → 停 + 报原因
```

- 行为树里已经有重规划、清代价地图、后退，缺的是「换控制器」这一级。
- Nav2 Humble 支持在控制器服务里挂多个控制器，行为树按 `controller_id` 选用。

**备用控制器候选：RPP。** 它跟 MPPI 的行为特性不同：

| | RPP | MPPI |
|---|---|---|
| 方式 | 按前瞻点跟线 | 采样优化 |
| 调速和碰撞检查 | 按曲率调速，带自己的碰撞检查 | — |

RPP 在窄弯处可能更稳，也可能根本救不回来。所以 RPP 只是**候选**，靠仿真决定进不进 V1：

1. 仿真加一组「MPPI 主 + RPP 备用」，跟只有 MPPI 比，看判定器可行场景的完成率。
2. RPP 的速度、前瞻距离在仿真里调，要考虑真机低速死区（0.13 m/s）。
3. **提升不明显就不进正式恢复链**，V1 只保留重规划和后退。

DWB 跟 MPPI 一样是采样式的，预期收益小，V1 不评估。

## 4. 卡住和打转检测

已有：

- 30 秒没向目标靠近、也没挪窝 → 报「被挡」；
- Nav2 20 秒不给速度 → 重发目标。

要补：

- **打转**：10 秒里朝向来回反转 ≥ 4 次，而且离目标的距离没变小。
- **长时间没进展**：保留 30 秒那条判据，但不再只报警，要触发恢复链的下一级。
- 每一级恢复都记一条事件：级别、用了多久、成没成。这样就能统计「MPPI 直接到 X%、重规划后到 Y%、备用控制器救回 Z%」，也就是商业发布门槛 2 要的数。

## 5. 事件和失败原因码

分两类，不让同一件事报两个互相竞争的码。

**事件**：过程中发生、不代表任务失败。照旧发事件，可以发很多次。

| 事件 | 含义 |
|---|---|
| `guard_emergency_stop` | 守卫一次瞬时安全动作：这一拍叫停了 |
| `nav_blocked` / `nav_unblocked` | 被挡住、解除（已有） |
| `recovery_step` | 恢复链走到哪一级、结果如何（新） |

**失败原因码**：任务这一段最终失败时，只报一个。

| 码 | 什么时候报 | 操作员该做什么 | 现在的出处 |
|---|---|---|---|
| `route_too_narrow` | 出发前检查：路线太窄 | 改路线，或在地图上标不可通行 | 新 |
| `goal_too_close_to_wall` | 目标点放不下有效车身，或原地转不开 | 把航点挪开 | 新 |
| `goal_occupied` | 目标点被东西占住（感知看得见） | 把东西挪开再派 | `_nav2_failed`：occupied |
| `goal_unreachable` | 规划器找不到路（地图上就不通） | 查地图、禁行区 | `_nav2_failed`：stuck；`plan_result` 失败 |
| `dynamic_obstacle_blocked` | 人、车、地图外的箱子一直挡着，等过时限，任务失败 | 去现场看是什么挡住了 | `_watch_progress` + 守卫记录的挡住原因 |
| `robot_trapped` | 机身前后都被挡、脚下被判成障碍 | 把机器人挪开或遥控出来 | `_nav2_failed`：trapped / lethal |
| `controller_stalled` | 恢复链走完了还是没进展，包括打转 | 遥控接管 | `_watch_progress`、`_watch_stall` |
| `localization_unreliable` | 定位质量差、跳变，不敢走 | 重新定位 | 定位器健康状态 |
| `sensor_lost` | 雷达或障碍数据断了 | 查雷达、重启感知 | 守卫的「障碍数据」原因 |
| `nav2_plan_failed` | Nav2 报失败，但细分不出原因（兜底） | 看日志；这个码出现多了说明分类还要补 | `_nav2_failed` 兜底分支 |

- `guard_emergency_stop` 只当事件，不当失败码。被动态障碍挡到超时才失败的，报 `dynamic_obstacle_blocked`。
- 事件和任务结果都带「码 + 中文说明 + 位置」。站点、手机按码显示，并给出处理建议。

## 6. 仿真放行门槛和长时间测试

- **几何判定器**：对场景库里每个场景，用有效车身做 (x, y, 朝向) 全搜索，判可行 / 不可行，结果写进场景描述。
- **放行门槛**：
  - 固定场景库：现在 33 个，再加卡住、贴墙、死胡同等不可通行类；
  - 每个场景跑 10 个种子，人/车场景 40 个；
  - 按 REPORT_SPEC.md 出报告，按上面两个门槛自动判 PASS / FAIL；
  - 整轮在台式机上大约 1.5–2 小时。
- **长时间测试**：

## 修订记录

**第 2 版（2026-11-07，按用户审核）：**

1. **车身尺寸统一成三层。** 有效车身 = 物理车身 + 基础安全余量 + 路线检查余量；0.98 m 只是直通道的最小宽度。第 1 版写「物理车身外扩 0.2 m」，算出来是 0.88 m，跟 0.98 m 对不上。
2. **删掉「≥ 1.0 m 必须通过」。** 改成按几何判定器分可行 / 不可行，各自考核。
3. **Route Validator 走 nav2bridge 拿路线。** 代理不直接碰 ROS。
4. **遮挡限速升为 POC 前 P0，跟 D 一起做。**
5. **RPP 改成候选，靠仿真决定进不进 V1。**
6. **原因码拆开**：`goal_occupied` 和 `goal_unreachable` 分开；`guard_emergency_stop` 改成事件，失败码用 `dynamic_obstacle_blocked`。
7. **门槛拆成 11/17 POC 候选门槛和 V1 商业发布门槛。** 碰撞写成「测试样本中观测到的真实碰撞 = 0」。

**批准时补充（2026-11-07）：**

- **`plan` / `plan_result` 单独一条通道。** 用独立的 `req_id`；路线保留 Smac 的原始 [x, y, yaw]，不复用画图用的抽稀 `path`。
