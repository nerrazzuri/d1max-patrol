## I1 · 授权失效以后，人一直在场就不再报 P1

原来「这一回」只记一个「看见过」，授权在场和报过 P1 不分；人一直在，就一直被挡在「看见过」外面。

- `person_sightings` 多一列 `kind`，库结构 52：
  - `'p1'`：这一回报过 P1；
  - `'authorized'`：这一回只记了授权在场的 P3。
- **每拍重核**：记成 `authorized` 的这一回，人还在、布防中、没在驱离，就按**当前**的授权、**当前**的可靠位置再核一遍。下面三种情况，**补报一次 P1**（标题注「授权已不适用」），并在同一个事务里把这一回改成 `'p1'`：
  - 授权到期或被删了；
  - 狗走出授权区；
  - 位置说不清了。
- 报过 P1 的这一回照旧去重，不会反复报。
- 补报写在库里：pending 表和 `kind` 在同一个事务。所以站点重启以后照样补报；告警台暂时报不出去，下一拍会接着报。

## I2 · 首单派狗失败后，补派绕过授权

补派（`_promote_follower`）原来只复查布防和可达性。现在补派跟首次派狗走同一套出动资格判断，也按当前防区核授权：授权在场时，同防区等着补派的事件都记成 `authorized`，结果也会推送出去，不派狗、不占狗。

## I3 · 定位不可靠时，仍按旧位置套用防区授权

`_zone` 只认**可靠的现在位置**，两条都要满足：
- 狗报告定位正常（`status.ready.loc_ok`）；
- 站点按**自己的钟**，在 `stale_ms` 以内收到过它的位置（`dispatcher.telemetry_at`；不用跨机器的时间戳）。

定位丢了、位置停更了，就按「说不清在哪个防区」处理，只认全站授权。跟 I1 合在一起：授权在场的这一回如果失去了位置依据，下一拍就补报 P1。

## I4 · 网页登录可被跨站表单换成攻击者的账号

`web: true` 的登录（会种 cookie）也必须满足两条：
- 带 `X-D1Max-Web: 1`；
- `Content-Type` 是 `application/json`。

别的网站的表单设不了自定义头，也发不了 JSON（要预检，而站点不答应跨域）。检查在建会话、种 cookie **之前**，拒的时候回 403、不带 `Set-Cookie`。手机、命令行的 Bearer 登录不受影响。

## I5 · 站点断网后，网页继续显示旧的健康状态

- 网页记下最后一次核心数据（狗、告警）拿成功的时刻，以及从什么时候开始拿不到。拿不到，或者超过 6 秒没拿到新的，就算**过期**。
- 过期的时候：
  - 顶栏下面常驻一条琥珀色提示：「与站点的连接中断，画面上的数据停在 hh:mm:ss，可能已经过期」；
  - 顶栏计数显示「未知: ?」，不再显示「没有待处理的报警」；
  - 每只狗的状态显示「未知」，电量、任务不显示；
  - 报警队列标题写「报警状态未知（最后更新 hh:mm:ss）」。
- 旧数据留着，并标明时刻。「全部急停」等安全操作照样能按。
- **部分接口失败**：驱离接口这一次没拿到，记成「说不清」（`null`），报警画面写「驱离状态未知」，不当成「没有驱离」。
- 重新拿到数据，提示自动消失。

## M1 · 静态目录里的符号链接能读到目录外的文件

先解析出真实路径（`resolve(strict=True)`），确认还在 `web/` 里面才给。`index.html` 也查。

# PR #105 复查（FIX-THEN-APPROVE，还剩 1 条 Important）与修复

> 复查报告：`../reviews/2026-10-11-B-stage-PR105-recheck.md`。I2、I3、I4、I5、M1 通过；I1 新版新建的记录通过，旧库迁移有 R1。

## R1 · 51 → 52 升级把旧的授权 P3 当成了已报 P1

老版本里，「报过 P1」和「只记了授权 P3」写进 `person_sightings` 的是同样的两列。补列时我用了缺省值 `'p1'`，等于无凭无据地认定它们都报过 P1。结果是：升级之前那一回如果只记了授权，升级以后授权没了、人还在，永远不会补报。

修法：补 `kind` 这一列时**按证据分类**（`SiteDB._migrate_sighting_kind`）。

- **记成 `'p1'`**：这一回有 `dog_sees_person` 的证据。两种都算：
  - 告警表里有这只狗的这种告警，而且最后一次触发不早于这一回开始；
  - 这条 P1 还在待报表里。
- **记成 `'authorized'`**：没有证据。下一拍就会按当前的授权和可靠位置重核：授权还在就不动；不在了就补报一次 P1。
- **判错的代价**：最多多报一条 P1（会被 15 分钟的聚合窗口吸收），不会漏报。
- **原子性**：补列和分类在同一个事务里（`BEGIN IMMEDIATE`），中途断了不会留下「全是 p1」的半截状态。
- 新建表的缺省值不变，新代码每次写入都明确给出 `kind`。

## 测试

- **旧库升级，这一回只记过授权 P3**（把表真的变回 51 版的两列，再用当前的 `SiteDB` 打开，走真的迁移）：
  - 分「P3 已发出去」和「P3 还在待报」两种情况；
  - 升级时授权已经删了、人一直在：迁移后是 `authorized`；
  - 还没 tick 又重启一次，意图不丢；
  - 连跑三拍，P1 **只补报一次**，记录变成 `p1`。
- **旧库升级，这一回真报过 P1**：迁移后是 `p1`。
  - P1 已经进了告警表：不再报。
  - P1 还在待报表：照常补发一次，不多发。
- **外审的两条迁移复现**：不再成立（迁移后是 `authorized`，不是 `p1`）；外审另外 7 条正向检查通过。
- **突变**：4 条全抓住（不分类、不看告警表、不看待报表、全当成授权）。

# PR #106 复查（FIX-THEN-APPROVE，还剩 1 条 Important）与修复

> 复查报告：`../reviews/2026-10-11-B-stage-PR106-recheck.md`。直接从 51 版升级已经修好；**51 → PR #105（52）→ PR #106** 这条路径仍然漏报。

## R1（第二轮）· 已经被 PR #105 升到 52 版的错标记录没有修复

PR #106 只在「缺 `kind` 列」的时候才分类。可是 PR #105 已经把列补上了（全标成 `'p1'`），版本也写成了 52，所以装上 PR #106 以后修复根本不跑。

修法：改成**一次性修复迁移**，库结构版本提到 53（`SiteDB._migrate_sighting_kind`）。

- **什么时候跑**：库里记的版本在 53 以前，**不管 `kind` 列在不在**。新建的库不跑。
- **怎么分类**：把标成 `'p1'` 的记录按证据核一遍（证据判据跟上一轮一样）：
  - 有 `dog_sees_person` 的证据（告警表或待报表）→ 留着 `'p1'`；
  - 没有证据 → 改成 `'authorized'`，下一拍按当前授权重核。
- **只跑一次**：补列（缺的话）、分类、把版本写成 53，三件事在同一个事务里。之后启动看到版本 ≥ 53，就不再重判。

没有另设完成标记，直接用版本号。上一稿用过单独的标记，外审的复现把它暴露了：那个库是先用当前代码建的，标记已经在了，再把表和版本改回旧样子，修复就被跳过。版本号不会有这种对不上的情况。
