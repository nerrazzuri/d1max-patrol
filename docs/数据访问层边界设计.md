# 站点数据访问层的边界（设计稿）

> RC 加固 H12（决策 56）：**只设计，不重构全库**。数字是 2026-10-12 在 master 上量的。
> 要回答的是：以后做热备（要把写过的东西送到另一台）、再以后也许换数据库，现在的代码要守住哪几条线，才不用到时候把三百多处 SQL 重写一遍。

## 1. 现在是什么样

| 量 | 数 |
|---|---|
| 站点模块 | 62 个，其中 41 个里有 SQL |
| 发 SQL 的地方 | 约 355 处 |
| 表 | 52 张 |
| 只有一个模块写的表 | 46 张 |
| 不止一个模块写的表 | 6 张（见第 4 节） |

好的地方（已经是事实，要守住）：

- **所有读写都从一个口子过**：`SiteDB.tx()`（一次事务：加锁、`BEGIN IMMEDIATE`、出错回滚）和 `SiteDB.query()`。一个连接、一把锁。没有哪个模块自己另开连接往库里写。
- **跨模块的事在同一个事务里做**靠把事务对象传过去（比如告警写库的同一个事务里排推送）。这是「先落盘再动作」那几条外审结论的基础。
- **SQL 里没有不确定的东西**：没有 `datetime('now')`、`random()`、`CURRENT_TIMESTAMP`。时间都是程序算好当参数传进去的。同一串语句在另一台机器上重放，结果一样。
- 库结构只在一处定义、一处升级（`db.py`）。

不好的地方：

- SQL 散在 41 个模块里，没有「仓储」这一层；每个模块直接拼 SQL。
- 用了 SQLite 的方言：`INSERT OR REPLACE / OR IGNORE`（27 处）、`ON CONFLICT … DO UPDATE`（16 处）、`json_extract`（4 处）、`AUTOINCREMENT`、`PRAGMA`、在线备份接口。
- 5 个模块直接 `import sqlite3`（见第 3 节）。
- 6 张表有不止一个模块在写。

## 2. 三条线，一条一条来

**第一条线（现在就守）：口子只有一个。** 业务模块不 `import sqlite3`，不自己开连接；读写只走 `SiteDB`。只读的工具（清点、自检、恢复后的校验）可以用只读方式另开，名单写死。

**第二条线（做热备之前做）：在口子上记「写过什么」。** `SiteDB.tx()` 提交成功时，把这次事务里执行过的写语句和参数、连同一个只增的位置号，交给一个可以挂的钩子。热备的复制就挂在这儿：

- 业务模块一行都不用改；
- 因为 SQL 是确定的（见上），备机按位置号顺序重放就得到一样的库；
- 位置号连续不连续，就是「备机缺没缺」；
- 设计稿《热备与HA设计》里那三样要同步的（P1 告警、驱离会话、命令意图），是在提交时等钩子说「备机收到了」，也在这儿。

这条线要先补一个前提：**自增主键不能靠各自的库去编**。两台库各自 `AUTOINCREMENT`，重放时序号一样没问题；但将来只要有一处不是按顺序重放（比如挑着同步），就会对不上。所以重放必须是「全量、按序」，写进复制的规矩里。

**第三条线（真要换数据库时才做）：一张表一个主人，方言收进主人里。** 那时候把每张表的 SQL 收进它的主人模块，别的模块只调主人的函数；`OR REPLACE`、`ON CONFLICT`、`json_extract` 在主人里换成新库的写法。现在不做，但**现在不许再把线踩乱**：新加的表只许一个模块写。

明确不做：不上 ORM；不为了「整齐」把现有 355 处搬一遍；不为了将来可能换库现在就写两套 SQL。

## 3. 谁可以直接碰 sqlite3

| 模块 | 为什么 | 以后 |
|---|---|---|
| `db.py` | 就是那个口子 | 留 |
| `backup.py`、`restore.py` | 在线备份、恢复后只读校验、演练时开临时库 | 留；热备做完以后备份改成从备机做 |
| `inventory.py`、`selfcheck.py` | 从外面只读地看一眼（服务可能没起、不许顺手升库） | 留，必须只读 |
| `incidents.py` | 只用来接 `sqlite3.IntegrityError`（撞了唯一键） | 改成 `SiteDB` 给一个自己的异常，不让业务模块认识驱动 |

## 4. 不止一个模块写的 6 张表

| 表 | 谁在写 | 是不是问题 |
|---|---|---|
| `meta` | `db`、`backup`、`health`、`main` | 键值表，各写各的键。不是问题；规矩是一个键一个主人 |
| `runs`、`run_photos` | `evidence`（收证据）、`runs`（标留着）、`privacy`（按要求删） | 删除要跟证据文件一起做，放在 `privacy` 里有道理。第三条线时把删的 SQL 收进 `evidence`，`privacy` 调它 |
| `push_devices` | `push`（登记）、`accounts`（退出登录、停用时删） | 外审要求「撤权和登记在同一个库里串行」，所以 `accounts` 在自己的事务里直接删。第三条线时改成 `accounts` 在事务里调 `push` 的函数 |
| `pending_alerts` | `pending_alerts`、`deterrence` | 同上：驱离在自己的事务里记一笔待报的告警。改成调函数 |
| `enroll_claims` | `provision`、`registry` | 吊销狗时顺手作废开通码。改成调函数 |

都是「为了同一个事务」才跨过去写的。办法也都一样：主人给一个**接事务对象**的函数，别人在自己的事务里调它（`push.enqueue(tx, …)` 已经是这么做的）。

## 5. 读的方向

读别人的表的模块：`reports`（日报，读 4 张）、`standby`、`push`、`modes`（各 3 张）、`api`、`health`、`deterrence` 等。读不影响复制，只影响换库时要改的面。第三条线时，报表这类跨很多表的读集中在 `reports` 一处，是合适的；`api.py` 里那 3 处直接查库的挪到对应的主人里。

## 6. 现在就加的看门测试（不改业务代码）

`packages/site-node/tests/test_site_dal_boundary.py`，把上面量出来的现状钉成基线，**只许变好不许变坏**：

1. 直接 `import sqlite3` 的模块就是第 3 节那几个，多一个就红。
2. SQL 字符串里不许出现 `datetime('now')`、`random()`、`CURRENT_TIMESTAMP` 这类不确定的函数（第二条线的前提）。
3. 不止一个模块写的表就是第 4 节那 6 张、写它们的就是那几个模块；新表只许一个模块写，老表不许多出新的写入方。
4. 库只从 `SiteDB` 一个地方打开写连接。

## 7. 顺序

1. 现在：第 6 节的看门测试（这一单做了）。

3. 定了要换数据库：第三条线，一张表一张表收。
