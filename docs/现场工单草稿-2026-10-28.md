# 2026-10-29 现场查出的问题（工单草稿，收工后按台账下一个号开）

不在现场改代码。每条写清现象、证据、建议怎么改。

## 1. 停定位器时它自己 abort，systemd 记成 failed（3z.13 ❌）

- 现象：`sudo systemctl stop d1max-localizer` → `Active: failed (Result: signal)`。人员检测、感知同样停法都是 `inactive (dead)`。
- 证据（狗上 journal，11:12:26）：主进程收 SIGTERM 后打 `terminate called without an active exception` → `code=killed, status=6/ABRT`；systemd 接着 `Killing process … (lidar_odom) with signal SIGKILL`。没有 Python Traceback。日志 `runs/field-logs/3z13-20261029.log`。
- 猜测：主进程里有个 C++ 层的 `std::thread` 析构时还 joinable（rclpy / MOLA 绑定那层），收 SIGTERM 退出时没先 join。
- 建议：收 SIGTERM 时先停 MOLA 子进程、关 ROS 节点、join 线程再退；补一个「stop 后是 inactive」的部署测试。

## 2. 「被撞」误报：站起 / 趴下没避开，站着不动也报（3r.5 ❌、3r.2）

- 现象：
  - 11:29:16 我们自己发 `lie`，趴下那一秒报「机器人被撞了一下(3.74 g)」（10-26 趴下没报）。
  - 11:17:37 狗站着不动、用户确认没人碰，报 1.59 g。
- 代码：`packages/robot-agent/src/d1max_agent/force.py` 判 bump 只看 `shock_g >= bump_g`（缺省 1.5）和冷却时间，**不看是不是正在执行我们自己发的姿态动作**。
- 建议：
  1. 发 stand / lie / 切步态之后几秒内（到运动状态稳定为止）不判 bump。
  2. `bump_g` 用 C–F 段录下的 shock 峰值定（3r.2），站立微调的 1.6 g 不该报。

## 3. site.json 里 video.fps 写错时只给一整段 Traceback（3z.10 ◐）

- 现象：写 `"fps": "15"` → 站点起不来，最后一行写清了「video.fps 要是 1–30 之间的数，现在是 '15'」，但前面是一整段 Python Traceback。
- 建议：启动时配置错误统一捕获，只打一行说明、退出码非 0（跟其他配置错误一样）。

## 4. 1.15 的测法过时

- 现象：`d1max speed --x 0` 现在是 `d1max speed 0`；这条走厂家导航接口（ws://192.168.144.100:10010），速度 0 不在本机拦，会真发给厂家导航。
- 建议：改测法（或在 CLI 本机先拦 0），再定这一项要不要留。

## 5. 狗的钟不准，视频推流命令被拒（现场已绕过）

- 现象：狗慢 24.5 s；站点推流命令有效期 30 s，被狗按过期拒，网页「画面丢了、重连中」。狗上 chrony 指竞品板子 192.168.168.19，对不上。
- 现场：停 chrony、笔记本每 5 分钟推钟（收工还原）。
- 建议：隧道拓扑下也要有对时办法（比如代理经 MQTT 校钟，或者把站点主机放到狗能直接到的网段）；钟差大时网页直接说「狗的钟差 N 秒」，不要只显示画面丢了。

## 6. 10-26 清理重装把人员检测的 onnxruntime 一起清掉了（现场已装回）

## 7. 旁路跑在 Orin 上（用户要求）—— 产品化要补的

- 现场：`/etc/systemd/system/d1max-field-sidecar.service` + `/home/robot/d1max-motion/`（源码 + SDK aarch64 库，Orin 上编）。第一版单元缺 `runs/` 目录、撞 systemd 起停次数上限，开机那几秒修好才抢到窗口。
- 建议：发布包带旁路的服务单元（`StartLimitIntervalSec=0`、`ExecStartPre` 建目录、日志走 journal），装机脚本按角色装；以后跑在 3588 上同一套。

## 8. 「没加密」报警只报一次，处理掉以后再也不提醒（3p.9）

- 现象：`evidence_plain` 10-13 报过；今天清旧报警时处理掉了，狗的状态没变（还是明文），站点之后不再报。
- 代码：`evidence.py` `_plain()` 第一次看到 `sealed: false` 就记进 `evidence_plain` 表、报一次；表里有就不再报，直到狗报 `sealed: true`。
- 建议：被人处理掉以后隔一段时间（比如每天）还没修就再提醒；或者这条不许直接「处理」，只能「搁置到某天」。

## 9. 狗的证书 10 天后到期（运维，不是缺陷）

- 站点 11:01 报 `cert_expiring`：C40221、C40221L 的证书还有 10 天（约 11-07）。10-08 enroll 时给的 30 天。
- 要做：到期前续签（`d1max-site enroll … --days N` 重新发证书包，拷到狗上 `/etc/d1max/tls/`，重启代理）。

## 10. 设错位置后定位器自己回对了，代理却一直不信（3z.18 ◐）

- 现象：设错 3 m 后代理按里程判「人给的位置跟定位器稳住的地方差 3.0 m：请重新设位置」，一直不可信；定位器那边 σ 回到 0.1（真实位置匹配得好）。期望的「点云套图：定位器给的 … 多半锁错了，按那里重定位」没出现。
- 建议：人给的位置跟定位器稳住的位置冲突时，拿点云在两处各套一次图，哪处贴合度高信哪处（全局重定位那套代码已经有），而不是只能等人。

## 11. 站点显示的「定位质量」是 1−2σ，不是 ICP 质量

- 现象：站点 /api/robots 的 loc.quality 一直 0.8（σ 下限 0.1 换算），原始 ICP 质量 0.94 看不到。3f.17 要靠在狗上订 `/lidar_odometry/pose_quality`。
- 建议：能力或定位状态里把原始 ICP 质量（或近 3 s 低于 LOWQ_Q 的占比）也报上来，网页定位历史里显示。

## 12. 旁路「控制权丢了…救不回来」的日志说重了

- 现象：手持遥控器接管时旁路打这句，实际遥控松手后它自己拿回了控制权。
- 建议：改成「控制权被别的主控拿走（遥控器 / 上装）；对方放开后会自动拿回，拿不回才要重启 RK3588」。

## 13. 定位历史的原因被 σ 小步刷屏（3z.6 小毛病）

- 现象：盖雷达那一段原因「…雷达被挡住了…;后来:在按最后的位置重定位;后来:定位偏差可能到 1.5 m;后来:1.3 m;后来:1.2 m;后来:1.1 m;…」，只是数字变也接一句。
- 建议：`loc_history` 接「后来」时，只是数字不同的同一类原因合并成「定位偏差可能到 1.5→0.7 m」。

## 14. 挪的方向不查实时障碍：终点在障碍正后方时永远往前挪、不退（3z.1 ❌，阻断）

- 现象：C1 第 4 次，方块前停下、重规划找到绕行路，但「转向被看不见的格子挡住：先往前挪 1.3 m」每次都选往前、被方块挡，20 s 放弃，循环到整趟中止；一次都没往后退。
- 代码：`planned_nav._pick_creep()` 的 `_can_creep(here, 1)` 只查静态地图和区域；终点在障碍后面时往前挪「顺路」（离路径 ≤ 0.4 m）→ 返回 +1。
- 建议：往前挪那一段也要过实时障碍层（临时格、扫过区）；前方被挡就选往后退。
- 往后退同样：13:05 回原点时狗朝 −137°（斜对玻璃、航空箱），选「先往后退 1.3 m」，退 0.2 m 就被挡（扫过区有挡 2 处）→ 定位重置 → 30 s 中止。用户指出：朝 −90° 时身后是通道才有空位。往后退也要先查实时障碍和地图，退不了就别选；或者先原地转到身后有空的朝向。补回放测试：正前方 1 m 有临时障碍、终点在它后面 1 m。

## 15. 原地转身时定位跳 → 自动重定位 → 停 30 s；σ 大时禁行区加宽把终点盖住就中止（阻断）

- 现象：今天每一趟转身（往前挪完要转、朝终点转）都出现：定位器判「跳了」→ 代理 `reset()` 请定位器在最后可信位置重定位（σ 1.0）→ 狗原地等稳定期；C1 第 5 次这时禁行区按 σ 加宽 0.5 m，终点 (3.3, −2.6) 被玻璃侧硬墙盖住 → replan goal_blocked → 整趟中止。
- 不是算力：12:20 起 MOLA 0 丢帧、CPU 空闲 55%（厂家进程已暂停）。
- 12:34 录包复现：原地左转约 405°（朝向对得上），第 5 s 代理「定位器跟里程对不上（位移差 0.34 m）」触发 → 是代理的里程对照，不是定位器的跳判据；包 `turn-123414`。
- 要查：原地转时是 MOLA 位置漂了 0.34 m 还是里程（`--fwd-offset 0.10` 等换算）把转身算成了平移；转身时里程对照的阈值要不要放宽；也查转身时 MOLA 位姿的跳动量 vs 定位器的跳动判据（MAX_TURN_RPS 2.0、JUMP_MARGIN）；10-08 `rot-150934` 录包同类。建议现场录一段原地转身的包带回台式机。
- 另外：σ 暂时变大引起的 goal_blocked 不该直接中止整趟，应该等 σ 降下来再规划。E5 巡检同样：12:45:06 p1、p2 都 goal_blocked（展台侧硬墙按 σ 加宽盖住两点）→ retry_then_skip 两点都跳 → 整趟中止，几秒后 σ 就回到 0.1。窄通道里所有派单都会撞上。
- 还有：每趟起步朝向差几度就「先往前挪 1.3 m」，之后调方向就转身 → 触发上面的跳。

## 16. 被手持遥控器（或任何绕开代理的方式）开进禁行区，站点不报 P1

- 建议：代理空闲时也按定位每拍查一次「在不在禁行区」（有可信定位时），在里面就报一次 P1（跟区域变了时同一条）。

## 17. 起步两侧看不见 + 第一个点在 1.45 m 内 + 身后退不了 → 原地卡死、20 s 放弃

- 现象：12:57 E5 从起点 (2.58, 1.14) 派 office-line：「被挡：扫过区有挡 0 处、看不见 116 处」，没往前挪（p1 只在 1.4 m 外，往前挪 1.3 m 会冲过点），也没往后退（身后不到 1 m 是墙）→ 20 s 放弃这一段，重试照样卡。

- 建议：离点很近时允许「往前挪到点上为止」（挪的距离取 min(CREEP_M, along)），两侧看过了就到点；或者原地小幅左右摆头把两侧扫一遍。

## 18. 真狗上航点拍照动作一定失败（功能没接）

- 现象：12:58:56 E5 在 p1「点位 p1 没到：没有配 'front' 这路相机的取流」。
- 代码：`robot-agent/main.py` `--hal d1max` 分支 `media = None  # RTSP 取图归后面的工单` —— 拍照动作在真狗上没有取图来源；实时画面、录像走的是 VideoPusher/Recorder，另一条路。

## 19. 自动重定位后的稳定期（σ 1.5、20–25 s+）和引擎「定位重置后 30 s 不收敛就中止」撞车

- 现象：E5 第 2、3 次都是「定位重置后 30s 仍未收敛」中止；定位器那边点云套图早就对得上（0.66–0.68），只是还在 RELOC_SETTLE_S 稳定期里 σ 给 1.5。今天量：盖雷达恢复 23 s，转身自动重定位 15–35 s。
- 建议：两个时间对齐（引擎等的时间 > 稳定期 + 余量），或者点云套图核对对得上时提前结束稳定期。
- 连带：bump 误报又出现一次（13:02:25 走路时 1.61 g），见工单 2。

## 20. 原点在障碍膨胀区里：回原点永远被拒

- 现象：v3 原点 (−0.268, −0.295) 离最近的地图障碍 (−0.40, −0.89) 0.61 m，规划要 ≥ 0.62（半径 0.52 + 余量 0.05 + 格子取整）→ goal_blocked；离它 0.11 m 的 (−0.30, −0.19) 才能去。

- 建议：标原点时站点按同一套规划检查「这个点去得了吗」，去不了当场说；回原点 / 待命点时终点被挡就找最近的能去的点（≤ 0.3 m）。
