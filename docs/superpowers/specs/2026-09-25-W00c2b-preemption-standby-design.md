# W00c2b · 抢占与待命点 —— 设计稿

日期：2026-09-25 · 工单：W00c2b（M，依赖 W00c2a；吸收 W14 的「高优先级打断巡逻」「多待命点」）
状态：**按推荐（用户 2026-09-25 授权连续推进：「把整个 W00 跑完再给外审，都按你推荐的来」）**。三个决定都取推荐项。

## 0. 事实

- **抢占的机制在代理里已经有了**（W00）：新命令与正在跑的任务抢同一资源时，**严格更高**的优先级把旧的以 `preempted` 收尾再起新的；相等或更低回 `rejected(busy)`。`priority` 是任意整数，负数合法。
- **站点现在没有优先级规则**：排程派的 `patrol` 用排程条目的 `priority`（默认 0），站点 API 的 `goto` 让请求体随便填 `priority` —— 登录的人填 1000 就能打断一切，包括将来的事件派遣。
- **没有待命点**：任务结束狗停在最后一个点。老系统只有一个 `home`（`/api/maps/<id>/home`，狗上）；庄园方案要多个待命点（充电位、门岗、制高点）。
- 狗的遥测报位姿（`MapPose`），站点目前没订遥测。

## 1. 决定一：优先级由站点按任务来源定，代理只比数字

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | 站点一张表：回待命点 `-10` < 排程巡检 `10 + clamp(条目 priority, 0, 39)`（10–49）< 人手动派单 `60` < 外部事件派遣 `80`（W00c2c）；`90+` 留给安全类。API 不再收请求体里的 `priority`。代理不变 |
| B | 让代理按任务类型定优先级。换一种来源就要改狗上的代码，且站点才知道「这是谁派的」 |

## 2. 决定二：被打断的巡检怎么办

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | 记 `preempted`（排程账的 `result`），**不自动续跑**。续跑要知道从哪个点接着走、那一轮是否还在窗口里，留给后面 |
| B | 高优先级任务结束后从被打断的航点续跑 |

## 3. 决定三：待命点

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | 站点给每台狗登记若干个命名待命点（地图、x、y、yaw），其中一个是**默认**。站点派的任务（排程巡检、手动派单）**正常完成（`task_done`）**后，站点自动给这台狗派一条回默认待命点的 `goto`（优先级 `-10`，task_id 以 `standby-` 开头）。回待命点本身结束后不再回；被抢占（`task_preempted`）不回——抢占它的那一趟结束后会回。**被人 abort、或失败（急停、丢定位、安全裁定）不回**，狗停在原地等人（内部评审改的）。待命点记着地图与版本，对不上不回。排程执行器把「正在回待命点」看成空闲（可被任何任务抢占） |
| B | 回离当前位置最近的待命点。要订遥测、算距离；而待命点多半就是充电位，回哪一个应当是确定的 |

## 4. 形状

- `site-node`：`priorities.py`（那张表）；`standby.py`（`standby_points` 表、`StandbyManager`：登记、默认、任务结束自动回）；`dispatcher.busy()` 忽略 `standby-` 开头的任务；API `GET/POST /api/robots/<id>/standby`、`POST /api/robots/<id>/standby/return`（手动回）；CLI `d1max-site standby <robot> <name> --map M --pose x,y,yaw [--default]`；`serve` 挂上 `StandbyManager`。
- 契约、代理不改。

## 5. 验收

- 排程巡检跑到一半，人手动派 `goto`（60）→ 巡检 `preempted`、排程账 `result = preempted`、goto 跑完 → 自动回默认待命点。
- 请求体里的 `priority` 不起作用（填 1000 也按 60 派）。
- 回待命点途中排程到点 → 排程巡检照派、把回程抢占。
- 没有默认待命点 → 不回，也不报错。
