## 问题

W09a 做好了代理这一头：本机桥、定位质量（新鲜、σ、跳变、跟里程交叉校验）、重定位与换先验的请求。另一头 —— 狗上真正算位置的
定位器 —— 还没有。工单：ROS 2 侧节点，在先验地图上做点云匹配（推荐 MOLA 只定位模式），加跳变检测，经本机桥给代理；拿已有的室内
录包离线回放出指标。

## 探路结论（2026-09-26/27，开发机，只读录包）

录包：9 月 19 日下午 coverage2（整层一圈，先验用）、coverage（同一地点另一次）；9 月 21 日智元展厅 newdog2（先验用）。calib 是标
IMU 外参录的（原地转、俯仰），不用来测定位；newdog-cov 雷达盖子没开、点全是 NaN，不用。

1. **MOLA 只定位模式在建过图的地方跟得住。** 先验 = 建图时存下的雷达里程计局部地图（`MOLA_SAVE_MM`，关掉「删远处关键帧」）；
   只定位 = `MOLA_MAPPING_ENABLED=false` + `MOLA_LOAD_MM`（命令行要先加载 `libmola_metric_maps.so`）。coverage 放到 coverage2 的
   先验上、初值对：前 100 s 定位出来的路程跟独立建图一致；开发机上每帧 33–42 ms（10 Hz 雷达的预算是 100 ms）。
2. **初值必须给，而且要大致对。** 初值差 7 m、90° 全程乱跳（450 s「走」了 2 km）。初值偏 0.5–3 m 或 15–30° 几秒内收敛到同一条
   轨迹；**偏 45°、或另一方向偏 2 m 时，带着约 2.5 m 的偏差、ICP 质量分还很高地跑了将近一分钟才对上** —— 这段时间里谁也看不出它错。
3. **走出建过图的范围就乱跳，质量分不一定掉**（coverage 100–130 s：狗走进 coverage2 没去过的地方，30 s 里跳了 60 次，其中 10 s
   质量分还在 0.89 以上）；走回有图的地方自己又对上。
4. **一帧没有有效点的点云就让 MOLA 永久停摆**（报 `ESTIMATED_OBSERVATION_RADIUS` 未定义，之后「丢掉进来的观测」、再也不出位姿）。
   雷达盖子没开、雷达刚起来都会这样。
5. **坐标系**：雷达原始系 X 朝上；MOLA 的位姿、先验都在「建图起点那一刻的雷达系」里。给代理的是平面位姿，要一个「重力对齐」的
   变换（从建图轨迹估：雷达的「上」取平均）和「朝前」的方向。
6. 先验不小：一层楼 530 MB（coverage2）、150 MB（newdog2）；只定位时内存约 1.6 GB。体素化压缩归 W09c。
7. newdog2「前半段建图、后半段定位」那一组误差很大（17 m），更可能是切分或初值取错了，**没有定论**，留给正式的回放工具复查。

## 决定（都按推荐）

1. **节点 = 纯 Python 的核心 + 一层薄的 ROS 适配**，新包 `packages/localizer`（`d1max_localizer`，只依赖 `d1max_contract`；ROS 的
   部分单独一个模块，只在狗上、回放集成测试里 import）：
   - `frames.py`：MOLA 系的三维位姿 ↔ 地图平面位姿（`x, y, yaw`）。参数 `frames.json` 跟先验放在一起：重力对齐的旋转、平面原点、
     「朝前」是雷达的哪根轴、雷达相对狗身中心的水平偏移（按 URDF 取）、建图时雷达的平均高度（重定位时反算三维初值用）。
     `d1max-loc calibrate` 从建图轨迹算出前三项（「上」= 雷达 X 轴的平均；「朝前」= 狗走动时速度方向在雷达系里的平均）。
   - `core.py`（定位核心，纯函数式状态机，测试不要 ROS）：进 —— 一帧点云到了（只要时刻）、MOLA 给了一帧估计（时间戳、三维位姿、
     ICP 质量、MOLA 当前的搜索窗口）、先验换好了没有、重定位请求、每拍的时钟；出 —— 给代理的 `pose`（平面位姿、σ、来源、`jump`、
     `reloc_id`、`meas_age_ms`、`stamp_ns` = 那一帧点云的时间）与 `status`。规则见第 3 条。
   - `client.py`（本机桥的客户端，asyncio）：连代理的 `loc.sock`、`hello`、断了 1 s 后重连、每秒心跳、序号；`set_prior` 与
     `relocalize` **当场回「收下没有」**（W09a 契约：回复要快），真正的活交给后端做，进度走 `status`。
   - `mola.py`（ROS 适配，只在狗上跑）：见第 2 条。入口 `d1max-localizer`。
2. **MOLA 由节点当子进程管**（不另起 systemd 单元、不要 root）：
   - 换先验 = 带新的 `MOLA_LOAD_MM` 重启 MOLA 子进程（不用 `MapLoad` 服务：重启语义清楚，也顺带清掉 MOLA 的内部状态）；
   - 重定位 = 调 MOLA 的 `RelocalizeNearPose` 服务（初值 = 人给的平面位姿经 `frames.json` 反算成三维，σ 照给）；
   - **看门**：点云在来、MOLA 1 s 不出位姿 → 报 `lost`「定位程序卡住了」并重启 MOLA（重启后等重定位，见下）；点云 1 s 没来 →
     `lost`「雷达没数据」（不重启 MOLA —— 探路结论 4：开盖子、雷达起来之后才有数据）；重启有退避（1、2、4… 最多 30 s）。
   - 点云只订阅来计时刻：用 rclpy 的原始订阅（不反序列化 2.7 MB 的点云，只读消息头里的时间戳）。
   - MOLA 输出的位姿、ICP 质量、搜索窗口从哪个话题拿（`nav_msgs/Odometry` + `/diagnostics`，或 MOLA 的调试输出），**实现时先在
     一段录包上用 ROS 跑通再定**，写进报告；核心只认第 1 条的「一帧估计」。
3. **定位质量规则（节点这一头）**：
   - **初始化**：先验没换好 → `initializing`「在载入先验」；换好了但没收到重定位 → `initializing`「等人给初始位置」（探路结论 2：
     不给初值不出位姿；人在手机上设位置或者「在原点」，已有）。MOLA 重启之后同样要重新给初值 —— 节点自己用**重启前最后一帧可信的
     位置**请 MOLA 重定位（σ 1 m），不等人。
   - **σ**：`σ_xy = max(ICP 质量给的, 搜索窗口给的, 重定位之后的)`。ICP 质量 ≥ 0.8 → 0.1 m；0.8 → 0.5 线性涨到 1.0 m（代理那边
     1.0 m 就不信）。MOLA 的搜索窗口开到 0.6 m 以上说明它在找 → σ 不小于窗口。重定位之后 σ 从给的初值开始、跟住 30 s 才降到 ICP
     给的（探路结论 2：初值偏大时会带着偏差跑一阵）。数值是起点，回放工具出分布后再定。
   - **跳变**：相邻两帧挪得比狗能跑的还远（> 1.5 m/s × 间隔 + 0.3 m）或转得比能转的还快（> 2 rad/s × 间隔 + 0.3 rad）→ 这一帧
     `jump`；5 s 里跳 3 次以上 → `lost`「匹配在来回跳」，直到连着 5 s 不跳。重定位后的第一帧 `jump` + `reloc_id`（W09a 契约）。
   - **`meas_age_ms`**：ICP 质量低于 0.5 的那帧是 MOLA 靠运动模型推的 → 算作「没真匹配」，报离上一次真匹配多久；代理按 W09a
     的规则算进新鲜与推算上限。
   - **走出图外**（探路结论 3）靠上面三道一起抓：跳变、σ 随搜索窗口涨、代理用腿式里程的交叉校验。根上的办法是**巡逻路线只许在
     建过图的范围里** —— 先验里记下「哪里有图」、站点排路线时拒绝图外，归 W09c。
4. **回放工具**（W09b 的交付物之一，`d1max-loc replay`，开发机上跑、不要狗）：
   - 对一个录包：用 MOLA 命令行只定位跑一遍（先验、初值、`frames.json`），拿到每帧的位姿、ICP 质量、搜索窗口、处理耗时；
   - **用狗上同一份核心代码**按「时间戳 + 处理耗时」模拟到达，出给代理的报文流，再喂给代理的 `BridgeLocalizer`（W09a 的同一份
     代码），里程用录包里的 `odom → base_link`（录包里没有腿式里程，这是替身，报告里写明）；
   - 出报告（JSON + 一页 Markdown + 俯视图）：帧率、处理耗时 p50/p95/max、代理判「可信」的比例、σ 分布、跳变与丢定位的段、
     有参考轨迹时的平面误差与朝向误差（参考 = 同一坐标系下的建图轨迹，或者经轨迹形状配准对齐的独立建图）；
   - `--sweep`：在给定初值上加偏差（位置 0.5–3 m、朝向 15–45°）各跑一遍，出「初值要多准」的表（给手机「设位置」提示用）。
   - 录包、MOLA 都是本机的东西，工具不进 CI；pytest 用小的合成数据测工具本身（解析、对齐、指标算法）。
5. **部署**：`deploy/d1max-localizer-start`（加载 ROS humble 环境、W08 过渡期的 zenoh 与 domain 24、本版本的 Python 包路径）与
   `deploy/d1max-localizer.service`（`User=robot`，跟代理同一个账号 —— 本机桥按账号认）。**装上、不启用**；代理也保持
   `--localizer anchor`，真机验过之后再切（跟 W00b 的做法一样）。MOLA 在 Orin 上的安装（arm64 的 apt 包，离线）写进真机项。
6. **仿真不动**：W09a 的仿真定位器照旧给 W10/W11 用；本工单的节点核心用单元测试 + 录包回放验。

## 不做

- 三维先验的格式、压缩、「哪里有图」、在线建图（W09c，决策 17）；建图时手机实时看图（W09f）。
- 对时（W09d）：节点报的时间戳用 ROS 时间，代理按 W09a 的「相对晚到」配里程，不需要两边钟一致。
- RTK（W09e）；全局重定位（不给初值自己找）。
- 自己写点云匹配算法。

## 真机项（W09b 的，列进《庄园场景待真机测试》）

1. Orin 上装 MOLA（arm64、离线包）；只定位每帧耗时 p95 ≤ 100 ms、内存；跟不上时先降点云（体素）再说。
2. 开机 → 设位置 → 代理判可信；走一段，手机上位置跟着走。
3. 盖上雷达 / 拔雷达：报「雷达没数据」、狗停；打开后恢复要重新设位置吗（按设计：节点用最后可信位置自己重定位）。
4. 杀掉 MOLA：节点 1 s 内报「定位程序卡住了」并重启，狗停，恢复后接着走。
5. 走出图外：狗停、不乱走。
6. 设位置时朝向故意偏 45°：记下多久对上、这期间手机显示的位置偏多少（决定要不要在设位置之后让人确认一眼）。

## 测试

- `frames`：来回换算一致；标定从合成轨迹（已知「上」「朝前」）估得回来。
- `core`：初始化的几种状态与原因；σ 随质量、搜索窗口、重定位之后的时间；跳变线、5 s 内跳 3 次丢定位与恢复；`meas_age_ms`；
  MOLA 卡住、雷达没数据；重启后用最后可信位置重定位。
- `client`：连代理（真套接字，用 W09a 的 `LocBridgeServer`）、握手、心跳、断了重连、换先验与重定位当场回、报文都过契约。
- `mola`：ROS 不在时不 import；有 ROS 与短录包时（标记为慢测试、默认跳过）跑通一次只定位、出位姿。
- 回放工具：指标算法用合成轨迹测（已知误差、已知跳变）；轨迹形状配准能从已知变换估回来。
- 端到端（不要 ROS）：节点核心 + 客户端 + 代理的本机桥与 `BridgeLocalizer` + 仿真狗，喂一段合成的「MOLA 输出」：可信、跳了
  停、恢复、重定位、换先验。
