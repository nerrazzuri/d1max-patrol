# 自建导航后端（乙路线）设计

写于 2026-09-02。这是对 `2026-08-31-d1max-patrol-inspection-design.md` 的**增补**，
不是替代：那份 spec 的 §11「第一版明确不做」里写着「自建 Nav2 / SLAM Toolbox」，
本文档推翻的正是这一条，并写清楚为什么。

## 1. 为什么现在要做

第一卷定的是「混合导航：先厂商、后自建」，`NavBackend` 这个口就是为这一天留的。
两件事把「后自建」提前了：

1. **厂商建图被拒**（清单 #42），机器上一张图都没有（#49）。没有图，厂商导航
   那条路（甲）连 `load_map` 都调不了。前置条件文档里一个字没写，厂商也还没回。
2. **我们已经有自己的图和定位了**（2026-09-02，见 `建图定位与巡检管线.md`）：
   slam_toolbox 建的图、`localization` 模式的实时定位、`patrol_agent` 的运动通道，
   三件都在真机上跑通过。

用户裁定：**甲和乙都要能走通**。所以这不是二选一，是给 `NavBackend` 再补一个实现。

## 2. 边界：这一版做什么、不做什么

**做**：在已知自建地图上，从当前位姿走到一个目标位姿，能停、能查状态、能报到达/失败。

**不做**：
- **不接 Nav2。** Nav2 拖进来的是一整套 costmap / planner / controller / behavior tree，
  而它的收益（全局规划 + 动态避障）我们这一版都用不上——巡检路线是人预先标好的点，
  不是让机器自己找路。更要命的是 Nav2 的控制器在末段会把速度降到 0.05 m/s 量级，
  **正好落进 `Move` 的死区**（#37：`fwd=0.11` 几乎不动），会静默失败。
  留着以后再说，接口位置就是本文档定义的这个后端。
- **不做动态避障。** 超声波 `/uss_driver/*` 只订不用；撞上东西靠急停和人。
- **不做全局路径规划。** 点到点走直线，走不通就报失败让上层处置。

这个边界是有意压到最小的：**乙这一版的价值在于"厂商那条路堵着时巡检照样能跑"，
不在于导航本身有多聪明。**

## 3. 架构：三条线，一个口

```
  ┌─ ROS2 侧（系统 python3，有 rclpy）────────────────┐
  │  slam_toolbox localization                        │
  │      └── TF: loc_map → base_link                  │
  │              └── tools/ros2_pose_bridge.py        │
  │                     ↓ TCP/JSONL :8091（只出不进）  │
  └───────────────────────────────────────────────────┘
                        ↓
  ┌─ Python 侧（本仓库 venv，无 rclpy）───────────────┐
  │  LocalNavBackend  (implements NavBackend)         │
  │      ├── 位姿 ← :8091                             │
  │      ├── 运动 → :8090  patrol_agent（Move）       │
  │      └── 地图 ← 本地文件 runs/slam/*.yaml/.pgm    │
  └───────────────────────────────────────────────────┘
```

**为什么位姿要过一条 TCP 线，而不是在 Python 里直接 `import rclpy`：**
和 `tools/ros2_odom_bridge.py` 同一个理由，且更硬——venv 里没有 rclpy，
往 venv 里塞 ROS2 是条死路。更重要的是，**这样 `d1max_patrol` 整个包保持
纯标准库可测**：契约测试喂的是 TCP 上的 JSONL，不是 ROS 节点。
桥本身薄到没有业务逻辑（订 TF、序列化、发送），与 §5.2「bridge 做薄」同一条规则。

**为什么不复用 8090 那条线**：`patrol_agent` 是 C++，不认识 ROS。它吐的 `odom`
是**腿式里程**，会漂；定位器吐的是**地图系真值**。这是两个不同的源，§3.4 的
真理源规则在这里落地为：**地图系导航一律以定位器为准，`odom` 只用于交叉校验
（两边差得太多就是定位跳了，停车）。**

## 4. 位姿线协议（`pose_frames`）

单向、换行分隔 JSON，桥只出不进。复用 `agent_frames` 的风格与 `PROTO_VERSION` 惯例。

```json
{"t":"hello","proto":1,"map_frame":"loc_map","base_frame":"base_link"}
{"t":"pose","x":-0.79,"y":0.11,"yaw":1.632,"ok":true,"ts_ms":1756800000000}
{"t":"pose","ok":false,"reason":"lookup failed"}
```

- `ok:false` 表示这一刻查不到 TF。**连续 `loc_lost_after_s` 秒拿不到 `ok:true`
  就判定 LocLost**，而不是一帧丢了就慌——现场 TF 抖一下很正常。
- 桥固定 10 Hz 发送，即使查不到也发（心跳兼失败通知）。**没有帧本身也是一种信息**：
  连接断了 = 定位器挂了 = LocLost，不能当成"位姿保持不变"。

## 5. 控制器：转-走-校，脉冲式

不是连续控制器。每一拍：读定位 → 算误差 → 发一个**有限时长**的 `walk` → 停 → 再读。

```
到点判据: hypot(dx,dy) <= xy_tol            默认 0.25 m
朝向判据: |wrap(yaw_goal - yaw)| <= yaw_tol  默认 0.20 rad
一拍:
  角误差 > turn_enter(0.35 rad)  → 纯转向脉冲
  否则                            → 纯前进脉冲（不做转+走复合）
```

**死区是第一性约束，不是调参项。** 控制量按下式取：

    cmd = clamp(sign(err) * max(MIN_CMD, min(MAX_CMD, |err| * gain)), ...)

其中 `MIN_FWD = 0.30`（来自 #37 实测：0.11 几乎不动、0.3~0.5 明显走）、
`MIN_YAW = 0.30`（**假设(待真机验证)**：转向那一路一次都没量过，见 #56，
先按平移同量级取；#56 量出来之后改这一个常数即可）。

误差小到"按 MIN_CMD 走一拍会冲过头"时，**缩短脉冲时长**而不是降低控制量——
这是绕开死区的唯一办法，也是不接 Nav2 的直接理由。脉冲时长下限
`min_pulse_s = 0.3`，短于此就判定已到达（再抠下去没有物理意义）。

**卡住检测**：连续 `stuck_pulses`（默认 4）拍误差没有实质改善（改善量 < 2 cm /
0.02 rad）→ 判 `Failed`，交给上层的 `on_waypoint_failed` 处置。不原地打转到超时。

## 6. 地图与路线：落在文件上

`LocalNavBackend` 的地图源是目录里的 `<id>.yaml` + `<id>.pgm`（map_server 格式，
就是 `runs/slam/` 里已经有的那些）。

| `NavBackend` 方法 | 乙的实现 |
|---|---|
| `list_maps` | 扫描地图目录里的 `*.yaml` |
| `load_map` | 校验 yaml/pgm 存在且可解析，记下当前地图；**不影响定位器**（定位器是外面起的） |
| `get_map_grid` | 读 pgm，返回与厂商 `get_pgm_map` 同形状的 dict |
| `list_paths` / `save_path` / `remove_path` | `<id>.paths.json` —— 与地图同名的边车文件 |
| `start_mapping` / `stop_mapping` | **明确不支持**，抛 `NavRequestError`。建图是 slam_toolbox 在 ROS 侧的事，不走这个口 |
| `reset_localization` | **明确不支持**。重定位要人在看板上点 `/initialpose` |
| `get_speed` / `set_speed` | 控制器的 `MAX_FWD` / `MAX_YAW`，读写内存 |

**`start_mapping` 抛错而不是静默成功**，理由同 §3.4：半能力静默运行比明确报错危险得多。

## 7. 状态映射

| `NavBackend` 概念 | 乙的来源 |
|---|---|
| `nav_status` | 控制器自身：`StandBy` / `Running` / `Succeeded` / `Failed` / `Canceled` |
| `loc_status` | 位姿帧新鲜度：有新鲜 `ok:true` → `ContinuousLoc`；超 `loc_lost_after_s` → `LocLost`；从没收到过 → `None` |
| `MappingStatus` | 恒 `None` |

## 8. 仿真与测试

**`LocalNavBackend` 必须能跑与 `VendorNavBackend` 同一套契约测试。** 这是整个
Port 设计的兑现时刻——契约测试里凡是断言"厂商特有行为"的，说明当初写进了实现细节，
要么改测试要么改 Port，两边都不能将就。

- `d1max_sim.pose_server.SimPoseServer` —— 拿 `SimAgentServer` 的 `x/y/yaw`
  当定位真值往外发。**不是复制一份状态**，是持引用读，否则两边会不一致到没人发现。
- 故障注入：`drop_localization()`（开始发 `ok:false`）、`freeze()`（停止发送，
  模拟定位器进程挂掉）、`jump(dx,dy)`（位姿跳变，用来测交叉校验）。
- `SimAgentServer` 已经建模了 `WALK_DEADBAND = 0.2`，**控制器的死区常数取 0.30
  高于它**，所以仿真里控制器是能走动的；把常数调到 0.15 就应该走不动——
  **这条要写成测试**，它是对"我们真的绕开了死区"的唯一自动化证明。
