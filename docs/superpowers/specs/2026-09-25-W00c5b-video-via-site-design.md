# W00c5b · 视频经站点 —— 设计稿

日期：2026-09-25 · 工单：W00c5b（L，依赖 W00c5a）
状态：**按推荐（用户 2026-09-25 授权连续推进：「从W00c5a到W00c5e直接做完」）**。四个决定都取推荐项。受决策 8 约束（信息不留在狗上）与决策 7 约束（遥控「没画面不许动」要有站点这一路的画面健康）。

## 0. 事实

- 狗上两路相机：RK3588 上的 RTSP `rtsp://192.168.234.1:8554/{front,back}`（GStreamer 推流）。**编码、分辨率、延迟都没在真机上量过**（清单 #29）。
- 现在：狗上老服务每路相机一条 ffmpeg（RTSP → MJPEG 5 fps，有人看才起、最多 6 个观众），经 HTTPS 直接给手机（`multipart/x-mixed-replace`），手机的 `LiveVideo` 自己解析。
- 总设计 §5：「视频扇出与录像 → 站点」；§1：手机不直连狗；老商业化设计：狗的上行只推一份，站点是唯一复制点。
- 连续录像、事件前后缓冲、H.264 到手机是 **W18**（「连续录像……顺带 H.264」），不在这一张。
- 站点主机是 Ubuntu 22.04，apt 的 ffmpeg 4.4 带 SRT 与 libx264（开发机同款已核对）；狗上（Orin）也有 ffmpeg，**有没有 SRT 没核对过**（进真机清单）。
- 站点与狗之间只有 MQTT（mTLS），站点 API 只给手机（HTTPS、令牌）。

## 1. 决定一：狗怎么把画面送到站点

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | **按需推、SRT 加密**：站点要看某路相机时，经 MQTT 给代理发一条 `video` 命令（相机名、站点的 SRT 地址、这一次随机生成的口令、有效期）。代理起一条 ffmpeg：拉本机相机 RTSP，**不转码直接转封装**（`-c copy`；相机若不是 H.264 再按配置转码，待真机定），用 SRT（AES，口令只经 mTLS 的 MQTT 下发）推到站点。**有效期到了没续就自己停**：站点没了、网断了，狗不会一直往外推。上行只推一份，站点复制 |
| B | 狗上转成 MJPEG 再经 HTTPS 推给站点。复用老代码，但上行带宽大 5–10 倍，4G 上行吃不消 |
| C | 站点装 MediaMTX（流媒体服务器）。录像、WebRTC 都现成，但多装一个外部二进制、多一套鉴权；留给 W18 再评估 |

## 2. 决定二：站点怎么给手机

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | 站点每路（狗, 相机）一条 ffmpeg：收 SRT → 解码 → MJPEG 5 fps，**多个观众共用这一条**（照搬狗上 `video.py` 的扇出、观众上限、过期判定）；站点 API `GET /api/robots/<id>/video/<camera>`（`multipart/x-mixed-replace`，令牌鉴权、`view` 权限）与 `GET /api/robots/<id>/video/health`。手机的 `LiveVideo` 换个数据源就能用，不用新播放器 |
| B | 手机上 WebRTC/H.264。要新播放器插件，归 W18 |

## 3. 决定三：什么时候起、什么时候停

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | **第一个观众来了才起，最后一个走了 10 s 后停**（给来回切屏留缝）。起的时候站点分配一个 SRT 端口（配置的端口段里挑空的）、生成口令、起收流的 ffmpeg、发 `video` 命令；有观众期间每 `ttl/2` 续一次命令（有效期默认 10 s）。**起了 8 s 还没收到第一帧**：给观众回 504 并说明（狗不在线、相机不通、端口不通），收流进程收掉。狗报 `video_failed` 事件时同样收掉 |
| B | 狗一直推。4G 流量一直在走，也违背「没人看就不产生数据」 |

## 4. 决定四：画面健康给谁用

| 选项 | 内容 |
|---|---|
| **A（推荐，取）** | 站点每路记最后一帧的时刻；`video/health` 回每路 `{online, last_frame_age_ms, viewers}`（`online` = 2 s 内来过帧，同老判据）。W00c5c 的遥控「没画面不许动」读的就是它；站点也在观众流里遇到断流时结束该连接 |
| B | 让手机自己判。遥控闸门要在站点与代理那头，不能信手机 |

## 5. 形状

- 契约：命令种类 `video`（不是任务：不占资源、不进任务状态机、不看 `control_epoch`），载荷 `{camera, url, passphrase, ttl_ms}`；`camera` 只认 `front/back`；`url` 只认 `srt://`；事件 `video_failed {camera, reason}`；黄金夹具。
- 代理：`d1max_agent/video_push.py`：每路相机至多一条推流进程；续命令刷新有效期；到期、被新命令替换、进程退出都收干净；进程非正常退出发 `video_failed`；输入源可配置（真狗：相机 RTSP；仿真：ffmpeg 的测试图 `lavfi testsrc` 编成 H.264）。`d1max-agent --camera-host 192.168.234.1 [--video-transcode]`。
- 站点：`d1max_site/video.py`：端口段分配、口令、收流 ffmpeg、MJPEG 扇出（观众上限、慢观众丢帧不拖别人）、续命令、按需停；API 两条；配置 `video.srt_host`（狗连站点用的地址）与端口段（写进 `site.json`，安装脚本开防火墙的说明进文档）。
- 手机：`LiveVideo` 的数据源抽成接口（直连狗 / 站点），站点单狗页加画面（前、后切换）。
- 狗上老服务的视频路由**这一张不删**（直连遥控还在用），W00c5e 一起退役。

## 6. 验收

- 开发机（真 ffmpeg、真 SRT、仿真相机）：手机（Dart 测试用假站点）/ Python 测试客户端经站点 API 拿到连续 JPEG 帧；两个观众只起一条收流与一条推流；最后一个观众走后 10 s 狗那头推流停、站点收流停；续命令断了狗在有效期内自己停。
- 口令错、URL 不是 `srt://`、相机名不认的命令被拒；业主能看（`view`），没登录 401。
- 起流 8 s 没帧 → 504 带理由；`video/health` 如实反映。
- 真机项（进 `docs/庄园场景待真机测试.md`）：狗上 ffmpeg 有没有 SRT、相机编码与分辨率、`-c copy` 能不能直接推、端到端延迟、4G 上行带宽。
