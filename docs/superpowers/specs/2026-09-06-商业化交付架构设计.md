# 商业化交付架构设计

写于 2026-09-06。

这份文档回答的是一个产品问题，不是一个技术问题：**一套机器狗巡检系统，怎么卖给客户、
怎么在客户现场跑起来、以及客户为什么要为服务器多掏一笔钱。**

它推翻了 `2026-08-31-d1max-patrol-inspection-design.md` §11「第一版明确不做」里的两条 ——
**崩溃后自动续跑**和 **ABORT 时的自动位移** —— 因为那份文档假设的是「人在旁边看着」，
而本文档假设的是**无人自主运行**。假设变了，那两条就从「不做」变成「必须做」。

**本文档覆盖 §0–§8，全部展开完毕。**

---

## 0. 已经定死的前提

这几条是拍过板的，后面所有设计都建在它们上面。**改动其中任何一条，本文档大部分要重写。**

| 前提 | 决定 |
|---|---|
| 商业模式 | **先卖产品，后转服务。** 所以 `ArchiveStore` 和 `Identity` 从第一天起就是抽象口；但**不做多租户业务逻辑**（YAGNI） |
| 垂直行业 | **未定。** 所以内容层（判读的 prompt 与阈值）做成插件点，部署架构不等它 |
| 值守模式 | **无人自主 + 实时值守。** 值守员在**客户现场监控室**，就在现场附近 |
| 架构路线 | **路线 C**：自足任务包下发给狗，狗离线跑完整轮；服务器做编排、归档、看守、告警 |
| 充电 | **没有充电桩。** 回到原点由人热插拔换电池 |
| 导航 | 甲（厂商导航）与乙（自建导航）**都要走得通**，不是二选一 |

### 0.1 路线 B 已经明确否掉，不要再提

**路线 B = 服务器当大脑，实时指挥狗走每一步。**

否掉的理由只有一条，但足够：**它和「断网续跑」直接冲突。** 网一断，狗就变成一块砖。
而客户现场的网络会断——这不是风险，是常态。

这是企业软件的默认直觉（「把逻辑放在服务器上好管理」），所以会被反复提出来。
**写在这里就是为了让下一个人不用重新论证一遍。**

## 1. 运行节律与电量策略

### 1.1 电量的真理源是 `min(power1, power2)`

`refs/robot-sdk/RobotSDK-0.2.0/docs/zh/sdk_type_zh.md:145-157` 里，`BatteryData` 把两块电池
**分开报**：`power1` 和 `power2`。

而硬件手册 2.3.3「内部异常保护」写着：**电池在位但电量 <10% → 机器人自动停车并缓慢着地**。
`sdk_type_zh.md:58-59` 的 `PowerControlPowerEmpty` 也是「**单电池** <10%」。

**这个保护是按单块电池判的，不是按平均值。** 所以：

> **任何跟电量有关的判断，一律用 `min(power1, power2)`，永远不用平均值。**

一块 60% 一块 12% 的狗，平均 36% 看着很健康，但它随时会原地趴下。

### 1.2 三条线

| 线 | 值 | 含义 |
|---|---|---|
| **出发线** | `预计耗电 × 1.5 + 返航储备` | 电量低于它就不出发。**1.5 倍不是保守，是因为预计耗电本身不准** |
| **返航线** | **动态**，按「从当前位置回原点还要多少电」实时算 | 跑到场地最远端时的返航线，必然高于刚出发时 |
| **中止线** | **25%** | 立即就地中止，报警叫人 |

**中止线从 15% 提到 25%。** 现有代码 `engine/mission.py` 的 `Policy.battery_abort_pct`
默认是 15.0——**离厂商那条 10% 的强制趴窝线只剩 5 个点**，而这 5 个点要覆盖：发现、
告警、人走过去、把狗弄回来。不够。25% 留出的余量才是真的余量。

`battery_return_pct` 则从一个常量变成一个按剩余里程算出来的值。

### 1.3 原点升格为一等公民

原点同时是三样东西：**换电位、待命位、返航目标**。它不再是「地图上随便哪个点」，
而是**建图时就要标定、并且存进地图**的一个结构。

没有充电桩这件事，一半是麻烦，一半是**便宜**：

> 电池支持热插拔（`refs/hardware/D1Max-SDK开发指南V0.1.0-正文提取.txt:156`：
> `电池模组 504.9Wh*2，双电池，支持快拆快换，支持热插拔`）。一块一块换，狗全程不断电，
> **定位不丢，不需要重设初始位姿**。
>
> 有充电桩的设计反而要额外解决「上桩/下桩重定位」。我们不用解。

续航参数：空载 5±0.5h，满载 3.5±0.5h，充电 <1.5h。

### 1.4 换电池是值守员的活

值守员本来就在现场。系统的义务**不是让人盯着电量**，而是**在该换的时候准确地叫人**：
提前量足够走回原点，且告警要能穿透「没人开着 app」的时段（见 §3.5 分档）。

## 2. 三层职责与边界

### 2.1 三层

| 层 | 职责 |
|---|---|
| **狗** | 走路、感知、拍照、判断能不能继续。**离线自足**：任务包在手，断网照跑 |
| **服务器** | 编排（发任务包）、**归档的记录源**、值守大屏、告警、扇出 |
| **手机 app** | 人机界面。单机时直连狗，联网时连服务器 |

### 2.2 三条边界规则

1. **服务器永远不在控制回路里。** 它发的是**意图**（「下次这么跑」），不是**动作**
   （「现在左转」）。唯一豁免见 §3.4。**这条不靠自觉：服务器上根本没有移动接口，
   移动只在手机 app 上**（§5.5）。
2. **服务器可以在数据通路上，但永远不在控制回路上。** 这两件事必须分开：
   单机时视频由 app 直连狗；有服务器时视频经服务器扇出（§3.7），
   此时服务器**转发字节**，但仍然不闭任何环。
3. **归档的真理源会迁移**：拍摄当下在狗上，确认上传后在服务器上。**同一时刻只有一个真理源。**

### 2.3 网络拓扑：CPE 是必需件，不是选配

```
                    ┌── 客户网络（有线 / WiFi）   ← 主链路
   狗 ──M12 网线──▶ CPE ─┤
                    └── 5G SIM                    ← 无网时兜底

   狗的 wlan0 ────────── 永远是 AP（XG2WIFI_xxxxxx）  ← 低保通道，从不切走
```

**为什么必须走网线接一个 CPE，而不是让狗自己连客户 WiFi：**

硬件手册 5.6「连接外部 wifi」用的是 `wpa_supplicant -i wlan0`，5.7「连接 WiFi 的情况下
访问有线网口」说的是连狗自己的 AP `XG2WIFI_xxxxx`——**两节用的是同一个 `wlan0`**。
基本可以断定两者互斥：一旦切成 STA 去连客户 WiFi，那个 AP 就没了。

而那个 AP 是**唯一一条不依赖任何外部网络的通道**。客户网崩了、5G 没信号、狗卡在角落里，
就靠它。把它切走去上网，等于把降落伞拿去当桌布。

**所以：上网这件事整个交给 CPE，狗的 `wlan0` 永久钉死在 AP 模式。**
双链路切换（有线优先、蜂窝兜底）是 CPE 的成熟功能，狗侧零配置零代码。

代价说清楚：**多一个单点故障。** CPE 挂了远程全断，但狗还在自己跑任务（路线 C 的
离线自足），值守员走过去连 AP 就能接管。可接受。

### 2.3.1 M12 航插：不要买 PoE 设备

《SDK 开发指南》1.5.3 / 1.5.4，板端型号 `M12-P12A-GPFM12`，**12 针 A 型航插**：

| 针 | 用途 | 针 | 用途 |
|---|---|---|---|
| 1(棕) | GND | 7(黑) | 网口 B- |
| 2(蓝) | **24V** | 8(灰) | 网口 C+ |
| 3(白) | **24V** | 9(红) | 网口 C- |
| 4(绿) | 网口 A+ | 10(紫) | GND |
| 5(粉) | 网口 A- | 11(橙) | 网口 D+ |
| 6(黄) | 网口 B+ | 12(浅绿) | 网口 D- |

**两件事同时成立：**

1. **用不着 PoE。** A/B/C/D 四对数据全在（所以是千兆），外加独立的 24V 和 GND。
   电和数据物理分开，比 PoE 在数据对上叠直流干净。面板上两个这样的口：
   **网口+24V(3A)=72W**、**网口+12V(5A)=60W**。所有供电接口总功率 ≤480W。
2. **想用也插不上。** M12 上能跑标准 PoE 的只有 **X 型 8 针**；**D 型 4 针**只有两对、
   跑百兆。这台是 **A 型 12 针**——A 型根本不是以太网编码，是通用信号/电源编码。
   市面上任何 PoE 网线、注入器、交换机都对不上。

**接线前必须先按扩展仓按键断掉扩展口供电**（手册明文）。线要定制：M12-P12A 公头 →
RJ45 + DC。

**CPE 选型硬指标**：DC 9~36V 宽压输入 / ≥1 个千兆 RJ45 / 有线或 WiFi 主 WAN + 蜂窝备份
自动切换 / 工业宽温无风扇 / 外置天线。类目是**工业级或车载 5G 路由器**，不是消费级便携 CPE。

马来西亚部署额外两条：**必须支持 LTE B7（2600）**——Maxis、Celcom、Digi、U Mobile 全在用，
缺了会在 5G 回落时掉一大截容量；**以及能过 SIRIM 认证**。5G 主力频段 n78 一般都有，
那一条不是问题。

### 2.4 实时性：网络允许时，全实时

**默认全实时，码率分级是降级阶梯，不是默认状态。**

| 数据 | 规则 |
|---|---|
| **位姿** | **永远常开，无条件。** `protocol/pose_frames.py` 已是 10Hz，一帧一百来字节 ≈ **1KB/s**。这就是监控室大屏：N 只狗在同一张地图上实时动 |
| **照片** | **拍完立即推**，不攒批。但**推成功不等于立刻删**——删除由盘水位驱动，见 §4.4 |
| **视频** | **网络允许就实时。** 码率分级只在链路撑不住时逐级降，最后才降到「只有事件没有画面」 |

**三者都只推给服务器一份，由服务器扇出**——理由见 §3.7。

### 2.5 两种「盘满」，处置完全不同

- **已上传的**：按水位删，删多少都不心疼
- **未上传的**：**绝不删**。报警 + **拒绝出新任务**

把这两种混为一谈，就会在某个没人注意的夜里把唯一一份证据删掉。

**这条规则在单机模式下会失效**（没有上传对象，所有文件永远算「未上传」，
狗迟早永久停飞）。补法见 §4.6。

## 3. 任务包与排程

### 3.1 包里装什么——判据只有一句

> **断网 72 小时，这只狗还能不能照常上岗？**

答案为「不能」的东西必须进包。

**进包**：`bundle.yaml`（身份/版本/目标 SN/校验和）、**地图**（乙用的 SLAM 图 +
甲用的 `path_id` 引用）、点位与动作、`policy`（§1 那套电量线）、**`schedule`**、
`origin`（§1.3 的原点标定）、`checks`（判读的 prompt 与阈值——**垂直行业的插件点就是这一层**）。

**不进包**，两条都有理由：

- **VLM 权重和 API key 不进包。** 判读不在控制回路里。狗断网时照拍、照归档，
  判读排队等有网再做。**把判读做成必须在线，等于让「看得懂」成为「走得动」的前提**，
  那是自找的耦合。
- **固件和代码不进包。** 任务包是**纯数据，不含任何可执行内容**。这是安全边界不是洁癖：
  包走网络、可能被改、而且**自动生效不经人确认**。一旦包里能带脚本，
  攻破服务器就等于拿到所有狗的 root。升级走独立通道、独立授权。

### 3.2 身份与版本

`bundle_id` + **单调递增整数** `version`（不用时间戳——时钟会跳，见 §3.3）+ 整包
`content_hash`。狗收到先校验再落盘。

狗上永远留**两份**：`current` 和 `previous`。校验失败、或新包首次执行就崩，
自动回退 previous 并上报。心跳里报 `(bundle_id, version, content_hash)`。

**不做增量下发。** 整包替换。地图几十 MB，一次几秒；增量的复杂度全堆在「部分成功」上，不值。

### 3.3 排程

**不用 cron 表达式。** cron 表达不了「错过了怎么办」，而错过是常态——上一轮超时、
正在换电池、人还没到。

```yaml
schedule:
  timezone: Asia/Kuala_Lumpur
  entries:
    - id: night-1
      mission: perimeter-full
      at: "22:00"
      days: [mon, tue, wed, thu, fri, sat, sun]
      window_min: 45          # 迟到超过 45 分钟就放弃这一轮
      on_missed: skip         # skip | run_late | alarm
```

四条必须定死：

1. **时区写进包，不读系统时区。** 刷机、OTA、换主板都可能把时区打回 UTC，
   然后整晚的巡检时间全错——**而且没人会发现**。
2. **`window_min` 是核心不是装饰。** 22:00 那轮拖到 22:50 才轮上，跑它可能比不跑更糟
   （跟下一轮撞、或者天亮了）。每条都必须回答「迟到多久就不跑了」。
3. **单队列，同一时刻只跑一个任务。** 撞车按 `priority`，没有则先到先得，
   被挤掉的按 `on_missed` 处理。
4. **时钟漂移要告警。** 联网时 NTP 对时，断网时靠 RTC 漂。心跳报 `clock_skew_s`，
   超阈值告警——整个自主运行都压在本地时钟上，**钟不准这个错是静默的**，
   狗会一脸认真地在错误的时间巡逻。

### 3.4 服务器改了排程、狗还断着网——以谁为准

> **狗手上那一版是「执行」的唯一真理源；服务器那一版是「意图」的唯一真理源。
> 两者不一致时，狗照旧跑它手上那版，绝不停摆。**

因为路线 C 的全部价值就是断网续跑。如果「服务器有新版但下不来」能让狗停下，
断网就重新变成单点故障——那是偷偷退回已经否掉的路线 B。

- 服务器改包 → 标 `pending` → 狗上线推送 → 校验落盘 → 回执 → 标 `applied`
- **推送不打断正在跑的任务**，新包在当前任务结束后生效
- 值守屏**必须显式显示落差**：「3 号狗还在 v7，服务器已到 v9，最后同步 4 小时前」。
  **不显示落差是这一节最危险的失败模式**——人以为改生效了，其实没有，而且看不出来

**唯一的例外：停机指令不进任务包，走独立实时通道，可以打断当前任务。**
这是 §2.2 第 1 条的唯一豁免，而且**是单向的：服务器只能让狗停，不能让狗动。**
让它停不需要闭环（停在安全侧），让它动需要闭环（动在危险侧）。**这个不对称是刻意的。**

### 3.5 软件控制权（L1）

**先把层分清楚，这里我们自己绕过一次弯：**

| 层 | 是什么 | 谁解决 |
|---|---|---|
| **L0** | SDK 会话独占（清单 #46/#47） | **架构一次性解决，对上层不可见。** `patrol_agent` 抢到窗口后死握不放 |
| **L1** | 谁能指挥这只狗 | **我们自己写的软件权限。跟 L0 没有半点关系** |
| **L2** | L1 跑在狗上（单机）还是服务器上（联网） | 部署形态，不是设计差异 |

清单 #47 结案原文：「SDK 资源（控制+数据读取）是独占的……不持有会话时读/控都进不去。
**架构含义：自主巡检须用一条常驻会话，抢到窗口后一直握住不释放。**」#46 结案：
「厂商侧没有交接机制。控制权一旦被上装拿走，就再也响应不了。」

**这些是 L0 的事，到 `patrol_agent` 为止。它们不构成「app 只能连一个」的理由。**

#### 语义是租约，不是锁

**这是这一层最关键的决定。** 锁要显式释放，而手机会没电、会走出信号、会被系统杀掉。
一个不会自己过期的锁，第一个持有者一掉线就把狗锁死——**那就是在我们自己这层，
把 #46/#47 那个「交接不回来」的坑原样重挖一遍。**

租约有 TTL，持有者靠心跳续租，断了自动到期。

#### 四条规则

1. **只读永远不需要控制权。** 位姿、视频、照片、事件流——有有效 token 就能看。
2. **急停不需要控制权。** 任何持有有效 token 的人都能让它停。跟 §3.4 是同一个不对称：
   **停在安全侧。** 把急停放在权限后面，等于让权限设计变成安全隐患。
3. **接管要留痕，且必须能强制。** 请求接管 → 当前持有者收到提示 → 同意或超时即移交。
   **强制接管必须存在**（带审计），因为持有者可能已经不在了。
4. **控制权的定义收窄成「我能改变它正在做什么」**，不是「我能动它」。
   `app/teleop.py:111` 已经有这个直觉：「任务在跑,先停任务再遥控 —— 两边一起动是在抢腿」。

仲裁逻辑是**一套语义、一份实现**：单机跑在狗的 `app/server.py` 里管一只狗，
联网时同一套逻辑上移到服务器管 N 只狗 × M 个人。

### 3.6 并发上限：**一只狗最多 3 个 app 会话**

其中**控制权租约只有 1 份**，其余为只读。第 4 个请求进来**明确拒绝并说明原因，不排队**
——沿用 `app/video.py` 的既有原则：「排队意味着人盯着一个转圈的图标，不知道是没连上
还是在等」。

**服务器不占这 3 个名额中的一个——它就是那唯一的会话。** 接入服务器后，狗只认服务器
一个客户端，扇出全在服务器侧，人数上限由服务器的资源决定，不再由狗决定。
所以「3」是**第一、二档的上限**，第三档没有这条限制。

#### 3 这个数字是怎么来的

**不是算力。** `app/video.py` 现在是「一个观众一条 ffmpeg 子进程」（`MAX_VIEWERS = 2`），
那是按「一台笔记本看」写的写法，**不是物理限制**——改成一相机一条 ffmpeg、
把同一串字节扇给 N 个连接，编码就是 O(1)。这个要改（见 §10）。

**真正 O(N) 的是 CPE 那条无线上行。** 因为链路上**没有任何环节会把一份变成 N 份**：

```
狗 ──M12 千兆──▶ CPE ──【无线上行】──▶ 客户 AP ──▶ N 台手机
   N 份            N 份    ↑↑ N 份全挤这里 ↑↑
```

CPE 是路由器，**转发不复制**。N 台手机各开一条 TCP，就是 N 份独立的字节流，
从源头就得是 N 份。要「只发一份」，路径上必须有一个**复制点**，而现在没有。
（多播不行：手机浏览器消费不了、WiFi 多播按最低速率发且不可靠、客户网络基本都拦。）

而这条无线上行恰好是整条路径上**最弱、最不可控、还共享**的一段——狗在动、离 AP 远、
隔着金属结构件时它最差，**也正是最需要看画面的时候**。

| | 每观众 | 3 观众 |
|---|---|---|
| 位姿 10Hz | ~8 kbps | 可忽略 |
| **MJPEG 1080p（现状，`-vcodec mjpeg -q:v 6`）** | **8–16 Mbps** | **24–48 Mbps** |
| H.264 1080p（该换成的） | 1–2 Mbps | 3–6 Mbps |

CPE 无线上行标称几百 Mbps，但移动中、有遮挡时实测常只剩二三十 Mbps，还是共享的。

**还有一个更要命的二阶效应**：上行被视频挤满时，**位姿流和告警会跟着遭殃**。
位姿只有 1KB/s，但它要的是**低延迟**；链路一拥塞、TCP 重传打架，它就被拖垮。
表现是大屏上的狗开始跳、卡、位置滞后——而这时候你正因为看不清画面才更需要那个位置。
**这是安全相关的，不只是体验问题。**

**所以 3 是刻意压在物理极限（换成 H.264 后约 3–5）之下的**，留出的余量是给位姿和告警的。
这个上限有物理依据，不是人为设卡。

### 3.7 产品三档

| 档 | 卖什么 | 天花板 |
|---|---|---|
| **一、单用户** | 狗 + app | 一次一个人 |
| **二、多用户授权** | 纯软件许可，不加硬件 | **3 个并发 app 会话**（§3.6），受 CPE 无线上行限制 |
| **三、服务器** | 监控室 | —— |

**第二档几乎不增加成本**——仲裁层（§3.5）无论如何都要写。白捡一档收入，
还让第三档的必要性变得可信：客户先花小钱试过多用户，**撞到一个说得出数字的物理上限**，
才来买服务器，那时候他知道自己在买什么。

#### 服务器的差异化：它是那个复制点

不是「多人」（第二档就能多人），而是**解开 N 只狗 × M 个人这个乘法**：

```
狗 ──1 份──▶ CPE ──【无线上行只走 1 份】──▶ 服务器 ──有线──▶ M 个人
```

**狗的上行负载跟观众数彻底解耦，永远是 1。** 而服务器坐在**有线基础设施**上，
不在那条脆弱的无线上行的另一头。

加上只有服务器能做的：

- **归档之家**：服务器无限期留存，狗上只留水位允许的近期（§4.4），**狗的盘永远不满**
- **跨时间比对**：`inspect/judge.py` 的 `_previous_photo` 做的是同一点位跨日期比对
  （「这道裂缝上个月有没有？」）。**要有历史才活得起来，没有服务器就没有历史，
  这条路整个是死的。** 单机版能回答「这张照片有没有问题」，
  联网版才能回答「**跟上次比变了没有**」——而后者才是巡检真正值钱的地方
- **无人时段的常在告警**：凌晨三点没人开 app，服务器照收照升级
- **跨机统一视图**与值班交接
- **名录**：狗接进客户网络后拿的是 DHCP 地址，**不可预测而且会变**。
  客户有 5 只狗时「该连哪个地址」这个问题，只有服务器能一劳永逸地答（§6.1）
- **对外集成**：报表、webhook、对接客户已有的安防平台
- **审计**：谁改了什么、谁批了什么
- **备份不用人惦记**：单机档要么装选配的镜像盘、要么记得在授权 OTA 前点一下
  （§7.4/§7.5）；联网档的备份**是自动的、异地的，没人需要记住任何事**

**原则：不靠阉割 app 来卖服务器。** app 该有的功能一个不减——单机版是「先卖产品」
阶段的主力，做残等于自断前路，客户也看得出来是故意的。

### 3.8 打包器是库，不是服务器的功能

包在服务器上产出（服务器是编排者），但**必须能在没有服务器的狗上原地产出**——
因为「先卖产品后转服务」意味着客户完全可能只买一只狗。

- 库本身（编包、校验、算哈希）：**共享，两边一样**
- **服务器独占的是规模**：跨机下发（一个包推给 5 只狗）、完整版本历史与任意回滚
  （狗上只留两份）、变更审批与审计

**共享的是「做一个包」，服务器多出来的是「管很多包、发给很多狗、并记住这一切」。**

### 3.9 app 必须一套界面同时对得上狗和服务器

否则就是两个 app、两倍维护。

- app 的后端地址可配置：指向狗（单机）或指向服务器（联网）
- **服务器实现狗那套 `/api/*` 的超集，但移动类接口除外**——那几个永远不实现（§5.5）
- 但**实时的东西在有服务器时走服务器扇出**（§3.7），单机时直连狗

这条正好落在既定的两个抽象口上（`ArchiveStore` / `Identity`）——它们现在有了具体的
第二个实现，不再是空谈的扩展点。

## 4. 归档与回传

### 4.1 上传的单位是**文件**，不是**任务**

直觉是「跑完一趟打包上传」。不能这么做：`RunArchive.finish()` **有可能永远不被调用**
——断电、进程被杀、任务中途 ABORT。按任务打包等于宣布「崩溃那一趟的数据永远传不上去」，
而那恰恰是最需要看的一趟。

**每个文件独立成为一个上传项**，run 目录只是它的分组元数据。`events.jsonl` 是追加写的，
按**字节偏移续传**：已传到 N 字节，下次从 N 开始。

### 4.2 「传成功」的定义：**服务器自己算出来的哈希对上**

不是「HTTP 返回 200」，也不是「服务器回显了我发的哈希」——回显只证明它收到了那个
**字符串**，不证明它收到了那个**文件**。

> 回执里必须带**服务器落盘后重新算的 `sha256`**。对不上就是没传成功，重传。

这一条同时定死了 §2.2 第 3 条「真理源迁移」发生的**确切瞬间**：在服务器算完哈希并对上
的那一刻，不在之前任何时候。

### 4.3 队列在盘上，四级优先

队列必须落盘（`queue.jsonl`，同样每行 flush），因为**断电重启后队列还得在**。
内存队列等于「一断电，攒了三天的东西全没了」。

上行带宽紧张时按这个顺序让路：

| 级 | 内容 | 带宽不够时 |
|---|---|---|
| 1 | **告警** | 永不让路 |
| 2 | **事件流** `events.jsonl` | 永不让路（一趟几百行，几十 KB） |
| 3 | **照片** | 排队，慢慢传 |
| 4 | **遥测** `telemetry.jsonl` | **可以整个放弃**，只在带宽有富余时传 |

重试用指数退避，**封顶 5 分钟**。**不做「重试 N 次后放弃」**——放弃意味着悄悄丢证据。
传不上去就一直排着，同时把**队列积压条数报进心跳**，让值守屏看得见。

**上传线程绝不阻塞巡检。** 任何时候「传不出去」都只影响回传，不影响走路拍照。

### 4.4 删除由**水位**驱动，不由**上传**驱动

**这一条推翻 §2.4 里「推成功即删本地」的说法，以本节为准。**

上传成功只把文件标成**「可删」**，不立刻删。真正的删除等到盘触及水位线时才发生，
在「可删」里按时间从旧到新删。

差别在于：立刻删的话，服务器那边一旦出事（盘坏、误删、备份没做），狗这边已经空了，
**世界上就没有第二份了**。按水位删，狗上通常会白白留着一份冗余副本，而这份冗余
**不花任何额外成本**——盘反正空着。花钱买的盘，空着才是浪费。

### 4.5 基线集：判读要的那一张，**永不删**

`inspect/judge.py:182` 的 `_previous_photo` 是这么找比对基准的：

```python
for run in list_runs(history_root):        # 扫本地历史 run 目录
    candidates = sorted(...)               # 找 P1__front__*.jpg
```

**它读的是本地历史。** 一旦把传完的照片删掉，跨日期比对就**静默失效**——不报错，
只是从此每张照片都变成「无基准」判读，而没有人会发现。

拆开这两件事：

> **归档是证据，基线是工具。** 另存一份 `baselines/<waypoint>__<camera>.jpg`，
> 每次判读通过后覆盖更新，**独立于 run 目录，永不参与水位删除。**

体积算得过来：50 点位 × 2 相机 × 300KB ≈ **30MB**，一次性占用，不随时间增长。
用 30MB 换「判读能力不依赖网络、不依赖服务器、不依赖保留期」。

### 4.6 单机模式的盘满：两套策略，由「有没有上传目标」来选

§2.5 定的是「未上传的绝不删」。但**单机模式下没有上传对象，所有文件永远算「未上传」**
——照那条规则，狗迟早因为盘满而永久拒绝出任务。这个洞在这里补上。

| | 有服务器 | 单机 |
|---|---|---|
| 分类依据 | 已传 / 未传 | **保留期内 / 保留期外** |
| 删谁 | 已传的，按水位 | 保留期外的，按水位 |
| 硬约束 | 未传的绝不删 | **删之前必须先预告** |

单机模式的删除有三条附加要求，因为**这里删掉的是世界上唯一一份**：

1. **提前预告。** app 上显式显示「盘 78%，预计 6 天后开始删除 8 月 12 日之前的记录」。
   不是删完之后写条日志——那时候已经晚了。
2. **必须有导出通道。** 至少能把一个日期区间打成 zip 从 app 拉走。
   **没有导出通道的自动删除，等于系统单方面销毁客户资产。**
3. **基线集不在保留期管辖内。**

保留期默认 **90 天**，写在任务包的 `policy` 里，客户可调。

### 4.7 起飞硬门槛：**盘 ≥90% 不许出发**

两条门槛并列，**都得过**：`free ≥ 500MB`（现有 `preflight.MIN_FREE_MB`）
**且** `used ≤ 90%`。大盘上 90% 还剩几十 GB，小盘上 500MB 已经是 99%——谁先触发听谁的。

**是「不许出发」，不是「就地中止」。** 已经在跑的那一趟不因为盘满而停：
半趟数据比空盘值钱得多。中途真写满了，降级顺序是**先停拍照，保住 `events.jsonl`
和告警，把路走完回原点**。events 一趟几十 KB，照片才是大头。

**80% 就要报警，不能等到 90% 才说话。** 90% 是拦停线，80% 是提前量，
中间那 10% 是留给人反应的时间——跟 §1.2 电量那三条线是同一个道理。

**联网模式下 90% 基本不该触发**：传成功的都标了「可删」，水位一到自动清。
真触发了，说明**回传已经断了很久**。所以这时的告警文案不能是「盘满了」，
而要是「**回传已中断 N 天，盘要满了**」——说病因，不说症状。

**单机模式下「盘 90% + 保留期未到」是个死锁**，而且必然会撞上：所有文件都在 90 天
保留期内，一个都不能自动删，狗就永久停飞。

**不自动放宽保留期。** 那等于系统自己决定销毁客户唯一一份资产。改成**升格为必须人处理
的事件**：app 上一条挡不掉的提示，配一个「导出并释放」动作——先打包拉走，
人确认拿到了，才删。

> **这个死锁是故意留的。** 它逼出一次人的确认，而这正是「删掉唯一副本」
> 这件事应该有的门槛。

起飞门槛后来还加了一条，判据完全无关但性质相同：**认到外插的取走盘就不许出发**
（§7.5）。两条并列，都得过。

## 5. 值守与远程接管

### 5.1 值守屏只回答三个问题

不做「什么都显示」的仪表盘。三个问题，按优先级排：

1. **现在有没有需要我动身的事？**
2. **每只狗此刻在哪、在干什么？**（§2.4 那条 1KB/s 的位姿流就是喂这个的）
3. **有没有什么正在悄悄坏掉？**

第三个是仪表盘通常漏掉的，而它恰好是前面每一节的兑现处：

| 显示项 | 出处 | 不显示的话 |
|---|---|---|
| 任务包版本落差 | §3.4 | 人以为改生效了，其实没有 |
| `clock_skew_s` | §3.3 | 狗一脸认真地在错误的时间巡逻 |
| 回传队列积压 | §4.3 | 证据在狗上堆着，没人知道 |
| 盘水位 | §4.7 | 直到它拒绝出发那天才发现 |
| `min(power1, power2)` | §1.1 | 平均 36% 看着健康，随时趴下 |
| 镜像盘状态与同步落后量 | §7.6 | 一块坏掉或被刷没了的备份盘，一切看起来都正常，直到你需要它 |

这六条有个共同点：**它们的失败都是静默的。** 所以值守屏的正经定义是——
**把这套系统里所有静默失败变成可见的那块玻璃。**

### 5.2 告警只分三级，判据是「人的动作有什么不同」

| 级 | 人做什么 | 什么进来 |
|---|---|---|
| **P1** | **立刻动身** | 卡住、电量中止（§1.2 的 25%）、跌倒、定位丢失后暂停、急停被按 |
| **P2** | **今天之内处理** | 巡检有发现、盘 80%、回传积压、版本落差、时钟漂移 |
| **P3** | **只记录** | 正常完成、开始、换电池 |

> **两级如果会导致人做同样的事，那它们就是同一级。**

不做 1–5 分制。分了五级的系统，实际使用中人只认「要不要现在起身」这一个二值，
剩下四级是给做系统的人自我安慰用的。

### 5.3 升级看的是**有没有人确认**，不是**问题有没有解决**

修一个问题合理地可以花一小时。**没人看见**才是真正的失败。

- P1 未确认满 N 分钟 → **换通道**升级：大屏 → app 推送 → 声音
- **确认 ≠ 解决**，两个独立状态，分开存
- 确认必须**记名**：谁、在什么时候看到的

这条直接兑现 §1.4 那句「告警要能穿透『没人开着 app』的时段」。

### 5.4 告警风暴：同因聚合，但 P1 不跨狗合并

一个根因产生 50 条告警，真要紧的那条就被埋了。同一 `(狗, 类型)` 在窗口内合并成
一条，带计数和首末时间。

**但 P1 不跨狗合并**——两只狗同时卡住是两件事，要跑两趟。

### 5.5 能力划分：**移动只在手机 app 上，服务器没有这条能力**

> **服务器能让狗做的动作只有一个：停。**（§3.4 那条单向豁免）
> **移动指令只能从手机 app 发出，服务器上根本没有这个接口。**

这不是功能取舍，是把 §2.2 第 1 条**从纪律变成物理事实**。「服务器不在控制回路里」
写在文档里靠人遵守，写成「服务器压根没有移动接口」则不需要任何人遵守。
§3.4 那个不对称——**让它停不需要闭环，让它动需要闭环**——从此由产品形态强制执行，
而不是由代码审查强制执行。

**手机 app 的移动能力首要不是为接管准备的，是为扫图准备的。** 建图要有人牵着狗
走一圈，那是遥控最主要的工作量；接管是它的第二用途。

所以值守员在监控室看到 P1，他有且只有两个动作：
**在服务器上按停**，或者**掏出手机 app**。

这也修正 §3.9 里「服务器实现狗那套 `/api/*` 的超集」的说法：
**是超集，但移动类接口除外**——那几个接口服务器永远不实现。

### 5.6 接管是任务**挂起**，不是任务**中止**

`app/teleop.py:111` 现在是这样：

```python
if self._engine.running:
    raise TeleopBusy("任务在跑,先停任务再遥控 —— 两边一起动是在抢腿")
```

**「两边一起动是在抢腿」这个判断完全正确，原样保留。** 问题是它给出的唯一出路是
`abort`，而 abort 意味着这一趟就此结束。可值守员想做的往往只是
「过去把那个箱子挪开，然后让它接着跑」。

所以在「跑」和「中止」之间加一个状态：**挂起**。

- 接管 = 拿到 L1 租约（§3.5）+ 引擎进 `SUSPENDED` + **记下挂起时的点位与位姿**
- 挂起期间遥控可用，守死人照常
- **归还必须显式**

### 5.7 归还走哪条路，由位姿自动判定

人可能把狗开到了任务路线之外。归还时只问一个问题：**现在离挂起时那个位姿有多远？**

- **阈值内** → 原地续跑，从挂起的那个点位接着走
- **超出阈值** → **只能回原点重来**，不提供「就在这儿接着跑」

不给第二个选项，是因为后续路径规划的前提就是它还在路线上。

阈值先定 **2 米 + 30°**。**这个数是拍的，没有依据，现场拿到手感之后再调**——
写在这里是为了让下一个人知道它可以改，而不是把它当结论。

### 5.8 租约到期**不自动续跑**

人接管完，手机往兜里一揣走了，TTL 到期。

> **停在原地 + 升 P1。绝不自动续跑。**

理由和 §3.4 那个不对称完全一样。一只狗在「最后已知状态是人正在接管」的情况下
自己动起来，是这套系统里最不该发生的事。

### 5.9 **视频不在线，禁止移动**

现场遥控时人看得见狗周围；远程遥控看不见。没有画面还让人开着走，是在盲开。

这条是**安全约束，不是体验约束**，因此不设「确认后继续」的绕过口子：

- 对**人**：盲开的狗会撞到人
- 对**狗**：它自己也会被撞坏、被开下台阶

**要挪狗，就必须能看得见。** 网差到没有画面，那就走过去挪。

配套的保障在狗自己身上：`teleop.HEARTBEAT_TIMEOUT_S = 0.6`，链路一断狗自己停，
**不依赖任何远端来决定停**。所以链路质量在这里不是安全问题，是体验问题——
安全那一层已经由守死人和本条规则各自封死了。

## 6. 发现与鉴权

### 6.1 CPE 把「地址都一样」换成了「地址都不知道」

`app/identity.py` 开头那段判断今天是对的：

> 每只 D1 Max 的内网地址是同一套……**靠地址分不出谁是谁**

但 §2.3 定的拓扑改变了这件事。狗从 M12 网口接进 CPE、再进客户网络之后，
它在客户网段上拿的是 **DHCP 地址**。问题从

- **旧**：地址都一样——不可用，但**可预测**（永远是 `192.168.168.100`）

变成

- **新**：地址各不相同——可用，但**不可预测，而且会变**（续租、重启、换网段）

**这是我们自己引入的问题，得自己解决。** 三条路，按优先级回落：

| 顺序 | 手段 | 什么时候用 | 失效条件 |
|---|---|---|---|
| 1 | **问服务器要名录** | 联网档 | 没买服务器 |
| 2 | **mDNS**：`d1max-<SN>._d1max._tcp.local` | 局域网、无服务器 | 客户网络跨 VLAN 拦组播（常见） |
| 3 | **手填 IP** | 兜底 | 永远可用 |
| — | **AP 模式**：连热点前就看得见 BSSID | 无网时 | 不适用 |

第 1 条顺带又是一个真实的服务器差异化：**服务器是名录。**
客户有 5 只狗时，「我到底该连哪个地址」这个问题只有服务器能一劳永逸地回答。

### 6.2 SN 必须在装机时人工写死

`identity.py` 的候选链是对的，但它自己的注释点出了要害：

> 自动查出来的那些（设备树、DMI）标识的是**模组**不是**整机**——换过一次主板就变了

而归档是按 SN 归堆的。主板换一次，同一只狗的历史就断成两截，**而且不报错**。

> **装机清单第一项：填 `D1MAX_SN`，值取机身外壳上那个贴标号。**
> 交付验收检查 `GET /api/identity` 的 `source == "配置"`，
> **`provisional == true` 的机器不许出厂。**

这条听起来硬，其实不是：`resolve()` 里**人填的永远赢**，`D1MAX_SN` 就是个环境变量，
跟机器读不读得出设备树无关。**不存在「读不出真 SN 所以发不了货」的机器**，
填一下就是了。

要做的不是加代码——`Identity.provisional` 已经在了，`mobile/` 的名册也已经会显示
「序列号是兜底的」。**要做的是把它变成一道验收关。**

### 6.3 token 是匿名的，而 §5.3 要求记名

现在 `Guard(pin)` 是**一只狗一个 PIN**，换出来的 token 里没有任何人的信息。于是：

- §5.3 说「确认必须记名：谁、在什么时候看到的」——**做不到**
- §3.5 的租约说「谁持有控制权」——只能答「某个 token」

补法要诚实，分两级：

| 层 | 是什么 | 谁有 |
|---|---|---|
| **设备 PIN** | 证明你**物理上有权接触这只狗**。现状不动 | 都有 |
| **人的身份** | 证明**你是谁** | **只有服务器有** |

单机档的做法：**解锁时 app 报一个操作员名，狗只记录、不验证。**
而且必须在界面上把这件事说破：

> 这是**记账，不是鉴权**。单机模式下没有可信的人身份来源，谁都能填任何名字。
> **要经得起查的记名，得有服务器。**

不假装单机版能做审计。这既是诚实，也**恰好又是一条服务器差异化**——
而且是客户一旦需要就绕不过去的那种（§3.7 已列的「审计」，这里给了它具体形状）。

### 6.4 token 与租约怎么接：三个时间尺度，别混

| 机制 | 周期 | 管什么 | 出处 |
|---|---|---|---|
| **守死人** | **0.6 秒** | 腿还该不该动 | `teleop.HEARTBEAT_TIMEOUT_S` |
| **L1 租约** | **30 秒 TTL / 10 秒心跳** | 谁有权指挥 | §3.5，本节新定 |
| **token 闲置** | **12 小时** | 这个会话还算不算数 | `auth.TOKEN_IDLE_S` |

接口只有一条规则，但很硬：

> **租约必须绑在 token 上。token 一失效，租约立即释放。**

否则会出现「一个早就过期的会话还握着控制权」——那正是清单 #46/#47 里厂商犯的错。
**我们不能在自己这一层再犯一次**（§3.5 已经为此定了「租约是租约，不是锁」）。

反过来不成立：**一个 token 可以没有租约**，那就是只读观众——
§3.6 那 3 个会话里的另外 2 个。

### 6.5 狗的热点是**敌意网络**，就按敌意网络设计

**热点密码不能改。** 厂商做运维、调测、定位问题都要用它，改了等于掐掉厂商的支援通道。
这个约束是硬的，先认下来。

那就得承认它推出的结论：**射程之内，AP 上的流量是公开的。**
WPA2-PSK 下，知道密码的人抓到握手包就能解密别人的流量。所以射程内的人不只是能上网，
他还能看见 `/api/auth` 里那个 PIN，以及之后每个请求的 token。
`auth.py` 开头写的「射程之内谁都能上这个网」，**实际比它说的还严重一层**。

先量一下这个暴露面——比直觉小：**§2.3 已经把 AP 降级成低保通道**，
日常流量全走 CPE 进客户网络。AP 只在「客户网崩了 / 5G 没信号 / 狗卡在角落」时才用。
**这是应急通道的安全问题，不是主通道的。**

三条措施，从贵到便宜：

1. **TLS + 证书钉扎在手机 app 里。** 自签证书在浏览器上是持续的告警噪音
   （而噪音会训练人忽略告警），但**在 Flutter app 里钉扎一张自签证书比公共 CA 更强**
   ——它只信我们那一张。而 **app 才是交付物**，浏览器只是开发和现场调试用。
   这条是真解，不是缓解。
2. **PIN 永不上线：改成质询-应答。** 狗发 nonce，app 回 `HMAC(PIN, nonce)`。
   就算 TLS 那层出了问题，**长期口令也从来没上过网**，被偷的最多是一个会限时失效的 token。
3. **AP 上签发的 token 用短闲置期**（30 分钟，不是 12 小时）。
   AP 是应急通道不是办公通道，没有「一整天不掉线」这个需求。

另加一条写进文档而不是写进代码的：

> **AP 模式下，信任边界是「射程」。**

这不是缺陷，是这台机器的物理事实。**写出来是为了不让人误以为 PIN 在那儿能挡住什么。**

### 6.6 落到代码

| 文件 | 改动 |
|---|---|
| `app/auth.py`（326 行） | `unlock` 加 `operator` 并记进 token（§6.3）；PIN 改质询-应答（§6.5）；AP 来源的 token 用短闲置期。**限速、`?token=` 白名单、内存存储三条现状全部不动** |

## 7. 装机、升级、回滚

### 7.1 一切从 #46/#47 那条约束推出来

厂商侧的事实（清单 #46/#47）：**SDK 会话是独占的，而且没有交接机制。控制权一旦被
上装拿走就再也响应不了，只能抢开机窗口。**

从这条推出三个不可谈判的结论：

1. **我们的服务必须开机自启，而且要在上装之前抢到那个窗口。** 抢不到，这只狗这一轮
   开机就是死的——不是「功能受限」，是**读也读不进去、控也控不进去**。
2. **升级必须整机重启。** 因为重启我们自己的进程 = 释放 SDK 会话 = 下次不一定抢得回来。
   「热更新一个 Python 文件」这条路在这台机器上不存在。
3. **自动升级绝不能有。** 凌晨三点自动升了一次、没抢回会话，狗就那么死到天亮，
   而没有任何人知道。**升级必须是有人按下去、有人看着结果的动作。**

第 3 条是本节最重要的一句。它不是保守，是因为**失败的代价是一台需要有人到现场去
按电源的机器**——而客户现场往往没有这个人。

### 7.2 自检要重到「显得过分」为止

既然每次尝试都要付一次重启，那自检就该在**重启之前**尽可能多地把问题挡掉。

升级前（新版本还没生效时）跑一遍：

| 查什么 | 不过就拒绝升级 |
|---|---|
| 包完整性 | 哈希对不上 |
| 版本兼容 | 新版要求的任务包 schema 高于现存包（§3.2） |
| 磁盘 | 装不下新版 + 保不住回滚位 |
| 电量 | `min(power1, power2)` < 50%——重启途中断电是最脏的一种坏法 |
| 任务态 | 有任务在跑，或有活跃的 L1 租约 |
| 备份 | 见 §7.5：**提示，不阻断** |

重启后（新版本已生效）跑一遍，这一遍是**回滚的判据**：

1. 进程起来了
2. **SDK 会话抢到了**——这一条是核心，抢不到就等于没升级成功
3. 相机、位姿、地图三个桥都能应答
4. `/api/identity` 返回的 SN 跟升级前是同一个

### 7.3 回滚靠「两份 + 一个符号链接」，不靠包管理器

盘上永远有两份：

```
/opt/d1max/
  releases/
    2026-09-06-a3f9c1/     ← 上一版，不动
    2026-09-20-77b2de/     ← 新版
  current -> releases/2026-09-20-77b2de
```

升级 = 解包到新目录 → 改 `current` 指向 → 重启。
回滚 = 改 `current` 指回去 → 重启。**回滚和升级是同一个动作，只是方向相反**，
所以回滚这条路不会因为「很少走」而烂掉——它跟升级共用全部代码。

**只留两份。** 第三份没人会用，只会占盘，而盘是 §4.7 里那个已经紧张的资源。

**自动回滚的触发只有一条：7.2 的重启后自检没过。** 过了就算成功，之后再出什么问题
都归人判断——自动回滚的判据必须窄，否则它自己会变成故障源。

### 7.4 OTA 是厂商的事，但我们必须挡在它前面

厂商的开发指南写得很直白：

> 算力板为 Orin NX……**需做好备份管理，刷机或 OTA 升级可能会被刷新**

关键在于：**OTA 推送了，客户还得授权才会升。** 所以这不是一个「随时会从天而降」的
风险，而是一个**有预告的时刻**。

真正的风险因此不是技术上的，是流程上的：**授权的那个人不会想起来先备份。**

对策是一条规程加一个按钮：

1. app 上有一个 **「升级前备份」**：同步一次 → 校验 → 提示「可以拔了」
2. 交付文档写死一句：**收到厂商 OTA 通知后，先点这个按钮，再授权**
3. 值守屏在「距上次备份超过 N 天」时提示（§7.6）

**不要把这件事讲得比它实际更吓人。** 吓人的说法一旦被客户发现是夸大的，
比不说更伤。

### 7.5 备份盘：能力必选，硬件可选

先把两件被混为一谈的事拆开——它们**防的不是同一种坏**：

| | 镜像盘 | 取走盘 |
|---|---|---|
| 防的是 | 系统盘被刷、盘坏、误删 | **狗整台没了**——被偷、烧了、摔了 |
| 在哪 | 装机时装进机器内部，不外露 | 人来的时候插一下，用完拔走 |
| 谁碰 | 没人碰 | 客户 |
| 依赖人 | 否 | 是 |

镜像盘再可靠也挡不住第二种，因为**它跟狗在一起**。

**镜像盘是选配硬件。** 有服务器的客户不需要（备份已经是自动异地的），单机档的客户
自己权衡。装的时候优先级：

| | 方案 | 判断 |
|---|---|---|
| 甲 | **独立物理盘**（空 M.2，或一块盘固定在仓内） | 最好。OTA 刷的是启动设备，碰不到它 |
| 乙 | 仓内短线 + 盘绑在里面 | 一分不外露，靠谱 |
| 丙 | 超短 nano 盘（凸出约 5mm） | 能接受，但最脆 |
| ✘ | **同一块盘上的另一个分区** | **不算备份。** 刷机重建分区表，两个一起没 |

最后一行必须写死。「独立分区」听起来像备份，实际上是心理安慰——而这是那种
**发现的时候已经太晚**的错误。

**它在文档和界面上叫「备份盘」，不叫「U 盘」。** 名字决定客户会不会伸手去拔它。

**为什么不能常年外插一块 U 盘：** 凸出二十毫米的盘挂在走动的狗侧面是个**杠杆**。
先坏的不是盘，是**接口**——接口撬坏了整个扩展仓的 USB 就废了，而那不可现场维修。
为一块六十块的盘赌上扩展仓，不划算。

**取走盘则相反，凸出来无所谓**，因为它只在「狗站着不动、人就在旁边」的那几分钟里
存在。但要有一条硬规则兜住：

> **认到外插盘时，禁止起飞。**

跟 §4.7 的盘水位一样是个 start gate，狗自己看得见、自己拦。这条把「凸出来」从一个
持续风险压缩成一个有人看着的短窗口。

### 7.6 备份怎么做

**app 看见的不是 U 盘，是狗看见的 U 盘。** 手机不接触那块盘，它问狗
`GET /api/backup/targets`，狗回「我认到哪些盘、容量、剩余、上次同步到什么时候」。
这个区别是有后果的：**没有手机在场时，同步照常进行。**

**认盘必须靠标记，不能见 U 盘就写。** 客户插上来的可能是相机卡、可能是他自己的
资料盘，往人家盘上乱写不可接受。

- 首次：app 上点一次初始化 → 狗在盘根写 `.d1max-backup/target.json`，
  记 **这只狗的 SN** 和 **`role`**（`mirror` 或 `transfer`）
- 之后：只认带标记的盘；`role` 决定它是自动同步还是手动取走
- 起飞前检查认到 `role != mirror` 的盘就拒绝，提示「有临时盘插着，拔掉再走」

记 SN 是为了**拦住把 A 狗的备份盘插到 B 狗上**。混一次，§6.2 那条「归档按 SN 归堆」
就全乱了。**插错盘要明确拒绝并说清楚原因，绝不默默合并。**

同步的几条规矩：

- **只增不删。** 狗上按水位删掉的（§4.4），备份盘上不跟着删——否则备份成了狗的
  复读机。**狗上删掉的那些东西，正是备份盘存在的全部理由。**
- **跳过当前正在写的那个 run 目录。** `archive.py` 的 `read_events` 遇到坏行是抛异常，
  同步出一个末行截断的 `events.jsonl`，事后读不出来。下一轮自然会带上它。
- **写完重新算哈希核对**，跟 §4.2 一个规矩。备份是最不该「以为写成功了」的地方。
- **备份盘满了不删旧的**（那是唯一副本），报 P2 停同步，跟 §2.5 同一个道理。
- **必须有「安全弹出」**：停同步 → `sync` → 提示可以拔了。

**「可选」的三条纪律**（不写死就会走样）：

1. **备份绝不能成为起飞的前置条件。** 认到盘就干，认不到就不干，巡检照跑。
   这一条要在代码里写死，否则「选配」迟早变成「装了才能用」。
   （这跟 §7.5 那道「认到外插盘就不许出发」不矛盾：那道门拦的是**插着的临时盘**，
   拦的理由是机械安全；**没装备份盘从来不是拦停理由**。）
2. **没配镜像盘时，§5.1 那一项不许一直红着。** 显示中性的「未配备份盘」，只在
   **两个时刻**主动顶到人脸上：授权 OTA 之前、保留期到期之前。
   **常年报警的东西等于没报警。**
3. §5.1 那块玻璃上加第六项：**镜像盘还在不在、上次同步什么时候、落后多少。**
   一块坏掉或被刷没了的镜像盘是个完美的静默失败——一切看起来都正常，
   直到你需要它。

### 7.7 手机遥控：这一节把它定完

遥控的后端契约在 `app/teleop.py` 里已经跑着，本节只定界面侧和几个没定的数。

**界面在 app 里原生做，不嵌 WebView。** 两个场景：

| | 自主操控（漫游） | 扫图 |
|---|---|---|
| 一拍时长 | 默认 0.4s | **更短**——走得碎、走得稳 |
| 转向上限 | 满 | **压低**——转太快里程计会丢，图就废了 |

扫图那趟的产出是**一张要用一年的图**，走坏了要重来，值得为它单独限速。

**布局：** 视频铺满，两个虚拟圆心摇杆半透明压在视频上。
**左下 = 前后左右（平移），右下 = 只转向。**

**左摇杆吸附到单轴。** 取 |x| 与 |y| 中大的那个，另一个归零——厂商自带遥控器就是
这个行为，推 45° 也只走一个方向，不斜着走。**这条待真机确认**（见 §7.9）。
两个摇杆同时推是允许的：左杆前推 + 右杆右推 = 向右画弧，这也待真机确认。

**为什么必须吸附到单轴：** 底层控制量是**百分比不是速度**，而且死区不小
（清单 #37/#38）——`0.11` 几乎不动，`0.3~0.5` 才真的迈腿。现在的代码逐轴把非零值
顶到死区之上。如果左摇杆能出二维组合，斜推时两个分量会被各自顶到各自的死区，
**合成方向就不是人推的方向了**。吸附到单轴，逐轴顶死区才成立。

**但 `MIN_LAT` 仍然要单独标。** `teleop.py:121` 现在拿 `MIN_FWD` 给横向凑数——
螃蟹步和直行是完全不同的步态，凭什么同一个数。纯横移那一档还是要顶对死区。

**松手必须主动发停。** 摇杆是连续的，底下是一拍一拍的。按住期间持续发拍
（约每 0.3s 一拍，稍重叠保证不卡顿）；**松手立刻发一个全零的停**，不能只是
「不再发拍」等它走完——那要多走最多 0.4s。0.6s 的死人开关是兜底，不是正常路径。

**视频掉线，摇杆直接变灰失效**——不是弹框让人点掉，是按不动（§5.9）。

### 7.8 视线之外的遥控：不禁，但要留痕

不硬禁远程遥控。但要认清一件事：**每次都弹同一个框，第三次就被条件反射点掉了**，
那种提示在事后什么也兜不住。

所以分两档：

- **现场模式（默认）**：轻提示——「请与机器狗保持在同一视线范围内」。
  人和狗都在视野里，遥控延迟带来的风险自然就低。
- **远程模式**：需要**主动切过去**，切的时候确认一次，并且**这次确认自动写进事件流**
  ——谁、什么时候、切了远程遥控。

> **留痕才是真兜底。** 一个被点掉的弹窗证明不了任何事；一条带署名和时间、
> 跟着 §4 归档走、删不掉的事件记录可以。

跟 §5.3「确认必须有归属」是同一条道理。

**§5.9「视频不在线禁止移动」不受本节影响，仍是无豁免的硬规则。** 本节说的是
「视频在线、但人不在现场」这一档。

## 8. 测试策略

现在的家底：`tests/` 下 67 个文件、**1217 个 test 函数**，整套约 240 秒；
`mobile/` 那套 56 条，一秒出头。两套各跑各的，互不相干。

本节要回答的只有一个问题：**同一份代码要同时在单机和联网两种形态下成立，
怎么测才不至于把测试量翻倍、又不至于漏掉那个没跑到的组合。**

### 8.1 先是架构约束，才是测试策略

如果「有没有服务器」变成散落各处的 `if`，测试矩阵会炸，而**没被跑到的那个组合
一定会出厂**。所以第一条不是测试规矩，是代码规矩：

> **形态差异只允许存在于三个可替换对象里：上传目标、名录来源、鉴权来源。
> 其余代码不许知道自己跑在哪一档。**

管住这个，绝大多数测试根本不需要关心形态。管不住，下面几条全是白写的。

### 8.2 单机/联网是两个 target + 一个能力集，不是两套测试

`tests/contract/conftest.py` 里已经有这套机械装置了——`BACKEND_FACTORIES`
加能力集，以及那条规矩：

> 没声明能力的后端要过 `test_不建图的后端必须明确拒绝建图` —— 它必须**拒绝**
> 而不是假装成功。少了这一条，「不支持」就跟「悄悄什么也没干」分不出来了。

形态差异跟「厂商后端会建图 / 自建后端不会」是同构的，原样搬过来：

- 联网档声明 `upload` 能力，单机档**不声明**
- 不声明的必须过 **`test_没有上传目标的形态必须明确说没有`**——不许悄悄成功

**这条是 §2.5 那个 bug 的疫苗。** 当时写「未上传的绝不删」，单机档因为永远没有
上传对象，所有文件永远算「未上传」，狗迟早永久停飞。
**「悄悄成功」和「明确拒绝」的区别，就是这个 bug 会不会被测出来。**

### 8.3 只有四处跑两遍

| 跑两遍 | 为什么 |
|---|---|
| 归档与删除（§4.4/§4.6） | 两套盘策略，由「有没有上传目标」选 |
| 起飞门槛（§4.7） | 两档的诊断文案不同——「回传已中断 N 天」vs「保留期没到」 |
| 鉴权（§6.3） | 单机是**记账**，联网是**鉴权** |
| 发现（§6.1） | 名录 / mDNS / 手填三条链 |

**其余一遍。** 任务引擎、判读、遥控、协议编解码跟形态无关。

全套跑两遍会把 240 秒变成 480 秒，而其中九成的重复**零信息量**——
慢下来的套件最后的结局是没人跑。

排程的版本落差（§3.4）是**联网独有**，单机档压根没有那个场景，
不必造一个假的服务器去测它。

### 8.4 服务器要被**同一套** app 契约打过

§3.9 承诺「服务器实现狗那套 `/api/*` 的超集，移动类接口除外」。
兑现的方式就是把服务器当成契约测试的**第三个 target**：

> 同一份用例，指向狗跑一遍、指向服务器跑一遍，除了移动那几条，应该全绿。

不绿，就说明「一套界面同时对得上狗和服务器」是句空话——而这句话是整个产品
分档的地基（§3.7）。这不是锦上添花的测试，**它是那个承诺唯一的证据**。

移动接口那几条要有对应的 **`test_服务器必须拒绝移动`**，理由同 §8.2：
「没实现」和「实现了但什么也没干」必须能分开。这也是 §2.2 规则 1 从纪律
变成事实之后，唯一能守住它的东西。

### 8.5 三条硬规矩

**63 个协议样本是冻结的，只增不改。**
`tests/protocol/fixtures/` 那批是从厂商私有文档逐字抄下来的，是我们对那套协议
理解的**唯一书面证据**。改一个就是悄悄改了理解，而没有任何人会发现。
协议层任何改动之后，这 63 个必须还能原样解出来。

**时间必须可注入，绝不 `sleep`。**
本版新增的东西里，退避重试（§4.3）、token 闲置期与租约 TTL（§6.4）、
心跳超时（§5）、保留期（§4.6）全是时间逻辑。一个 `sleep(5)` 进了套件，
一年后套件就是十分钟。**这条没有例外。**

**回滚必须被真的走过一次，而且要故意失败一次。**
只测成功路径的回滚等于没测——它的全部意义就在失败那条路上。
做法：§7.2 的重启后自检判据**做成纯函数**（输入=四项检查结果，输出=继续/回滚），
单测把组合跑全；重启那一层用装机验收里的一次演练覆盖，
**演练必须包含一次故意做坏的升级包**。

### 8.6 仿真测不到的东西，点名列出来

这一节存在的唯一理由是：**别因为仿真全绿就以为可以出厂。**

| 测不到 | 为什么 |
|---|---|
| **SDK 会话抢占**（#46/#47） | 仿真里没有「上装」这个竞争者。而这是 §7.1 整节的地基 |
| **死区的真实数值** | `MIN_FWD` / `MIN_LAT` 是量出来的，不是推出来的 |
| **视频端到端延迟** | §5.9 的「看得见才准动」整个建立在这个数上 |
| **电池热插拔的电压跌落** | 仿真里换电池不掉电 |
| **OTA 到底抹掉了什么** | 只有真刷一次才知道 |
| **摇杆是否吸附单轴** | §7.7 的布局建立在这条上 |

这六条只能真机。§7.9 那张现场表已经是这份验收单的一半，
**交付前必须把它走完，而不是看着 1217 个绿点签字。**

### 8.7 手机端

`mobile/` 那套的价值在于**离机可测**——名册屏现在就是整屏离线跑的。
遥控屏加进来之后，三条核心行为仍然是纯逻辑，不许为了测它们去起真机：

1. **左摇杆吸附单轴**：给一组 (x, y)，断言输出只有一个轴非零
2. **松手主动发停**：断言松手那一刻发出的是全零，而不是「不再发拍」
3. **视频掉线即变灰**：断言按不动，而不是弹框

第 2 条尤其要测：靠 0.6 秒死人开关兜住的「松手」是**正常路径走了异常通道**，
测试是唯一能把这两者分开的地方。
