# W18 连续录像 · 设计与完工报告

> 工单：「常开录制、事件前后缓冲、片段上传、回放索引；顺带 H.264」。分支 `w18-recording` → PR。设计与报告合一份。

## 摸底（2026-10-04）

- 狗上相机走 RTSP（真狗 `rtsp://192.168.234.1:8554/front|back`）。
- 站点有人看的时候，才按需推一路加密 SRT 过来（W00c5b）；没人看就什么都不留。
- 原文说的 `recorder.py` 是导航协议帧的录制，跟录像无关。

**用户决定**（2026-10-04）：
- 决策 31：**站点优先录**。WiFi 断了狗上存着，WiFi 回来补推到站点，狗上清掉。这比我给的两个选项（狗上滚动录、只传事件片段 / 一直推站点录）都好。
- 决策 32：传到站点的录像**留 30 天**。

## 怎么做的

**一条路，不切换**：狗上一直录，一分钟切一段；切好的那段马上传站点，站点确认了才删狗上那份。
- WiFi 好：站点晚一分钟就有。实时画面照旧走 W00c5b 那条，不受影响。
- WiFi 断了：片段攒在狗上，回来自动补传、补完清掉。

为什么不做「平时推流到站点录，断了切到狗上录」：切换的那几秒会丢，而且要两套录制、两套对账。现在只有一套。上传沿用运行记录那一套：分块续传、站点按自己存下的字节回哈希、狗对上了才算传到、确认了才删。

### 狗

| 块 | 内容 | 文件 |
|---|---|---|
| 录 | 每路相机一条 ffmpeg：<br>- `-c copy` 不转码，相机原样的 H.264；仿真测试图编码；相机若不是 H.264 用 `--video-transcode`；<br>- 一分钟一段；<br>- **分片 mp4**：被杀掉、断电，正写着的那段照样放得到断的地方；<br>- 文件名是**狗的钟**（UTC）的时刻 | `recording.py` |
| 挪 | 写完的段从暂存 `.rec/<相机>/` 挪进录像发件箱 `video/<相机>/<时刻>/video.mp4`。正在写的那段（最新的、可能刚开还是空的）不碰；名字不合规的、写完了还是空的扔掉 | `recording.py` |
| 传 | 发件箱多一块 `video`，跟运行记录同一条上传线程轮着传，传到站点 `/video/api/intake/put`。**不算进盘况**：录像在发件箱里，但运行记录那一块量用量时不算它，攒多了不会让狗拒巡检 | `outbox.py`（`not_counted`、`uncounted`）、`main.py` |
| 配额 | 狗上攒着没传的超过 `--record-max-gb`（默认 30 GB），或者盘用到 80%，从最旧的删起，报一次 `recording_dropped`。巡检归档优先于录像 | `recording.py` |
| 录不了 | ffmpeg 自己退了（相机不通、盘写不进），报一次 `recording_failed`，隔 10 s 重起；切出新的段报 `recording_ok`。录像起不来（目录建不了）**不连累代理**，照常起 | `recording.py`、`runtime.py` |
| 开关 | `--record auto`（缺省）：真狗录前后两路、仿真不录；`--record none` 不录；`--record back` 只录后面。要 `--outbox`。能力报文报 `recording: {cameras, segment_s}` | `main.py`、`runtime.py` |

### 站点

| 块 | 内容 | 文件 |
|---|---|---|
| 收 | 收件口多一路 `/video`（mTLS，狗号按证书填）。路径只收 `<front/back>/<UTC 时刻>` + `video.mp4`，别的一律不收。存 `recordings/<狗>/<相机>/<日期>/<时刻>.mp4`；收齐了登记进 `recordings` 表（库结构升到 19） | `recordings.py`、`intake.py`、`d1max_contract.intake` |
| 留 | 30 天到期删（决策 32），从站点**第一次收齐**算（外审后），每 10 分钟查一次；标了「留着」的不删 | `recordings.py`、`main.py` |
| 盘 | 站点盘剩不到 10% 就从最旧的（没标留着的）删起，删到 15%，报一次 P2 `recording_trimmed`。30 天两路连续录像要 2–3 TB，站点盘未必有；不先删录像的话，盘到了收件口的底线（剩 2%），所有上传都停，巡检的照片、记录也传不上来了。录像**不进备份**（太大） | `recordings.py` |
| 接口 | `GET /api/recordings?robot=&camera=&since=&until=`：一段盖住那一刻也算在内，最新的在前。`GET /api/recordings/<id>/video`：mp4。这两个谁都能用（`view`）。`POST /api/recordings/<id>/keep {keep}`：值班的人、管理员能用（`review`） | `api.py` |
| 告警 | P2：`recording_failed`（某路录像断了）、`recording_dropped`（狗上没传到站点的删了几段）、`recording_trimmed`（站点为腾盘删了） | `alert_sources.py`、`alerts.py`、`main.py` |

### 手机、桌面

- 单狗页「录像」：
  - 一分钟一段，按 30 分钟一屏「更早 / 更晚」翻，按前、后相机筛；
  - 点一段下载下来放：走 app 自己那条钉证书的连接，系统播放器不认站点的自签证书。手机、Mac 在 app 里放（官方 `video_player` 插件），Linux、Windows 桌面交给系统播放器（这两个平台插件没有实现）；
  - 值班的人、管理员能标「留着」。
- 告警现场页（W17）多一个「现场录像」：看告警那一刻前后各 15 分钟，盖住那一刻的那段标出来。站点那一行的告警没有这个按钮。

## 外审第一轮（2026-10-05）：FIX-THEN-APPROVE，3 条阻断，已修

**阻断 1：录像的告警永远不会出现。**
- `Recorder` 报事件用的是私有字段 `_emit`，运行时接线却写到了 `emit` 上。
- Python 只是多出一个没人读的属性：ffmpeg 退了、录回来了、删了没传的，事件全丢，站点那三条告警从来不会出现。
- 原来的运行时测试用的是带 `emit` 的假对象，盖不住这个错配。

修法：
- `Recorder` 只留一个公开的 `emit` 字段，接线、内部调用都用它。
- 新测试用**真的** `Recorder` 接进 `AgentRuntime`：ffmpeg 退出、配额删除之后，`events.jsonl` 里真有 `recording_failed`、`recording_dropped`。去掉接线这条测试就红。

**阻断 2：30 天留存按狗的钟算。**
- 清理和盘紧时的「最旧」都按片段名里狗的钟 `start_ms` 算。
- 狗钟慢半年（真狗出过）时，刚收到的录像下一次清理就被当成过期删了；快半年时留得远超 30 天；几只狗钟差不同时，盘紧先删钟最慢那只的新录像。

修法：
- 留存期、盘紧时的先后，都按站点**第一次收齐**的时刻 `received_ms` 算。
- 重传不刷新 `received_ms`。
- 狗的钟只用来排时间线、查某一刻前后。

补的测试：
- 狗钟慢半年、快半年的两段，都从站点收齐那天起留 30 天，第 30 天零 1 毫秒一起删；
- 两只狗钟差不同时，盘紧先删先收齐的那段（不是钟最慢那只的）；
- 第 20 天重传同一段，不延长留存。

**阻断 3：文件删不掉也删登记，还报「腾了盘」。**

后果：
- 只读挂载、权限不对时，文件还在，登记却没了；
- 录像从界面上消失，以后再也清不到这个文件；
- 盘没腾出来却报「删了 N 段」；
- 大量失败时能把索引删光，盘照样满，最后巡检证据也传不上来。

修法：
- `_delete` **文件真没了才删登记**，回删成了没有。
- 按期删、腾盘删，都只算真删掉的。
- 腾盘时删不掉的不再挑，一轮一段都删不掉就停（不空转）。盘还紧又有删不掉的，报一条 **P1** `recording_delete_failed`：再拖下去盘到底线，巡检的照片、记录都传不上来。
- 狗上的配额删除同样改成确认目录真没了才算进 `recording_dropped`。

补的测试：
- 文件删不掉时，登记、文件都还在，按期、腾盘都记 0，报一次删不掉；好了之后下一拍照样删掉；
- 狗上删不掉的那段不算进「删了几段」。

修完全量 Python 0 失败。

突变 8 条全杀：
- 去掉运行时的接线；
- 按狗钟算过期；
- 按狗钟挑最旧；
- 重传刷新收齐时刻；
- 删不掉也删登记；
- 删不掉也算数；
- 不报删不掉；
- 狗上删不掉也算。

## 已知限制、要你做的

- **真狗没录过**：
  - 相机 RTSP 地址、码流是不是 H.264、码率多大，都没在真狗上量过（W00c5b 起就是待测）。
  - 真狗起来之后看站点「录像」里有没有一分钟一段地进来。不是 H.264 的话，在 `/etc/d1max/env` 的 `D1MAX_AGENT_ARGS` 里加 `--video-transcode`（Orin 上转码吃 CPU）。
- **站点盘**：30 天两路要 2–3 TB（按每路 4 Mbps 估）。站点主机盘小的话，会提前删并报 P2 告警。要么加盘，要么 `--record front` 只录一路。
- 狗上配额 30 GB，按每路 4 Mbps 大约 8 小时。WiFi 断得比这还久，最旧的会删掉并报告警。
- 录像上显示的时刻是狗的钟（狗的钟不准站点会报 `clock_skew`，W09d），查录像时心里有数。留存不受狗的钟影响（外审后）。
- 「事件前后缓冲」不用另做：站点有全部录像，告警现场页直接跳到那一刻前后。
- 录像不进站点备份（太大）。
