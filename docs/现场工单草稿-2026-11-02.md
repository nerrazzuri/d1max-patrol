## 1. 开机起的旁路没订上里程 / IMU，代理起不来，开机守卫把好包退了（3ao.1）

- 现象：整机上电后 `d1max-field-sidecar`（1970 年时间戳起的）只发 `state` 帧，**没有 `odom`、`imu`**。代理每次「连上旁路进程 3.0s 还没收到状态帧与里程帧」退出；新包装上连着 2 次起不来 → 守卫退回上一版（两次）。
- 证据：只读连 127.0.0.1:8090 收 5 s：`{'hello': 1, 'state': 7}`；`systemctl restart d1max-field-sidecar` 后 4 s：`state 5、odom 67、imu 78`，代理马上起来、新包坐实。遥控器占控制权（`another master exists`）时也是这样，但这次 held=1 之后照样没里程。
- 猜测：旁路在运控板还没准备好时订阅里程 / IMU，订失败没重试；心跳状态走另一条所以有。
- 建议：
  1. 旁路：收不到里程 / IMU N 秒就重新订（或整个 SDK 会话重连），日志里说清楚。
  2. 代理：报错里分清「旁路没连上」和「连上了但没里程」，后者提示「重启旁路」。
  3. 开机守卫：起不来的原因是旁路那头（不是新包本身）时不该算坏包次数；至少日志写明退回原因。

## 2. 设备身份：Orin 的芯片编号是厂家占位 `DummySN`，代码照收（3ao.2）

- 现象：`/proc/device-tree/serial-number` = `DummySN\0…`。`devid.read_hw_id` 只拒空、全 0，`DummySN` 照算 → 所有这种 Orin 的 `hw_id` 一样（`sha256("d1max-hw|DummySN")`），「绑芯片」等于没有。C40221 今天按用户决定照签（只测流程），出厂台账里那条要注明。
- 也读不到：`/sys/devices/soc0/serial_number` 不存在；`soc_id`=35、family Tegra；`/sys/bus/nvmem/devices/` 有 `fuse`、`module1`。
- 建议：
  1. 拒占位值（`DummySN`、全同字符、`0123456789` 之类），报「读不到芯片编号」。
  2. Orin：改读 Tegra 熔丝里的唯一编号（ECID / UID，`fuse` nvmem，root 可读），在 C40221 上核。
  3. RK3588 真板到了核 `cpuinfo Serial` / efuse 是不是真唯一。
  4. 改好以后 C40221 重签一次（设备钥匙不用换）。

## 3. 退回旧版以后命令行工具和代理不是同一版（3ao.2 附带）

- 现象：`/opt/d1max/bin/python` → `/opt/d1max/bin-venv`，每次 `install.sh` 都更新（11:04 装新包时就是新代码），守卫退回时**不跟着退**。今天守卫退回 649214ce 以后，`bin/python` 跑的是 0d7956f3 的代码、代理跑的是 649214ce。
- 影响：现场照文档敲 `sudo /opt/d1max/bin/python -m d1max_patrol.cli …` 跟代理版本不一致；这次正好是新的才没出事。
- 建议：`bin-venv` 跟着槽走（或退回时也切），或者文档里命令写 `/opt/d1max/current/venv/bin/python`。

## 6. 机器人网口被别的东西占满时没有任何提示（视频断）

- 现象：网页视频一断一断，站点日志一直「续期没成：等机器人的回执超时」、SRT「delayed for 3013 ms / RCV-DROPPED」。查了 40 分钟才找到：**厂家 ROS1 桥 `parameter_bridge`（PID 3116）往竞品上装 192.168.113.101 发 ~360 Mbit/s**，机器人只有一个有线口 `enP8p1s0`（三个网段都在上面，热点路由、运控板也在），出口 380 Mbit/s。SIGSTOP 它以后出口≈0，视频马上正常、续期不再超时。（10-29 那天上装关着，桥发不出去。）
- 建议：
  1. 诊断快照（`ops_diag`）加：各网口收发速率、哪个进程的连接在大量发（`ss -tin` 的 `bytes_sent` 差值就够）。
  2. 视频续期连续超时、命令往返正常时，站点提示「机器人网口可能被占满」。
  3. 现场手册：上装 V2 之前接竞品上装的机器人，先看一眼 `enP8p1s0` 出口。

## 9. Nav2 回程在同一处卡住：MPPI 跟守卫意见不一致（3aj.5，最要紧）

- 现象：3 趟回程都在 G1 原地转完身、往回绕方块的 (2.5–2.75, −2.5–−2.7)、朝 46–68° 出事：15 s、53 s 不动，第 3 趟定位丢失失败（见 13）。去程（方块在机器人右边）3/3 顺。
- 证据（回程 2，11:51:18–11:52:16）：守卫「拦住 Nav2 的速度」9 次，最近一处机身前 0.4 m、左 0.6–0.7 m（方块角）；Nav2 controller「Failed to make progress」→ 清代价地图 → 重来；planner 一次「no valid path」；控制循环一直「missed its desired rate of 20Hz」。机器人位置 50 s 内只变 2 cm。
- 原因：MPPI 用 1.03×0.58 m 机身 + 0.6 m 膨胀觉得过得去，代理守卫的扫过区更保守，把速度拦成 0；Nav2 不知道被拦，一直发、一直没进展。
- 建议：
  1. 守卫用的机身和余量跟 Nav2 的 footprint / 膨胀对齐（同一份参数）。
  2. 守卫拦了要回告 Nav2（转接节点发「被挡」让 Nav2 换路 / 退），不是只截速度。
  3. 用包 `nav2-c1-1-114505` 11:51–11:52 那段在台式机上复现。

## 10. 死区整形：前进 0.2 m/s 门槛把 MPPI 的小速度清零；转向门槛单位不对（3aj.5、3aj.7）

- 代码：`nav2_nav._deband`：前进门槛 `max(HAL deadband_vx, 0.13)`，HAL 缺省 `deadband_mps=0.2` → 0.1 m/s 以下当 0、0.1–0.2 抬到 0.2；转向 `MIN_TURN_RPS=0.07`，0.035 以下当 0。
- 问题：
  1. MPPI 在障碍边上、起步收尾都发 <0.1 m/s → 全清零 → 机器人不动 →「Failed to make progress」（卡住的一部分原因）。
  2. 0.07 rad/s 是 10-29 量的**实际**转速（比例 0.10 时实际 0.069），整形用在**命令**上：命令 0.07 rad/s ≈ 比例 0.047 → 实际 0.015 rad/s，等于不转。命令要 ≈0.15 rad/s（比例 0.10）才转得起来。
- 建议：死区按命令单位填（前进按 10-29：比例 0.2 才走、后退 0.15；转向比例 0.10）；把死区告诉 MPPI（vx_min 正向下限 / 噪声），别让它规划出走不了的速度；用包里 `/cmd_vel` vs 实际位姿核。

## 11. 原地只换朝向的目标 Nav2 规划不出路；贴墙起点在危险区里（3aj.7）

- 现象：同一位置换朝向 10°：Smac Lattice「failed to create plan, no valid path found」。屁股离墙 <0.4 m 时 60 s 超时没动；离墙 0.8 m 时靠 Nav2 后退脱困（退 0.3 m 再回来）才转到。33° 那次能转（控制器直接转了）。回程每趟到起点也是先绕一圈再转到 −90°，守卫拦（机身后 0.1 m 是墙）。
- 建议：
  1. 离目标位置在容差内（xy ≤0.2 m）只差朝向时，代理自己原地转（不交 Nav2），或给 Nav2 加 RotationShimController。
  2. 起点在危险区（贴墙停）时先按 3ah.14 的办法往前挪开再交 Nav2。
  3. 后退脱困（BackUp）要看身后：这次往墙那边退了 0.3 m（离墙还剩约 0.5 m），守卫要管到它。

## 12. MPPI 在 Orin 上跑不满；运动模型是 DiffDrive（3aj.5）

- 证据：controller「Control loop missed its desired rate of 20.0000Hz」几乎每秒；bt_navigator「tick rate 100 exceeded」；planner 1.83 Hz < 2 Hz。厂家导航 5 个进程已 SIGSTOP、ROS1 桥已 SIGSTOP 也这样。合并雷达节点一个就 ~170% CPU，MOLA 丢 30% 帧（worker busy）。
- 建议：MPPI `batch_size` 1000 → 300–500、或控制频率 10 Hz；BT 频率降；看合并雷达能不能降点数 / 频率。`motion_model: DiffDrive`、`vy_max 0` —— 机器人能横移（能力里 max_vy 0.25），换 `Omni` 在方块边侧移就不用整个转身（正是卡住的动作）。

## 13. 定位「慢」被当成「丢」：重置 MOLA 反而更不稳，任务判失败（3aj.5 回程 3、3ah.19）

- 现象：两次任务失败都是「定位丢失，已重置 3 次仍未收敛」（planned C1 去程、Nav2 回程 3）。期间：
  - 代理反复「定位变差了（在拿里程推算（定位器的位置是 0.5–0.6 秒前的））」↔「定位回来了」，一秒内来回；
  - 定位器「重定位到 …，σ 1.00（自动）」，MOLA `StateEstimationSimple reset()`；
  - **但每次修正量只有 1–16 cm，点云套图核对都「贴合度 0.70，对得上」**——MOLA 位置是对的，只是晚。
- 另：派单撞上「变差」那一瞬被拒 `not_localized`（11:50:15），重派就过；每趟转身都有一次约 5 s 的自动重定位停顿（10-28 的老问题，合并雷达 + IMU 开着照样有）；MOLA 转快时「Not able to use velocity motion model」。
- 建议：
  1. 位置只是晚（≤1 s）且点云核对对得上时，不升级成「丢定位」、不重置 MOLA；限速就够。
  2. 「已重置 3 次」的计数别把这种重置算进去。
  3. 站点派单的定位闸用一段时间的状态，不用一瞬间的。
  4. CPU（见 12）；原地大转身降转速让 MOLA 跟得上；用包复现 MOLA 转身参数。

## 16. 「定位丢失，已重置 3 次仍未收敛」是**整趟任务累计**的：转弯多于两三次的路线必失败（最要紧）

- 现象：今天 4 次任务失败全是这句——planned C1 去程、Nav2 回程第 3 趟、(2,−8)→起点、**用户网页上设的 5 点巡逻**（P1 (3.03, 1.00) ✅ 13:19:05、P2 (2.87, −3.22) ✅ 13:19:31、去 P3 (2.74, −6.07) 途中 13:19:40 失败，P4 (−0.10, −6.87)、start 没走）。巡逻失败那一刻**代理、定位器都没丢定位**：离开 P2 后 8 秒，日志里只有「交给 Nav2」。
- 原因（代码）：`engine/machine.py` `_recover_localization` 每次 `live.loc_reset_attempts += 1`；只有 `relocalized(..., reset_attempts=True)`（人给位置，`runtime.py:1553` `reset_attempts=human`）才清零。定位器自己重定位、稳下来**不清零**（W09a 内审应修 4 的本意：防来回跳的定位器一直走走停停）。`safety._loc_lost` 到 `MAX_LOC_RESET`（3）就 ABORT。
- 跟现场叠加：定位器每次转身都会自动重定位一次（σ 1.0 自动，修正量只有 2–5 cm，点云套图「对得上」，见 13），每次算 1 次 → 整趟里转 3 次弯就中止。巡逻那趟：13:18:50 出发转弯 1 次、13:19:23 P1→P2 一次、P2→P3 第 3 次 → 中止。
- 建议：
  1. 定位器自己重定位后，**点云套图核对对得上**就把计数清零（等同人给位置）；只有对不上、或真的连续丢才累计。
  2. 或者计数按「段」（当前点）算，到下一个点清零；再加一个时间窗（比如 2 分钟内 3 次才算来回跳）。
  3. 中止原因写清楚是哪 3 次（时间、修正量、核对结果），现在只有一句。
  4. 根子：转身就自动重定位（13、10-28 的「转身跳变」）。
- 验证：用这条 5 点巡逻（站点库里就有，`adhoc-836a50e4d18a`）在演示站点 / 仿真里转 4 个以上弯跑完；真机下次再跑一遍。
