# W30b 狗上证据加密 · 设计与完工报告

> W30 外审时单独列出来的未完成项：狗上断网暂存的证据没加密（`docs/W30-完工报告.md` 末尾）。分支 `w30b-evidence` → PR。设计与报告合一份。

## 用户决定（2026-10-09，决策 51）

三项都按推荐：

1. **加密什么**：照片、截图、录像（`.jpg`、`.mp4`）。清单、事件记录照旧明文：狗自己要读它们，判断一趟传完了没有，用站点公钥封了狗就读不了。建图录包、地图是雷达点云，没有图像，不加密。
2. **狗上没配站点公钥**（老狗、没装好）：照旧明文存、照常传，站点报 **P2**「狗上的照片、录像没加密」。不丢证据。
3. **升级前就在狗上的明文**：代理起来后自动补封。传到一半的，从头传封好的那份。

## 做成什么样

### 钥匙

- 站点上一对 **X25519** 钥匙：
  - **私钥** `/etc/d1max-site/evidence.key`：32 字节，`install-site.sh` 生成，跟 `secrets.key`、`backup.key` 一样只有站点用户能读、不进备份。**三把都要离线另存**，装机脚本收尾时会提醒。
  - **公钥**：`enroll` 时从私钥算出来，放进证书包 `evidence-pub.key`，拷到狗上 `/etc/d1max/evidence-pub.key`。
- **狗上只有公钥**：封得上、解不开。狗被偷了，盘上的照片、录像也看不了。

### 怎么封（契约 `d1max_contract.evseal`，狗、站点共用）

- **每个文件一对临时钥匙**：`共享 = X25519(临时私钥, 站点公钥)`，经 HKDF-SHA256 派生出加密口令和 MAC 钥匙（盐用两把公钥）。
- 加密和站点的 `sealbox` 一样：`openssl enc` AES-256-CTR（口令经环境变量给子进程，不上命令行），再算 HMAC-SHA256（先加密、后算 MAC，整段都算）。
- X25519 是纯 Python 写的（RFC 7748），跟 W30 的签名一个道理：狗上 OpenSSL 1.1.1，也不加 Python 依赖。对得上 RFC 7748 的测试向量。
- 文件格式：`D1EV1\n` + 临时公钥（32 字节）+ 密文 + MAC（32 字节）。文件名在原名后面加 `.d1e`。
- **拆的时候先核 MAC**，对不上一个字节明文都不写（不是这把私钥、被改过、截断都是这样）。

### 狗上

- **照片、截图**：`RunArchive.save_photo` 配了公钥就**从内存直接封进** `photos/<名字>.d1e`，**明文不落盘**。
  - 返回的还是原名：事件、汇总里记原名，站点解开后也是原名，两头对得上。
  - 人员截图也经它存，一并封。
  - 封不了（openssl 不在）就当照片存不下，不留半截。
- **录像**：ffmpeg 正在写的那一段在暂存目录（发件箱外）；写完的一段挪进发件箱时封成 `video.mp4.d1e`，封成了才删暂存里的明文。
- **补封旧的**：代理起来、上传线程开始之前，把发件箱里还是明文的照片、录像就地封上，上传队列里明文那一条销账。
- **封到一半的临时文件名以点开头**：发件箱扫盘跳过点开头的。不然半截文件会被排进上传队列，文件一消失，那一条就一直等在那儿。
- 代理新参数 `--evidence-pub`，缺省 `/etc/d1max/evidence-pub.key`：有这个文件就封，没有照旧明文。能力里报 `evidence.sealed`。
- `install.sh` 发现没有公钥只提示，不拒装。

### 站点上

- **收齐一个封好的照片、录像段，马上用私钥解开成原名**，成了才删封好的那份，再照常登记。照片判读、手机看图、录像回放读的都还是原名文件，一行没改。
- 解开以后，狗如果因为回执丢了又来问，站点那份封好的已经没了，狗从头再传一遍，站点再解一遍，结果一样，只是多花点流量。
- **解不开**（站点没配私钥、私钥不对、被改过）：封好的那份留在站点，报 **P2「狗封好的证据解不开」**，不登记。回执照回，狗那份会删掉，所以站点这份就是唯一的一份。配好私钥以后用 `d1max-site evidence-open` 补解、补登记。
- **狗报 `evidence.sealed` 是假**：报 **P2「狗上的照片、录像没加密」**，一台一次（记在 `evidence_plain` 表，库结构 39 版，跟待报告警同一个事务落库），装好公钥报真就清。老代理不报，就不说。
- 站点只收封好的照片、录像段，`manifest.json.d1e` 之类的不收。

## 已知限制

- **还有几处是明文**：
  - 录像正在写的那一分钟在暂存目录里；
  - 人员检测节点存的截图，到代理收进归档之前那一下；
  - 清单、事件记录（决策 51 定的范围）。
- **站点上解开以后是明文存的**，跟 W30 一样，靠站点主机本身的保护：盘加密、机房。
- **私钥丢了，封着传上来、还没解开的就再也解不开。** 已经解开的不受影响。
- 升级前已经传到一半的明文，站点上会留一个不完整的明文文件，不登记、不会被看到，按 W30 的留存期删。
- 每封一个文件起一次 openssl 子进程。一分钟一段录像、巡检一个点一张照片，量不大；Orin 的 AES 有硬件加速。真机上要量一下封一段录像花多久（`庄园场景待真机测试.md` §3p.8）。

## 测试

- 契约：
  - X25519 对得上 RFC 7748 §5.2、§6.1 的测试向量；
  - 封了拆得开，两次封的密文不一样（每个文件一对临时钥匙），明文不落盘，大文件流式；
  - 别的私钥、改一个字节、截断，都拆不开，一个字节明文都不写；
  - 钥匙文件：私钥 0600、已经有了不换、公钥十六进制；
  - 封到一半的临时文件名以点开头。
- 狗上：
  - 配了公钥，照片直接封，盘上只有 `.d1e`，返回原名，站点解得开；
  - 没配公钥照旧明文；
  - 封不了算存不下，照片目录里什么都不留；
  - 录像段封着挪进发件箱，暂存的明文删掉；
  - 代理有公钥文件能力报封了，没有报没封。
- 站点：
  - **端到端**：狗上真的发件箱补封旧照片，传上来，站点真的收件口解开、登记，跟原来一字节不差，狗上删掉，站点不留封好的；
  - 升级前明文已经排进上传队列：补封了照样传完、删掉；
  - 站点没配私钥：封好的留着、报 P2、不登记，配好了补解、补登记；
  - 私钥不对：解不开，封好的留着，一个字节明文都没写；
  - 封好的录像段：解开登记，登记的是解开后的大小和哈希；没配私钥留着、补解；
  - 封好的名字只认照片和录像段；
  - 狗报没封：P2 一台一次，装好了清，老代理不报；
  - 登记狗：证书包带证据公钥，`evidence-open` 能跑。
- 突变 11 条抓住 10 条：
  - 抓住的：配了也写明文、站点不解开、解不开也删、录像不封、清单也能封、没封每拍都报、不核 MAC、X25519 常数错、临时文件不藏、录像登记封好的哈希。
  - 「临时文件不藏」第一轮没抓住，补了「封的时候临时文件是点开头的」才抓住。
  - **活下来 1 条是等价的**：「补封不销账」。明文那一条不销账，上传线程只是对它退避重试；判断「这一趟能不能删」看的是盘上实际有的文件（封好的那些），传完照样整趟删、队列跟着清。销账只是让队列干净。

## 外审（2026-10-09，FIX-THEN-APPROVE）与修复

外审核对了 `f745264..1a1e8f1`，有 3 条阻断、1 条 Minor，都在分支 `w30b-review-fix` 上修了。

1. **补封失败后旧明文照样上传，能力还报「已加密」。**
   - 现在封不上的明文**扣着不传**：记进发件箱的 `unsealed`，上传器跳过它。这一趟也就确认不了、不删。
   - 上传线程**每分钟重封一次**，封上了就传封好的那份。
   - 录像段封不上就留在暂存里、记着，下一拍再封。暂存里扣着的段**也算录像配额**：openssl 一直坏着的话，从最旧的删起，报 `recording_dropped`，不会把盘写满。
   - 代理把件数报给站点，事件 `evidence_seal_failed`，站点报 **P2**「狗上 N 个照片、录像封不上，扣着没传」。都封上了报 `evidence_seal_ok`，告警自动解决。
   - 不降级上传明文。
2. **补解成功、登记失败后，再也补不了。**
   - `open_sealed` 不再删封好的那份。照片、录像都是**登记成了才删封好的**，登记失败就留着，下次 `evidence-open` 再解、再登记。
   - 补解录像时某一段登记出错只记日志，接着补后面的。
3. **解不开的录像没有留存、腾盘。**
   - 解不开的录像段**照样登记**，记成「还封着」：`recordings.sealed = 1`，库结构 40 版。
   - 留存期、盘紧腾盘、按时间段删除请求都按登记删，封着的也删得到；两份文件（封着的、解开的）都删。
   - 列表、回放不给封着的段，放不了。补解成了改成 0，大小、哈希换成解开后的。
   - 照片那头，解不开时这一趟照样登记（不登记照片），按趟删目录时封好的跟着删。
4. **Minor：X25519 不抗侧信道。**
   - 在 `evseal` 模块说明里写明了：梯子按私钥位走分支，Python 大整数运算也不是恒定时间。
   - 实际风险：狗上算的是每个文件新生成、用一次就扔的临时私钥；站点私钥只在站点主机上用。
   - 以后换成 OpenSSL 3 或 `cryptography` 的 X25519 再去掉这条。

**新增测试**（照外审的三个复现写）：
- 补封失败时明文一个字节都不传、这一趟不删，修好了重封、传完、删掉；
- 站点：封不上报 P2，封上了自动解决；
- 照片、录像解开后登记失败：封好的留着，补解能登记；
- 解不开的录像段：登记成封着、不列不放，过 91 天删掉，盘剩 1% 时也删得到，按时间段删除请求也删；
- 录像段封不上留在暂存、修好了下一拍封；扣着的段算配额；
- 代理报一次，件数变了不重报，都封上了报好了。

**突变**：12 条抓住 11 条。活下来的「`path()` 不看封着」是等价的：删一段时两个名字都删。
