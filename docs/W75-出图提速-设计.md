# W75 扫图走完以后少等 设计（待用户确认）

来源：用户 2026-11-04 现场（广场半室外扫图）：8 分钟的包，离线出图要 8 分钟，按 0.5 倍速回放是 16 分钟。不能让客户站在扫图的地方等。

## 一、现在的情况

- **正式流程是「边走边建」**（W09c2，工单 21）：扫图时机器人上实时跑 Super-LIO（话题 `/d1max_mapping/lio/odom`），走完以后不再重算轨迹，只剩打包：回环、去噪、栅格、定位先验。Super-LIO 装好时就用它，没装才退回 MOLA（`src/d1max_patrol/app/mapping.py` 的 `front`）。
- **今天没走这条路**：今天是手工录包，机器人上的定位器同时在跑 Super-LIO 定位，怕两个抢 CPU（Super-LIO 缺 CPU 会发散）。所以只能离线回放重算，这就是要 16 分钟的原因。
- **走完到出图要多久，没实测过**：打包在机器人上要几分钟，今天广场那次离线出图，会打印出打包用时（`prepare_s`），可以先当个参考。下次在机器人上用「边走边建」扫图时，把这个数记下来。

## 二、要什么

1. 客户扫完图，几分钟内能在手机或网页上看到图，确认没漏，然后离开。
2. 重算（换参数、轨迹不好要重来）不占着机器人，也不要求人在现场。
3. 离线重算不因为「跟不上实时」而发散，也不用为了稳妥放慢到 0.5 倍。

## 三、怎么做

### 3.1 扫图时只跑「边走边建」，不同时跑定位

- 进入扫图模式时，机器人上的定位器先停（扫图模式本来就不派任务）；退出扫图再起来。
- 这样 Super-LIO 独占 CPU，跟今天担心的打架问题没关系。
- Super-LIO 进程给高优先级，绑核（W68 已经给定位器这么做了，扫图照着来）。

### 3.2 走完：先出「预览图」，再出正式图

- 走完马上出一张**预览图**：直接用边走边建的点云，降采样后压成栅格，不做回环，一两分钟内能看。客户在手机上看有没有漏扫的地方，漏了当场补走。
- **正式图**（回环、去噪、栅格、定位先验）在后台打包，不用人等着。打包完成以后，在站点上通知「地图 X 第 N 版建好了，可以上机器人」。

### 3.3 重算放到站点主机上

- 站点**不收原始包**：今天 8 分钟就有 21 G，用 Wi-Fi 传比算还慢。
- 站点收**关键帧加轨迹**：每个关键帧是降采样后的点云，加上位姿，几百 MB。回环、去噪、栅格、调参以后重新打包，都只要这些。
- 只有「轨迹本身错了、要重算 LIO」时才要原始包。这种情况把机器人接到有线网或者拷硬盘，在站点主机上重算（站点主机要装 Super-LIO，安装包里加一个可选组件）。

### 3.4 离线重算按「一帧一帧」走，不按真实时间回放

- 现在的离线重算是按 0.5 倍速回放包给 Super-LIO，靠「放慢」保证它跟得上。算得快的机器也只能等着，算得慢的机器照样会发散。
- 改成**按帧推进**：回放程序发一帧，等 Super-LIO 把这一帧的位姿算出来再发下一帧（IMU 按时间戳一起发到下一帧为止）。这样不会因为跟不上而发散，CPU 能用满。台式机上估计比实时快几倍，要实测。
- Super-LIO 本身不用改：它每处理完一帧就发一条 `/lio/odom`，回放程序等的就是这条。

## 四、分几步

| 步 | 内容 | 好处 |
|---|---|---|
| 一 | 离线重算按帧推进（§3.4） | 今天这种手工包重算更快，也不发散；不用动机器人 |
| 二 | 扫图模式先停定位器；走完先出预览图（§3.1、§3.2） | 客户等的只有一两分钟 |
| 三 | 站点收关键帧加轨迹，在站点主机上重新打包（§3.3） | 重新打包、调参不占机器人 |

## 五、请用户定

1. 按上面三步的顺序做，行吗？
2. 第三步站点主机要装 Super-LIO（可选组件，GPL-3.0，单独进程跑，跟机器人上的一样），行吗？
3. 预览图不做回环，可能首尾差几十厘米，只给人看「有没有漏」，不能上机器人用。这样行吗？
