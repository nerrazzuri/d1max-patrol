## 交付

- **旁路进程协议 v3：`vel`**（`motion/patrol_agent.cpp`、`protocol/agent_frames.py`、仿真旁路）。带有效期的持续速度：比例值 ±0.5、`ttl_ms` 50..1000；**立刻回执**；速度线程在有效期内每 50 ms 发一次 `Move`，从静止起步先 `Gait` 一次，到期连发零速自停；新的 `vel` 覆盖旧的并续期；`halt`/`estop` 插队、作废有效期里的速度。趴着、锁死、姿态未知、任一路急停生效都拒。有一条测试直接读 C++ 源码，核对版本常量和这几项检查。
- **新包 `packages/adapter-d1max`**：`D1MaxHal` 复用根包的 `SidecarDeviceBackend`（连接、回执、状态与里程帧）。
  - **单位**：m/s 与 rad/s 换成比例值（`mps_per_unit` 默认 0.4、`radps_per_unit` 默认 1.0、`max_fraction` 默认 0.5、`deadband_mps` 默认 0.05，**都待实测**），夹上限后换算完再夹一次（`0.45×0.3÷0.3` 会比 0.45 多出一点浮点误差）；`VelocityResult` 如实报被夹了没有、拒了没有、为什么拒（`no_control`/`estop`/`not_ready`/`not_finite`/`no_lateral`/`deadband`/`sidecar: …`）。`invert_yaw` 用来应对 SDK 的转向正负跟约定相反。
  - **控制权**：`control_releasable=false`，`release_control()` 抛 `HalUnsupported`；`close()` 只断 Python 这头。代理收尾**看能力**，不能放的不去放（不是靠吞异常）。
  - **停没停**：刚发的速度还在有效期里不算停（真狗起步前 `Gait` 约 2 s，里程还是零）；里程超过 1 s 没来就不算停，定位质量也归零；阈值 `stopped_eps`（默认 0.02，可配）。
  - **急停**：软、硬两路**都**报「已解除」才算没急停；没状态帧或有一路 `Unknown` 都按急停算。
  - **姿态**：只有 `General`/`Gait` 算 READY；其余站姿算 STANDING，`LieDown`/`Locked` 算 LYING。姿态不是 READY 时不下发速度。
  - **执行器**：灯（front/back/both）；其余执行器与感知都抛不支持，能力里也都报 false（云台的单位没验过，不开）。
- **代理**：`d1max-agent --hal d1max [--sidecar 127.0.0.1:8090 --mps-per-unit … --radps-per-unit … --deadband … --max-fraction … --stopped-eps … --invert-yaw]`，这几个参数只认 `--hal d1max`。goto/patrol 等停止确认最多 5 s，等不到就再发一次停车，按 `stop_unconfirmed` 失败收尾。
- **装机**：`install.sh` 在根解释器和槽 venv 两处都装 `adapter-d1max`。`d1max-agent.service` **仍是 `--hal sim`、仍不 enable**；注释写了起用步骤：先停 `d1max-patrol.service`（同一时刻只能有一个 Python 通过旁路进程开车），或者用 `--legacy-http` 在同一进程里托管老 HTTP 面。
- **工具（本次都没在真机上跑）**：
  - `tools/w00d_probe.py`：**一条命令都不发**（连 `hold` 也不发）。看版本、控制权、姿态、电量、两路急停原始值、里程频率、站着时的里程速度最大值、故障帧。
  - `tools/w00d_motion_check.py`：不带 `--i-am-present` 连旁路进程都不连。命令**按比例值给**（默认 0.3，上限 0.35），不经过任何未实测的系数。走五步：原地慢转（看方向）、前进、停止用时、`ttl` 自停、死区。每步之后都停车并等停稳，异常和 Ctrl+C 也会先停车；最后给出建议的 `mps_per_unit`、`radps_per_unit`、`invert_yaw`。结果写进 `runs/field-logs/`。

## 设计取舍

1. **设计稿外加了两个参数**：`radps_per_unit`、`invert_yaw`（已补进设计稿）。转向方向反了，导航的转向环会越转越偏，所以方向是运动检查的第一步。
2. **急停取严**：硬急停没按时，真狗到底报 `Recover` 还是 `Unknown` 不知道。若报 `Unknown`，适配器会一概不走，探针会把它暴露出来（3b.2）。宁可不走也不赌。
3. **待命站姿取严**：只认 `General`/`Gait`。真狗待命时如果报的是别的，任务会全被拒，同样由探针暴露。
4. **`vel` 回执只等 0.5 s**：超时按拒绝算，导航随即按失败收尾。狗那头最多再走一个 `ttl` 就自己停。
5. **已知上限（同 `walk`）**：`Gait(2000)` 是 SDK 的阻塞调用，`halt`/`estop` 正好落在里面时要等它回来，最坏 2 s。SDK 没有能打断它的办法。
6. **转向没有死区参数**：HAL 的能力里只有前进死区。真狗若转向也有死区，导航在目标附近可能原地转不动。运动检查的第 5 步只量了前进。
7. **故障帧只留最近 20 条、从不清空**：就绪判断不看故障，目前没有实际影响；等见到真故障帧再定分级（现在按 `level>=2` 算致命，属于假设）。
8. **里程是运控自己的**（`OnMcData`），不是地图定位；W00d 只验速度环。

## 内部评审

只读子代理评审一轮，在仿真旁路上复现过。结论是先修再批准，**阻断 1 条，已修**：运动检查按 m/s 给命令，默认系数下被悄悄夹到比例 0.5，第一次前进就用了最大比例，算出的建议系数错 1.5 倍；测试用的参数恰好绕过了夹限。现改为按比例值给命令，被夹就中止，并补了默认参数的测试。

应修的都已修：
- 急停一路 `Unknown` 被当成没急停（旁路进程在客户端刚连上时会补一帧全零的占位状态）。
- 趴着、锁死、急停时速度照样下发到真机，C++ 也不拦。急停期间收下的速度，急停一解除就会生效。
- 速度线程在拿 SDK 锁之前判断「该不该走」，等锁或 `Gait` 期间被叫停后，仍会发一条过期的 `Move`；`Gait` 的返回值不看。
- `vel` 等回执 5 s，会冻住代理的速度环。
- 「停没停」可能永远不成立，任务卡在 RUNNING。

建议也修了：收尾那 150 ms 里新来的 `vel` 会被吞掉。

记为取舍：转向死区（取舍 6）、故障只增不减（取舍 7）、低于 50 ms 的 `ttl` 被抬到 50 ms（旁路进程的下限，不记日志）。

评审指出 C++ 的速度线程没有行为测试，只有编译和源码核对。要给它加测试，得造一个假的 `SDKClient`，本次没做，列进待办。
